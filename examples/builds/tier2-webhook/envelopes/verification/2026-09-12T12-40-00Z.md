## 3. Blockers

**PV-001 · M1-S02 · grounding · P0 — the build needs a field permission it grants nowhere.**
`Tier2_Webhook_Admin`'s `fieldPermissions` covers `Integration_Failure__c` only. M1-S03 reads
`Case.Tier2_Notified_At__c` for the ten-minute suppression window and writes it on webhook success;
M1-S04 queries it for the 24-hour success check. D14 and Q23 put both in API 67.0 default user mode
as the escalating or scheduling user, and `agents/_shared/AGENT_CONTRACT.md`'s version table states
that at 67.0+ SOQL, SOSL, DML and `Database` methods enforce the running user's FLS *with no keyword
at all*. M1-S04's own `inputs.running_user` names the gap — "Tier2_Webhook_Admin from M1-S02 carries
the `Integration_Failure__c` half" — and no `assumptions[]` row covers the other half. No acceptance
test looks for a missing grant, so this reaches the org as a silent dedupe failure.
*Fix:* add `Case.Tier2_Notified_At__c` (readable, editable) to M1-S02's permission set, extend that
step's manual test to confirm it, and say whether M1-S04's scheduling user is inside the D14
assignee set.

**PV-002 · M1-S03 · grounding · P0 — the detection mechanism is grounded in nothing the step cites.**
"OwnerId changed in this save to the Tier_2_Engineering queue" requires resolving a queue developer
name to a Group Id. None of the nine cited skills documents that lookup, and neither does
`apex-builder`'s own 33-entry `dependencies.skills`. The library has the skill that does —
`skills/apex/apex-hardcoded-id-elimination`, whose `references/examples.md:93` is "Example 3 —
Group/Queue assignment for Case routing" with a cached `SELECT Id, DeveloperName FROM Group WHERE
Type = 'Queue'` — and `apex-builder`'s `REFUSAL_SECURITY_GUARD` clause (d) refuses the hardcoded-Id
alternative. The step as written leaves its builder a choice between freestyling and a refusal.
*Fix:* add that skill to `M1-S03.skills[]` and say in `inputs.detection` that the queue Id comes
from a cached `Group` query on `DeveloperName`.

**PV-003 · M1-S04 · testability · P1 — no automated test on the step can fail on an absent artefact.**
Run against an empty directory, `check_apex_scheduled_jobs.py` exits 0 ("no .cls files found …
nothing to check") and `check_apex_queueable_patterns.py` exits 0; the `xml` test has nothing to
parse; the `manifest` test is `skipped-not-applicable` under the Apex exception. M1-S01 and M1-S02
are caught by the always-on manifest check and M1-S03 by `check_callouts_and_http_integrations.py`
(exit 1 on an empty tree); M1-S04 has no equivalent. `check-outputs` still gates `set-status built`,
which is why this is P1 — but the lens row is refuted on its own terms.
*Fix:* add a stdlib-only `command` test asserting the CRON literal and the two thresholds, or carry
the assertion in an M1 milestone test over `artefacts/`. **`amend-step` cannot make this edit now**:
`build_plan.py amend-step` is refused unless the build status is `building` or `approved`, and this
build is `planned`, so it belongs in the next plan body.
