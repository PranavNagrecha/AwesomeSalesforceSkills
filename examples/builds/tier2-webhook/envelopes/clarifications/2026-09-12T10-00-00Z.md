## Summary

Clarified `requirement.md` (Tier 2 Case-escalation → on-call webhook + platform
event, retries + visible failure record, API key never in code/Custom
Setting). Searched local coverage across 12 capability phrases, kept 8 skills
that carry a `## Questions to Ask Before Configuring` table, harvested every
row of each plus the generic `admin/requirements-gathering-for-sf` set and one

`set-clarifications` and rendered `CLARIFICATIONS.md`. Build `status` is now
`clarifying`. The sizing computation itself moved twice — see "Sizing line"
below — landing at **`scale: project`**, not the `feature` floor anticipated
going in.

## Confidence: MEDIUM

Every capability phrase returned index hits and every clarification traces to
a harvested table row, the generic set, or one of the two decision trees — the
HIGH bar. Confidence is capped at MEDIUM because six clarifications
(`Q6`, `Q7`, `Q8`, `Q22`, `Q16`, `Q19`) have `default_source: "none"` on a
genuinely design-changing question (vendor contract details and org-specific
facts no skill or requirement text can supply) — more than a negligible
fraction of the 24 blocking rows, though short of the "more than a quarter"
MEDIUM threshold on the full 45-row set (6/45 = 13%). Recorded conservatively
as MEDIUM rather than HIGH given how much of the design hinges on those six.

## AGENT.md / CLI gaps found at the feature tier

1. **No feature→project re-tier test.** § 3.1 gives the ask tier an explicit
   mid-Step-4 escalation ("if more than eight rows are blocking, the
   requirement was never an ask; re-tier to feature"), but states no
   equivalent test for feature exceeding its own inherited ≤8-blocking
   ceiling. This build hit 24 blocking rows at what Step 1 computed as
   `feature`. I applied the ask→feature test by analogy and re-tiered to
   `project`, but AGENT.md does not itself authorize or describe this move —
   a future run without that judgment call would either silently violate the
   ≤8 ceiling at `feature`, or a stricter reading would refuse to proceed at
   all pending human input on which tier applies.
2. **`set-clarifications` does not implement the feature-tier pre-fill.**
   § 3.1's tiers table describes feature's clarification scope as "those
   [the ask-tier row: proposed defaults, one round, informational rows
   pre-filled], plus one question per decision tree." I verified directly: a
   scratch build initialised with `--scale feature` and given the same
   `clarifications.json` left every informational row `status: "open"` with
   no `answer` written — `set-clarifications --help` itself says the
   pre-fill only fires "At scale 'ask'". The CLI's actual behavior does not
   implement the feature-tier inheritance the tiers table describes in
   prose. Confirmed by direct test, not inference — see the transcript in
   Process Observations.
3. **`owner_hint` is not a schema field.** AGENT.md's Step 4 worked example
   and its Output Contract table both use the key `owner_hint`. The actual
   `agents/_shared/schemas/build-plan.schema.json` clarification-item schema
   has no `owner_hint` property at all; it has an undocumented `asked_by`
   (bare `{"type": "string"}`, no description) that may or may not be the
   same field under a different name. `owner_hint` still lands in `plan.json`
   only because the schema's `additionalProperties` is not restrictive at
   that level — it is carried, not validated. This run wrote `owner_hint`
   throughout, per AGENT.md's explicit instruction, and flags the mismatch
   rather than guessing which name is canonical.
4. **`owner_role: null` is schema-illegal**, though AGENT.md Step 4 says to
   "fall back … to `null` when [the RACI vocabulary] names none."
   `build-plan.schema.json` types `owner_role` as `string` with
   `minLength: 1` — `set-clarifications` refused the write with a schema
   ERROR until every `null` was replaced with the requirement's named
   requester ("Support Engineering lead (Pranav)"), which is the *other*
   fallback AGENT.md names in the same sentence. Used that fallback
   throughout instead.

## Process Observations

**Healthy**
- The requirement states the security-sensitive fact up front ("the API
  key must never be stored in code or a custom setting"), which is exactly
  the fact `apex/apex-named-credentials-patterns` and
  `integration-pattern-selection.md`'s "Named Credentials — always, not
  sometimes" section both independently insist on — no contradiction to
  resolve. (evidence: requirement.md; skills/apex/apex-named-credentials-patterns/SKILL.md; standards/decision-trees/integration-pattern-selection.md)
- The eight kept skills' Questions-to-Ask tables agree with each other on
  the core mechanism shape (Named Credential + External Credential,
  Queueable with `AllowsCallouts`, status-code-classified retry) — nothing
  required `standards/source-hierarchy.md` adjudication.

**Concerning**
- `admin/outbound-message-setup` surfaced as a top-2 result for "outbound
  HTTP callout to external system" despite Outbound Message's host
  (Workflow Rules) having reached end of support 31 Dec 2025, per
  `integration-pattern-selection.md`'s own anti-patterns list. A future
  search on the same phrase will keep surfacing a legacy mechanism ahead of
  its replacement until the skill or its trigger phrasing is revisited.
  (evidence: repo_scan, skills/integration/outbound-webhook-from-salesforce vs skills/admin/outbound-message-setup search ranking)
- The Step 1 sizing line computed `feature`; the Step 4 harvest computed a
  blocking count that only fits `project`. This is exactly the
  "printed sizing line's D/S/O/X counts disagreeing with the tier actually
  in effect" case AGENT.md's own Concerning bullet names — recorded and
  acted on (re-tiered), not just noted.

**Ambiguous**
- Whether the ops dashboard's "already subscribed" platform-event
  consumption counts as a `standards/build-orchestration.md` § 3.1 "second
  system" for the X signal was a genuine judgment call: I did **not** count
  it (kept X at `implied`, not the project-tier "second system" value),
  reasoning that no new authentication, retry or endpoint contract is built
  for it — only an event schema. A reader who weighs the requirement's own
  words ("a separate system") more heavily could reasonably disagree; either
  reading now converges on `project` once the Step-4 blocking count is
  counted, so the disagreement did not change the outcome, but would have
  under a smaller harvest.
- `admin/case-management-setup`, `admin/assignment-rules`,
  `admin/escalation-rules` and `admin/process-automation-selection` all
  carry question tables and surfaced from legitimate searches, but were
  excluded from the harvest because the requirement states their subject
  (the queue and its escalation rule) already exists. This is a relevance
  judgment, not a mechanical "has no table" drop — a stricter reading of
  Step 3 ("keep every skill that has a table") could argue all four should
  have been harvested regardless, adding roughly another 20+ rows.
- Six blocking questions (`Q6`, `Q7`, `Q8`, `Q16`, `Q19`, `Q22`) carry
  `default_source: "none"` because they depend on the on-call tool's actual
  vendor contract or this org's own volume/ownership facts — no skill or
  requirement text could supply a default without inventing one.

**Suggested follow-up agents**
- `build-planner` (`/plan-build`) once G1 is recorded — the standard next
  step in the loop.
- `permission-set-architect` (`/architect-perms`) — `Q19` and `Q20` are
  exactly its design surface (the External Credential principal's
  permission set, and who may see/resend the failure record); this agent
  proposes the access questions but never designs the permission set
  itself.
