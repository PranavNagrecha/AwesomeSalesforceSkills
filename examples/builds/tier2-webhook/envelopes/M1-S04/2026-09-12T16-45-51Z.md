# apex-builder — M1-S04, run 4 (§ 0d test-only repair, S2-F-12)

**Build:** `tier2-webhook` · **Step:** `M1-S04` · **Run:** 4 · **Confidence:** MEDIUM

## Summary

Run 4 of `M1-S04` — a second, narrower § 4 test-only repair, after
`reports/MOCK-DEPLOY-M1.md` run 7 (S2-F-12), the same finding that sent
`M1-S03` back to `running` a second time. Run 6's fix (§ 0c, S2-F-11) got
every test method into `System.runAs(agent)` with a permissioned user; run 7
then failed all 30 test methods across `M1-S03` and `M1-S04` at the same
`@TestSetup` seed insert of `Case`, on `fieldNames: AccountId`.

The cause is in the shared factory, not the test: `TestDataFactory.createCases`
assigned `AccountId = accountId` unconditionally, so `Tier2ChannelHealthTest.seed()`'s
null `accountId` argument still marked the field populated. Under API 67.0's
default user mode, the plain `insert` inside `System.runAs(agent)` checked FLS
on that populated-but-null field, which the `Standard User`-profile agent has
no create access to.

**Fix:** `artefacts/M1-S04/classes/TestDataFactory.cls` replaced with a
verbatim copy of the corrected `templates/apex/tests/TestDataFactory.cls`
(commit `5edcb3281`). Diff against the template is empty (confirmed this run).
`Tier2ChannelHealthSchedulable.cls`, `Tier2ChannelHealthQueueable.cls` and
`Tier2ChannelHealthTest.cls` are all unchanged — the existing seed already
called `createCases(1, null, overrides)` and no test method reads or asserts
on `Case.AccountId`, so no test needed a compensating edit.

A parallel repair of the same shape is running on `M1-S03`; this run touched
no file under that step's artefacts.
