`reports/MOCK-DEPLOY-M1.md` run 6 (S2-F-11) applies to `Tier2ChannelHealthTest` the same
finding that sent M1-S03 back to `running`: `Tier2ChannelHealthQueueable`'s three aggregate
`COUNT()` queries enforce the running user's FLS by default (API 67.0 user mode), and
`Tier2ChannelHealthTest` had no `System.runAs` block for a permissioned user — every method
ran as the deploying user. This is a test-only repair (§ 4 of `standards/build-orchestration.md`,
`documented` → `running`): `Tier2ChannelHealthSchedulable.cls` and
`Tier2ChannelHealthQueueable.cls` are unchanged.

`templates/apex/tests/TestUserFactory.cls` is **not** shipped in this step's artefacts — it
already ships in M1-S03's (added by that step's own S2-F-11 repair) — per the task's explicit
instruction not to add a second copy. `Tier2ChannelHealthTest` gained:

- `PERM_SET = 'Tier2_Webhook_Admin'` and `PROFILE = 'Standard User'`.
- A new mixed-DML fence in `@TestSetup` — `System.runAs(new User(Id = UserInfo.getUserId()))`
  wrapping only the `TestUserFactory.createUser(PROFILE, new List<String>{ PERM_SET })` call.
  This class had no pre-existing setup-object fence to fold into (it inserts no setup object
  of its own), so the fence is new, matching the shape `skills/apex/test-class-standards`
  gotchas.md Gotcha 13 and examples.md Example 5 prescribe.
- Business-data seeding (`TestDataFactory.createCases(...)`, `buildFailures(2)`) moved inside
  a second `System.runAs(agent)` block, unchanged otherwise.
- A re-queried `agent()` helper, identical in shape to M1-S03's.
- Every existing `@IsTest` method's body wrapped in `System.runAs(testUser) { ... }` (`User
  testUser = agent();` precedes each block) — same statements, same assertions, same
  messages, same order. Nothing was added, removed or changed in any `Assert.*` call — verified
  with a whitespace-insensitive diff against the pre-repair file: every hunk is a pure
  insertion, zero removed lines.

## Process Observations

**Healthy:**
- The fix required zero changes to `Tier2ChannelHealthSchedulable.cls` or
  `Tier2ChannelHealthQueueable.cls` — S2-F-11 is precise about the boundary (a test-fixture
  defect, not a production-code one), and this repair stayed inside it, exactly as M1-S03's
  repair did for its own classes.
- The fix shape already existed in the library twice over: `references/examples.md` Example 5
  and M1-S03's own already-shipped repair are both worked instances of the same pattern. This
  repair is a direct application of both, not a new pattern.

**Concerning:**
- This is the **second** step in this build to ship with `check_test_class_standards.py`
  absent from its declared `acceptance_tests`, and the second to be caught only by a
  milestone-level mock deploy rather than by its own step's tests. A checker that exists, is
  correct, and would catch the defect offline, but is wired into neither step's
  `acceptance_tests`, is a planning gap that now has two instances in one milestone.
- `standards/build-orchestration.md` § 4's Apex-foundations recommendation (a dedicated step
  for a `templates/apex/**` class shared by more than one Apex step) now has **two** grounds
  in this build — `TestDataFactory` (recorded at M1-S04's original build) and, as of this
  repair, `TestUserFactory` — and the plan still has no such step.

**Ambiguous:**
- `Tier2_Webhook_Admin` (confirmed via `artefacts/M1-S02/permissionsets/Tier2_Webhook_Admin.permissionset-meta.xml`)
  grants no permission on `PermissionSetAssignment`. `rosterResolutionReturnsTheDistinctActiveAssigneeEmails`
  queries that object directly and now runs as the same permissioned agent under user-mode
  default — whether the query still returns rows for a `Standard User`-profile agent, rather
  than throwing or reading empty, is the same open question deploy-order.md § 4 item 1 already
  raises for the production running user. This repair surfaces it in the test rather than
  resolving it: resolving it means changing `Tier2_Webhook_Admin`, which belongs to M1-S02, a
  different step, out of scope for a test-only repair.
- `scheduleCreatesAWaitingCronTriggerAndDispatchesTheQueueable` now calls `System.schedule` and
  queries `CronTrigger`/`AsyncApexJob` as the same `Standard User`-profile agent. No cited
  skill states whether that profile can schedule Apex or read those two system tables.
- `PROFILE = 'Standard User'` is, again, the library's own worked-example default rather than
  a value any of this build's clarifications names — the same ambiguity M1-S03's repair
  flagged, now present in a second class.

**Suggested follow-up:** `milestone-verifier` — the same recommendation M1-S03's repair made
still holds and is now stronger: `milestone:M1` was approved on evidence that predates S2-F-06
and S2-F-11, and this repair is the second of two steps in that milestone whose tests changed

tests is what re-signs the M1 acceptance both repairs put back in question.
