## 2. Blockers

### PV-001 · P0 · `M1-S02` — the field permission the build needed and granted nowhere

`Case.Tier2_Notified_At__c` is now granted, `readable` and `editable`, in
`inputs.permission_set.fieldPermissions`, alongside the `Integration_Failure__c` fields it already
carried. Four related edits:

- **No `Case` `objectPermissions` row is added**, and a new `objectPermissions_scope_note` says why:
  the users this set goes to already hold Case object access from their profile, a CRUD row here
  would grant more than any answer asked for, and the checker's object-row rule only fires when a set
  that *has* a row for an object grants a field on it without `allowRead=true`. A `fieldPermissions`
  entry with no matching object row is the legal, narrower shape. Recorded as assumption **A14**.
- **The build-scope permission-set test's description now separates what it proves from what it
  cannot.** It proves the entry is well-formed — `editable` true with `readable` true, ERROR
  otherwise — and that it does not sit beside a Case object row lacking `allowRead`. It cannot prove
  *absence*: no checker in the library fails because a grant was never written.
- **So the manual test reads for the entry by name** — clause (d) of `M1-S02`'s manual test now asks
  the reviewer to confirm `Case.Tier2_Notified_At__c` is present with both flags, and says plainly
  that no checker fails on its absence, so the reviewer is the check.
- **D14's assignee set now names the scheduling user.** The verifier asked whether `M1-S04`'s
  scheduling user is inside it; nothing in the answers implies it, so the decision is restated as the
  union — every user who can escalate a Case, *plus* the user who schedules the hourly job — and
  assumption **A13** records that as something to confirm. `M1-S04.inputs.running_user` no longer
  names the gap; it states that `Tier2_Webhook_Admin` now carries both halves.

### PV-002 · P0 · `M1-S03` — the queue lookup is now grounded

`apex/apex-hardcoded-id-elimination` is added to `M1-S03.skills[]` (ten now) and to the matching
`fit_gap` row. `inputs.detection` binds the shape rather than leaving it to the builder: a private
static `Map<String, Id>` populated once per transaction from
`SELECT Id, DeveloperName FROM Group WHERE Type = 'Queue'`, read through a `queueId(String devName)`
accessor — pasted from that skill's `references/examples.md` Example 3, "Group/Queue assignment for
Case routing", read off disk. The note also names why a literal Id is not the fallback:
`apex-builder`'s `REFUSAL_SECURITY_GUARD` clause (d) refuses it.

**Its checker is deliberately not declared as a test.**
`check_apex_hardcoded_id_elimination.py` takes `--src`, not `--manifest-dir` — a fourth non-standard
argument form beyond the three § 5 lists — and a checker command without `--manifest-dir` costs a
`validate` WARN, which this plan is required to finish without. Probed to confirm rather than
assumed: `--manifest-dir` exits 2 with `unrecognized arguments`; `--src <fixture>` prints
`OK: scanned 4 Apex class(es); no findings` and exits 0.

### PV-003 · P1 · `M1-S04` — a test that fails on an absent artefact

`M1-S04` now declares `check_error_handling_framework.py --manifest-dir artefacts/M1-S04` at step
scope. This is the first of the three options ranked in the brief — a checker among the step's
already-cited skills that fails on "no .cls files" — so the reading list did not grow. Its
description records the behaviour the test relies on:

```text
empty artefacts/M1-S04   exit 1
  ISSUE: No .cls or .trigger files found under <dir> — confirm --manifest-dir points to a
         Salesforce metadata source directory
this step's three classes  exit 0   "No issues found."
```

It is not only a presence check: on files that exist it fails on rollback-unsafe logging,
`AuraHandledException` boundary violations, `BatchApexErrorEvent` truncation risks and bulk publish
anti-patterns, which is why its skill was already cited here before the verifier asked.

Candidates probed and rejected: `check_apex_scheduled_jobs.py` and `check_apex_queueable_patterns.py`
both exit 0 on empty. `check_test_class_standards.py` also exits 1 on empty and was left out to keep
the test list proportionate.
