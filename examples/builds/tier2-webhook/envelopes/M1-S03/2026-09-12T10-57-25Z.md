## 1. The refusal in one paragraph

`agents/apex-builder/AGENT.md` Step 6 requires that every `templates/apex/**` class an
emitted class or test references is shipped in this step's own outputs as a **verbatim**
copy plus its `-meta.xml`, or is already declared by an earlier plan step. Three of the
five templates this step's `templates[]` mandates fail that test **transitively**: they
reference further `templates/apex` classes which in turn require a custom object and two
custom metadata types that **no step of this plan ships**. Shipping the callers without
them fails deploy with `Variable does not exist: ApplicationLogger` /
`Variable does not exist: TriggerControl`; shipping `ApplicationLogger` contradicts this
step's own `inputs.logging_decision_2026_09_12`, which the requester and the dry-run
operator settled ninety minutes ago after exactly this finding on M1-S04.

## 3. Why the 2026-09-12T10:51:56Z amendment did not clear this step

The amendment set `include_logger: false` and removed
`templates/apex/ApplicationLogger.cls` from `templates[]`. That closes the logger at the
level of **the classes this agent writes**, which is exactly what M1-S04 needed —
M1-S04's `templates[]` is now `templates/apex/tests/TestDataFactory.cls` alone, which is
self-contained, so that step is unblocked by the amendment.

M1-S03 is the only step whose `templates[]` carries `TriggerHandler`, `BaseService` and
`HttpClient`, and the dependency lives one level below `include_logger`: inside the
template bodies. `inputs.callout_endpoint` still says the endpoint is *"composed through
`templates/apex/HttpClient.cls`"* and decision **D4** still mandates that template, while
`inputs.logging_decision_2026_09_12` says *"Do not reference ApplicationLogger."* Both are
bound inputs of the same step and they cannot both be satisfied.

`TriggerControl` is the half of this that the M1-S04 discussion never surfaced: it is a
second unshipped template with a second unshipped custom metadata type, reached through
`TriggerHandler`, which `templates[]` cites without it.

## 4. Two remedies — a human picks; this agent does not

**(A) Add an Apex-foundations step.** `standards/build-orchestration.md` § 4, Apex row
note, prescribes exactly this shape when more than one Apex step shares a template
dependency. A `metadata-builder` step shipping, all of which already exist in the repo and
need only be copied:

- `templates/apex/custom_objects/Application_Log__c.object-meta.xml` + its fields
- `templates/apex/cmdt/Logger_Setting__mdt/` + `Minimum_Severity__c`, plus a `Default` record
- `templates/apex/cmdt/Trigger_Setting__mdt/` + `Object_API_Name__c`, `Handler_Class__c`, `Is_Active__c`

M1-S03 then `depends_on` it and ships `TriggerHandler`, `TriggerControl`, `BaseService`,
`HttpClient` and `ApplicationLogger` verbatim under the provenance rule.

*Costs:* a sixth functional step in a `feature`-tier plan, and it re-opens **Q16** — whose
answer was about *where failures are visible to Support Engineering*, not about whether a
framework log table may exist alongside `Integration_Failure__c`. That is a question for
the requester, not an inference for this agent.

**(B) Drop the three templates.** `amend-step` this step's `templates[]` and
`inputs.callout_endpoint` to remove `TriggerHandler.cls`, `BaseService.cls` and
`HttpClient.cls`, and authorise build-local, dependency-free equivalents grounded in the
cited skills' `references/code-examples.md`. Each new `.cls` and `-meta.xml` is declared in
`outputs[]`.

*Costs:* decision **D4** mandates `HttpClient`, so D4 is revisited in the same amendment;
`AGENT_CONTRACT.md` rule 2 means the authorisation has to be explicit in the plan rather
than assumed by the builder.

**Considered and rejected:** shipping a class *named* `ApplicationLogger` or
`TriggerControl` that is not byte-identical to the canonical template. The provenance rule
says verbatim, and a same-named divergent copy misleads every later reader of both this
build and the template library.

## 6. Two findings that survive the refusal and belong to the rebuild

1. **The endpoint path is unsettled.** M1-S02's `OnCall_Tool` Named Credential carries
   `Url` = `https://api.oncall.example/v1/salesforce/escalations` — the full path. This
   step's `inputs.callout_endpoint` describes the endpoint as *"`callout:OnCall_Tool` plus
   a path"*. Appending any segment would POST to `/v1/salesforce/escalations/<segment>`.
   Whoever amends this step should settle whether the path suffix is empty.
2. **`TestDataFactory` will be shipped twice.** M1-S04 already ships a byte-identical copy
   at `artefacts/M1-S04/classes/TestDataFactory.cls`, and this step's tests need it too.
   `mock_deploy.py:copy_artefacts` rebases both onto the same assembled path, so the deploy
   tree is correct either way — but **M1-S05's `package.xml` must emit the `TestDataFactory`
   `ApexClass` member exactly once.** The same applies to every template class remedy (A)
   would add.
