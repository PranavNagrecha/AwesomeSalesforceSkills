## Why the gap exists, and why it is not a surprise

`deploy-order.md` § 5 item 3 already recorded, at run 2/3, exactly this gap and exactly
why it was left open: every existing `Tier2WebhookQueueableTest` method drives
`Tier2WebhookQueueable` to a result that lets `execute()` return normally (success,
permanent failure, or a transient failure with the attempt budget already spent), so
`Tier2WebhookFinalizer.execute(ctx)` — attached unconditionally — always sees
`ParentJobResult.SUCCESS`. The one branch that would give it `UNHANDLED_EXCEPTION`
requires the Queueable to throw for real, and **"an unhandled exception in a job run by
`Test.stopTest()` fails the test method."** That finding was this run's starting point.

## What changed, and what did not

One new file pair, nothing shipped touched:

- `artefacts/M1-S03/classes/Tier2WebhookFinalizerTest.cls` (new)
- `artefacts/M1-S03/classes/Tier2WebhookFinalizerTest.cls-meta.xml` (new, `apiVersion` 67.0)

**Why a new file rather than more methods on `Tier2WebhookQueueableTest`:**
`agents/apex-builder/AGENT.md`'s Output Contract and Escalation Rules never let this agent
modify an existing shipped file in place (`REFUSAL_OUT_OF_SCOPE`), and every other
production class this step ships already has its own dedicated test class.
`Tier2WebhookFinalizer` gets the same treatment.

**How the branches are reached without the "throw fails the test" problem:**
`skills/apex/apex-transaction-finalizers/references/code-examples.md` hits the identical
problem for its own worked Finalizer and solves it by extracting a `@TestVisible`
`handle(...)` decision seam that a test calls directly. That option is closed here — it
would mean editing `Tier2WebhookFinalizer.cls`, out of scope. Instead,
`Tier2WebhookFinalizerTest` calls the class's own `public execute(FinalizerContext ctx)`
method directly, as a plain synchronous call, against a hand-built class that implements
`System.FinalizerContext` (its four documented methods — `getAsyncApexJobId`,
`getRequestId`, `getResult`, `getException`; there is no `getJobId()`). No
`System.enqueueJob` of the parent job, no `Test.startTest()`/`Test.stopTest()` — the
platform machinery that fails a test on an uncaught async exception is never invoked.

**UNVERIFIED, and named up front rather than buried:** no skill in this repo confirms or
denies that customer code may implement `System.FinalizerContext`. It is not the technique
`apex-transaction-finalizers` uses in its own worked example. The interface's four-getter
shape matches `QueueableContext`/`BatchableContext`, and nothing states implementation is
forbidden, but this is an inference, not a citation. **Confirm against a scratch org
before trusting the coverage number this file contributes.** If it does not compile, the
fallback is the seam this run deliberately avoided — a shipped-code change, out of scope
here.
