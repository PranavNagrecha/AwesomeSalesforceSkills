plain `insert` checked FLS on it (API 67.0+ default user-mode DML). See
`skills/apex/test-class-standards/references/gotchas.md` Gotcha 14, which names this
exact org message and this exact build as its source.

## What the playbook/CLI did not fully support

- **`amend-step` was not used and would not apply here.** This repair changes a file's
  *content*, not the step's declared `outputs[]` or `templates[]` — `TestDataFactory` was
  already listed there before this run, so there is nothing to amend.
- **M1-S04 ships an independent, byte-identical (pre-fix) copy of the same
  `TestDataFactory.cls`, and it was out of scope for this M1-S03-only repair** (finding
  S5-F-02). `deploy-order.md` § 2 already documents that `mock_deploy.py`'s
  `copy_artefacts` rebases both steps' copies onto the same assembled path, so the two
  copies must now be corrected independently for the assembled tree to be
  order-independent — the coordination cost the same section already names as the reason
  an Apex-foundations step should exist. Fixing M1-S04's copy is not this run's to
  perform; it is named as a follow-up.
- **No `package.xml` change** — unchanged from run 4's reasoning: this `apex-builder`-owned
  step declares no manifest (`standards/build-orchestration.md` § 5, The Apex exception),
  and `TestDataFactory`'s membership at M1-S05 is unaffected by a content-only fix.
