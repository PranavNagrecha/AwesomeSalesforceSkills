## The fix

Two new methods in `Tier2EscalationServiceTest.cls`, calling
`Tier2EscalationService.escalate(List<Case>)` **directly** — a deliberate deviation from
the rest of the file, documented in a new comment block, since neither gap is reachable
through the trigger path:

1. **`escalateWithNoCasesReturnsImmediately`** — `escalate(null)` and
   `escalate(new List<Case>())`; asserts no enqueue, no DML. Covers line 44.
2. **`escalateWithAMissingCaseNumberWritesAPublishFailureRowAndStillEnqueuesTheJob`** —
   constructs an in-memory `Case` with `Subject`/`Priority` set but `CaseNumber` left
   unset. `Tier2_Escalation__e.Case_Number__c` is `required=true` (M1-S01) and
   `escalate()` maps it straight from `Case.CaseNumber` with no null guard, so this
   rejects the publish deterministically — on a **required-field violation**, not an FLS
   one. This is a different mechanism than S2-F-13's (a missing `Tier2_Escalation__e`
   Create grant): that asymmetry can no longer be constructed from this build's shipped
   permission sets, since S2-F-13's own fix bundled both grants
   (`Integration_Failure__c` CRUD and `Tier2_Escalation__e` Create) into the same
   `Tier2_Webhook_Admin` set. Asserts the failure row's `Case__c`, `Status__c` (`New`),
   `Severity__c` (`Error`), `Attempt_Count__c` (1), a blank `Endpoint__c`, and that
   `Error_Message__c` carries `errorText()`'s output — plus that the webhook job is still
   enqueued (Q11: a lost event is the tolerable half). Covers lines 84–96, 106, 119–127.

**Both methods register a 2xx mock before calling `escalate()`**, applying § 0e's lesson
(S2-F-15) proactively: `escalate()` unconditionally enqueues a `Tier2WebhookQueueable`
(line 103) regardless of publish outcome, and the org's own run 10 already proved that
job runs to completion by the end of the test method regardless of
`Test.startTest()`/`Test.stopTest()` wrapping.
