## Manual checklist — for the M1 gate

Verbatim, one entry:

> Given Q24, when each layout file is read, then `<layoutSections>` is preceded by the
> assignment-rule checkbox default set on, and every field a validation rule attaches an
> error to (assumption A13) is present on both layouts.

Shape check: well-formed Given/When/Then, names an observable outcome, tickable rather
than unusable. Two caveats before it is ticked.

**Half 1 — the checkbox.** Both layouts carry
`<showRunAssignmentRulesCheckbox>true</showRunAssignmentRulesCheckbox>`. This run applied
the **presence** reading. A literal **positional** reading fails: on both files the child
order is `layoutSections, layoutSections, showEmailCheckbox, showRunAssignmentRulesCheckbox,
showKnowledgeComponent`, so the checkbox follows the sections rather than preceding them.
The presence reading was applied because the cited skill's canonical Layout example
(`record-types-and-page-layouts/references/metadata-examples.md`) places all three `show*`
elements after the final `</layoutSections>`, and both artefacts match it exactly — a
positional reading would reject the metadata for matching the only ordering the cited
skill documents, which makes the plan's wording the defect rather than the artefacts.
Separately, "default set on" is **not** established: the skill documents this element as
controlling whether the checkbox is *shown*, not whether it is pre-checked, and no
pre-checking element exists in the artefacts or in the skill's inventory.
`deploy-order.md` records the same gap under "Elements this step could NOT ground".

**Half 2 — A13.** Not file-checkable at M1-S02 time. No `ValidationRule` metadata exists
anywhere under `artefacts/`, and A13's other step `M3-S01` (type `validation`) is still
`pending`. Carry forward: `Severity__c` is on the Support layout only, so a Case
validation rule in M3-S01 that attaches its error to `Severity__c` would fail A13 on the
Billing layout.
