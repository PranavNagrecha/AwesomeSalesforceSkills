# apex-builder — M4-S05 third test-only repair · run `2026-09-12T18-05-00Z`

Third **section 4 test-only repair** of a documented step, run inline by `agents/build-step-runner`
under the same three clauses as every prior run of this step: write only under `artefacts/M4-S05/`
(and this step's own `envelopes/`), return the contract envelope, deploy nothing and invoke nothing.
The operator reset the step `built → failed → pending → running` after `reports/MOCK-DEPLOY-M5.md`
run 6 found the § 9 repair incomplete on the two milestone-dependent methods. This is a repair on

## 1. Summary

Run 6's probe (`reports/MOCK-DEPLOY-M5.md`, `--tests CaseMilestoneServiceTest`, after § 9) found
that the § 9 seeding repair worked: the persona now creates and updates the `Case` (2 of 4 methods
pass — `staysAtOneQueryAndOneDmlFor200Cases` and `ignoresCasesWhoseStatusDidNotChange`, neither of
which depends on a real milestone row). The two milestone-dependent methods
(`triggerWritesCompletionDateOnAnOpenMilestone`, `skipsAMilestoneThatIsAlreadyCompleted`) still
fail — **F-61**: `requireActiveProcess()`'s `WHERE IsActive = true LIMIT 1` query carried no name
filter at all, and the target org has a pre-existing active `SlaProcess` (no `First Response`
milestone) that `LIMIT 1` returned instead of the deployed `First_Response_Standard`.
`deploy-order.md` § 4 flagged this exact gap as an open item before this step was ever run against
an org.

**The fix:** `requireActiveProcess()` now filters `Name IN ('First_Response_Standard',
'First Response Standard')` — Standard because `artefacts/M4-S02/entitlementProcesses/` ships both
Premier and Standard and `decisions.md` D-M1S01-04 records that `Account.Support_Tier__c` carries
no field default (so this fixture's synthetic Account is not entitled to assert a Premier
contract), and both spellings because neither `skills/apex/entitlement-apex-hooks` nor
`skills/admin/entitlements-and-milestones` states whether `SlaProcess.Name` preserves the metadata
`<name>` attribute literally (`First_Response_Standard`) or stores a space-separated label form
(`First Response Standard`) — UNVERIFIED, so the query does not guess. `LIMIT 1` is dropped and
`Assert.areEqual(1, processes.size(), ...)` replaces the old `isEmpty()` check, so the method now
fails loudly on zero matches **and** on more than one, naming the process and the count found.

**Nothing else changed.** The three other `@IsTest` methods, `entitlementFor`, `caseInsideProcess`,
`caseOverrides`, `mintAgent()`, `CaseMilestoneService.cls`, `CaseMilestoneTrigger.trigger`,
`TestDataFactory.cls` and `TestUserFactory.cls` are byte-for-byte unchanged from § 9. F-61 is
entirely inside `requireActiveProcess()`.

**Confidence MEDIUM**, for the same structural reason as every prior run of this step: no
`target_org_alias` on this design-only build, so no offline Apex compiler exists to confirm the fix
compiles or that the org actually stores `SlaProcess.Name` in one of the two queried spellings
(`agents/apex-builder/GATES.md` Gate D) — the remedy is confirmed by the operator's run 7, not by
anything in this run.

## 8. Process Observations

**Healthy.** The § 9 seeding fix held under real org execution — 2 of 4 methods passed outright,
and the 2 that failed did so on a milestone-lookup assertion, not on any FLS/DML error. The repair
loop is converging: each run's failure is a strictly different defect class than the one before it
(F-59 wrong context, F-60 wrong seeding scope, F-61 wrong row selection), not a recurrence of an
earlier one.

**Concerning.** `deploy-order.md` § 4 named this exact gap — "`LIMIT 1` over *any* active process,
not necessarily `First_Response_Premier` or `First_Response_Standard`" — as an open item at the
step's very first build, before any org ever ran this test. It took three org-executed runs (F-59,
F-60, F-61) to reach the one open item that was documented from the start, because § 9's org
validation was the first run to actually execute a passing-shaped test far enough to reach it. A
documented-but-unenforced open item is easy to lose track of across repairs aimed at other
defects in the same method's neighborhood.

**Ambiguous.** Whether the target org's `SlaProcess.Name` field stores
`First_Response_Standard` or `First Response Standard` is still unresolved by this repair — the
`IN` clause with both spellings sidesteps the question rather than answering it. Whichever
spelling actually matched will only be visible in run 7's result, and neither this build's cited
skills nor its corpus states which one applies.
