## 2. The fix, and the choice between the two skill-prescribed options

`skills/apex/apex-security-patterns`'s access-mode table names this exact shape — platform-utility
code on a 67.0+ class that must see/write regardless of the running user gets explicit
`WITH SYSTEM_MODE` / `AccessLevel.SYSTEM_MODE` plus a `// reason:` comment, distinct from
`WITH USER_MODE` ("code both queries and updates data on behalf of a user"). Completing a milestone
is the former: the entitlement engine's own completion signal, not a field the Tier 1 agent edits
directly — the agent changes `Case.Status`; the platform decides what that means for
`CaseMilestone`. `skills/apex/apex-stripinaccessible-and-fls-enforcement` reinforces the boundary
from the other side: its internal-trusted-context-data framing does not treat platform-owned,
non-user-supplied writes like this one as needing a strip pass in the first place.

**Granting the Tier 1 persona Edit on `CaseMilestone` instead was considered and rejected.** It
would repeat, one object over, the exact anti-pattern `skills/apex/test-class-standards` Gotcha 15
already named in this build's own test fixtures — widening a persona to access nobody's requirement
asks it to have. No skill this step cites (`apex/entitlement-apex-hooks`,
`admin/entitlements-and-milestones`) names the case-working agent as the intended writer of
`CaseMilestone`; both frame it as platform-administered state with one supported write
(`CompletionDate`), which is exactly what the fix now performs in system mode rather than as the
agent.

**A cross-skill tension, resolved by the more precise, docs-grounded reading.**
`apex-stripinaccessible-and-fls-enforcement`'s own "Before Starting" line — a trigger body runs in
system mode "at every API version," and the 67.0 default-user-mode change "does not reach it" — is
imprecise here: `CaseMilestoneService.completeMilestones` is not code inside the literal
`trigger { }` block, it is a method on a separate `with sharing` class governed by its own
`apiVersion`. `apex-security-patterns` (quoting the Apex Developer Guide directly in its
`references/well-architected.md`) states the finer rule that actually governs: trigger-**body**
database operations run in user mode at 67.0+ unless system mode is explicitly named, and that
default reaches called classes, not only the literal trigger block.
`apex/entitlement-apex-hooks`'s own reference example predicts this exact failure by name: "A
service-agent user who cannot see a `CaseMilestone` row will not complete it through this trigger,
and `Database.update(..., false)` will hand you that row's error rather than throwing." Per
`standards/source-hierarchy.md`, the docs-grounded skill governs. The looser line in
`apex-stripinaccessible-and-fls-enforcement` is flagged as a skill-quality signal in
`deploy-order.md` § 11, not corrected here.
