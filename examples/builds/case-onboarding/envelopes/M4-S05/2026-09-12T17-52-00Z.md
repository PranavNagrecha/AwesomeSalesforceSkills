## 1. Summary

Run 5's probe (`reports/MOCK-DEPLOY-M5.md`, `--tests CaseMilestoneServiceTest`) found finding
**F-60**: the § 8 repair wrapped every method's fixture inserts *and* its action under test in one
`System.runAs(agent)` block. `Case_Agent_Core` grants Create on `Case` but field permissions on
only `Severity__c` — not `Subject`, `Origin`, `AccountId`, `Priority` or `EntitlementId` — so the
fixture `Case` insert itself now failed FLS as the persona, the same error class § 8 was written to
fix, moved from the deploying user onto the fixture.

**The fix, per `skills/apex/test-class-standards/references/gotchas.md` Gotcha 15 ("Seed In System
Mode, Act As The Persona"):** every fixture insert this class performs — the `Account`, the
`Entitlement`, and every `Case` row, including the ones carrying `EntitlementId` — now runs through
`TestDataFactory.insertAsSystem(...)` outside `System.runAs(agent)`. Only the action under test —
the `Status` change that fires `CaseMilestoneTrigger` in
`triggerWritesCompletionDateOnAnOpenMilestone`, and the `CaseMilestoneService.completeMilestones(...)`
calls that stand in for it in the other three methods — still runs inside `System.runAs(agent)`.
`TestDataFactory.cls` is refreshed to the current template (commit `be09a7bff`), which added
`insertAsSystem(List<SObject>)` since the § 8 copy (commit `5edcb3281`). No assertion, message
string, or `Test.startTest`/`Test.stopTest` boundary was added, removed or changed.
`CaseMilestoneService.cls`, `CaseMilestoneTrigger.trigger` and `TestUserFactory.cls` are unchanged,
byte for byte, since § 8.

**Confidence MEDIUM**, for the same structural reason as every prior run of this step: no
`target_org_alias` on this design-only build, so no offline Apex compiler exists to confirm the
fix compiles (`agents/apex-builder/GATES.md` Gate D) — the remedy is confirmed by the operator's
run 6, not by anything in this run.

## 3. What changed in `CaseMilestoneServiceTest.cls`, method by method

- **`entitlementFor`** — the `Account` insert and the `Entitlement` insert both move from a plain
  ambient `insert` to `TestDataFactory.insertAsSystem(...)`. This states in code what § 8 already
  documented in prose: the persona holds Read only on both objects, never Create.
- **`caseInsideProcess`** — loses its `User agent` parameter. The one fixture `Case` insert this
  helper performs (the insert § 8 wrapped in `System.runAs(agent)`) is now
  `TestDataFactory.insertAsSystem(cases)`, seeded with no persona context at all; the two callers
  (`triggerWritesCompletionDateOnAnOpenMilestone`, `skipsAMilestoneThatIsAlreadyCompleted`) call it
  with one argument now and still mint and use `agent` for the action that follows.
- **`staysAtOneQueryAndOneDmlFor200Cases`** — the 200-row `insert cases;` line moves out of
  `System.runAs(agent)` to `TestDataFactory.insertAsSystem(cases)`, called before the block is
  entered. The `oldCases`/`newCases` map-building loop and the `completeMilestones(...)` call stay
  inside `System.runAs(agent)`, unchanged.
- **`ignoresCasesWhoseStatusDidNotChange`** — its `Account` insert (already outside any `runAs`
  block) switches from a plain `insert` to `TestDataFactory.insertAsSystem(...)` for consistency
  with the other three methods, not because it was failing; its `Case` insert moves out of
  `System.runAs(agent)` the same way the bulk method's does.
- **Unchanged in every method:** every `Assert.*` call, every `Test.startTest`/`Test.stopTest`
  boundary, the `CaseMilestone` queries and the real `update responded;` in
  `triggerWritesCompletionDateOnAnOpenMilestone`, and every
  `CaseMilestoneService.completeMilestones(...)` call — these are the actions under test, and they
  are the only DML or query a real Tier 1 agent performs, so they are the only code that still runs
  inside `System.runAs(agent)`.
- The class-level doc comment gained a second repair paragraph, mirroring § 8's, naming F-60 and
  Gotcha 15. No possessive apostrophe was introduced into any comment this repair touched or added
  — § 8 (`AB-M4S05-14`) recorded that a stray apostrophe in a comment defeats
  `check_test_class_standards.py`'s `strip_literals` quote-pairing, so every new comment in this
  repair was written and then re-checked for that shape before the checker ran.

Full text: `artefacts/M4-S05/classes/CaseMilestoneServiceTest.cls`,

## 8. Process Observations

**Healthy.** Both declared and requested checkers run clean under `--strict` on the first attempt
this time — the `strip_literals` apostrophe hazard § 8 hit twice did not recur, because this
repair's new comments were written apostrophe-free from the start rather than discovered the hard
way.

**Concerning.** This is the second time in one session that a repair aimed at "run the test as the
permissioned persona" (§ 8, F-59) itself needed a second repair (§ 9, F-60) because the first pass
conflated "code the persona's own path writes" with "fields a fixture needs populated to be
meaningful." That the library had no named gotcha for this distinction until this build hit it
(Gotcha 15 was written *from* this finding, per its own "Where this came from" note) suggests the
distinction is genuinely non-obvious, not just a one-off oversight in this step.

**Ambiguous.** Whether `Case_Agent_Core` + `Case_Tier1` grant sufficient FLS for every field this
class's fixtures populate is now moot for the fixture path (system mode ignores FLS by
definition), but it remains open for the *action* under test: whether the persona can actually
write `CaseMilestone.CompletionDate` indirectly via the trigger, and whether the parallel `M2-S02`
repair (adding standard-field permissions) changes anything this test exercises, is unverified in
a design-only build and unaffected by this repair either way.
