## Process observations

**Healthy.** The loop closed on itself — a defect a real dry-run found became a skill rule and a
checker rule, and the rebuild was gated by that checker rather than by a human re-reading a deploy
log. And `set-status running` enforced its gate check exactly as documented.

**Concerning.**

1. **Contract drift, code vs standard.** `build_plan.py` allows `documented -> running` and its
   comment attributes the transition to "Section 4", but `standards/build-orchestration.md` line 211
   names only `failed -> pending` and `running -> running` as recovery transitions. The code cites a
   standard that does not say what it says.
2. **Contract drift, playbook vs code.** `agents/build-step-runner/AGENT.md` Step 2 therefore has no
   procedure for the rebuild the CLI permits — it carves out `blocked` and `failed` and explicitly
   denies one to `documented`. A runner following its playbook literally would have refused this run.
3. **Milestone consistency.** The step re-entered `built`, discarding the `tested` and `documented`
   records rebuild #1 earned, while milestone **M1 is already `accepted`**. The acceptance report
   behind that gate describes artefacts that have since changed.

**Ambiguous.** `steps[M1-S01].inputs.business_processes` still reads `["Support Process", "Billing
Process"]` while `outputs[]` and the artefacts read stem form. F-11 calls this a v6 planner decision;
nothing in this run may change it, so it is recorded in `deploy-order.md` and left standing.

**Suggested follow-ups.** `step-tester` (the seven declared tests are its to run), then
`build-doc-keeper` (the workbook and traceability rows carry the old member names), then
`milestone-verifier` (M1's acceptance report predates these artefacts). This agent invoked none of
them.
