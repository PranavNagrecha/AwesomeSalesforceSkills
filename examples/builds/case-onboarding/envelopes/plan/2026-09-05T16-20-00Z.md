## 5. Decisions

### D1 — Stamp Case.EntitlementId, Case.BusinessHoursId and the Priority default in one before-save record-triggered Flow rather than in Apex or an after-save Flow.

- Tree: `standards/decision-trees/automation-selection.md` branch **Q2**
```text
Q2. Does the logic run in under ~10s and touch only fields on the record itself?
    ├── Yes  → Before-save record-triggered Flow
    └── No   → Q3
```
- Rationale: All three writes land on the triggering Case; the Account and Entitlement reads are lookups, not DML. Q1's record-change branch routes to Q2 and Q2's 'Yes' leaf is the answer.
- Rejected: Apex before-insert trigger, After-save record-triggered Flow, three separate flows, one per field
- Consequences: No Apex means no coverage gate and no deploy-time test dependency, but also no custom exception handling: a Case whose Account has no entitlement must fall through to a documented default rather than throw (Q48).
- `adr_required`: `false` · closes answers Q16, Q40, Q48 · steps M4-S03

### D2 — The stamping flow is before-save, not after-save: the Account and Entitlement lookups are read-only Get Records, which a before-save flow supports.

- Tree: `standards/decision-trees/flow-pattern-selector.md` branch **Q3**
```text
Q3. Do you need any DML, an Action/callout, or an email — anything beyond
    writing fields on the triggering record?
    ├── No   → Before-Save record-triggered flow. Its element set is
                Assignment, Decision, Get Records, Loop — so a read-only
                cross-object lookup is fine here; a write is not.
```
- Rationale: Q1 'record INSERT or UPDATE' → Q2 'only set fields on the SAME record' → Q3 'no DML, no action, no email' → before-save. The branch text settles the one thing that looked like an obstacle: the cross-object read is allowed.
- Rejected: After-save record-triggered flow, After-save with a scheduled path
- Consequences: The customer acknowledgement (an email) cannot live in this flow; it stays in the auto-response rule (M3-S04), which is what Q63 asked for anyway.
- `adr_required`: `false` · closes answers Q16, Q48, Q63 · steps M4-S03

### D3 — Case ownership at creation is set by Case Assignment Rules, and the assignment rule is the sole authoritative OwnerId writer at create time.

- Tree: **none covers this choice** — `adr_required: true`
- Rationale: No decision tree covers this choice. automation-selection.md was checked: Q1's record-change branch leads to Q2, whose 'Yes' leaf is a before-save Flow, and the tree carries no leaf for the Lead/Case assignment-rule engine — only a Related-skills pointer that says 'Lead/Case ownership on create is a rule engine, not a Flow'. flow-pattern-selector.md was checked and has no rule-engine branch at Q1. The choice is resolved by skills/admin/assignment-rules/references/routing-selector.md row 1 ('Route a new Lead or Case to a user or queue from field values → Assignment rule'), which is a skill reference, not a tree. Recording it as ADR-worthy rather than pretending a branch produced it.
- Rejected: Before-save record-triggered Flow setting OwnerId, Apex trigger with round-robin counter, Omni-Channel alone with no queue-landing rule
- Consequences: Two by-design post-save OwnerId writers remain (Omni-Channel push in M3-S05 and the escalation rule in M4-S04). Q27 already flagged this; owner-writer-map.md in M3-S04 is the artefact that has to reconcile all three.
- `adr_required`: `true` · closes answers Q24, Q25, Q26, Q27 · steps M3-S04

### D5 — Case org-wide default stays Private and Tier 2 reaches Support cases through a criteria-based sharing rule on record type; nothing extends Billing cases to Tier 1.

- Tree: `standards/decision-trees/sharing-selection.md` branch **Q3**
```text
Q3. Can the access be described by "anyone who matches criteria X should see records matching criteria Y"?
    ├── Yes, criteria are on the record itself          → Criteria-Based Sharing Rule
```
- Rationale: Q1 'Private → Q2'; the three teams are peers, not a hierarchy, so Q2's 'No' branch leads to Q3; the access is exactly 'the Tier 2 group should see cases whose RecordType is Support', and RecordTypeId is on the record itself.
- Rejected: Public Read-Only OWD, Role-hierarchy grant, Case Teams, Manual sharing, Apex managed sharing
- Consequences: Deferred Q13 asked whether the Billing restriction is record-level or field-level. The plan takes the record-level (more restrictive) reading as assumption A1. If the answer turns out to be field-level masking, M2-S05 is re-planned, not patched.
- `adr_required`: `false` · closes answers Q13, Q80 · steps M2-S05

### D6 — The website form posts to native Web-to-Case; no middleware, no Bulk API and no custom REST endpoint is introduced.

- Tree: `standards/decision-trees/integration-pattern-selection.md` branch **Q5**
```text
Q5. How much volume?
    ├── < 1k rows/day                           → REST API (POST /services/data/vXX.X/sobjects)
    ├── 1k–1M rows/day                          → REST Composite (collections endpoint, up to 200/request)
    └── > 1M rows/day OR bulk upsert/delete     → Bulk API 2.0 (async ingest)
```
- Rationale: Direction 2 (external writes into Salesforce) Q5 places 60 web submissions plus 400 emails per day in the lowest band, so Bulk API 2.0 and an iPaaS are both ruled out by volume. The tree's leaf for that band names the REST API and has no leaf for native Web-to-Case or Email-to-Case at all — so the tree settles the negative half of this decision and not the positive half, which is why it is flagged ADR-worthy.
- Rejected: Bulk API 2.0, Middleware / iPaaS, Custom @RestResource endpoint
- Consequences: Q66 left open whether the form posts directly or through middleware. If middleware turns out to sit in front, the Origin stamping in M3-S03 and the assignment criteria in M3-S04 both change. Assumption A26 is not recorded because Q66 is answered — the answer itself says 'confirm', so the confirmation is a manual test on M3-S03.
- `adr_required`: `true` · closes answers Q15, Q66 · steps M3-S03

### D7 — The 8-business-hour Tier 2 handoff is a Case Escalation Rule, not a scheduled Flow or a time-based Apex job.

- Tree: **none covers this choice** — `adr_required: true`
- Rationale: No decision tree covers Service Cloud's escalation engine. automation-selection.md Q10 ('Scheduled job. Does it process > 50k records or run > 5 minutes?') was checked and routes between Batch Apex, chained Queueable and Schedule-triggered Flow — all three of which would re-implement an engine the platform already runs on business-hours arithmetic. async-selection.md was checked and is entered only once work has been decided to move off the transaction. Resolved by skills/admin/assignment-rules/references/routing-selector.md ('Re-route or notify when a Case is unresolved past a time threshold → Escalation rule (Case only)') plus skills/admin/escalation-rules.
- Rejected: Schedule-triggered Flow polling open Cases, After-save Flow with a scheduled path, Batch Apex
- Consequences: The escalation engine batches, so the 480-minute threshold is not a to-the-second promise (Q46 asked for headroom to be agreed). The rule also writes OwnerId, which is the third owner writer D3 has to reconcile.
- `adr_required`: `true` · closes answers Q42, Q43, Q45, Q46, Q47 · steps M4-S04

### D8 — Nothing in this build runs asynchronously: no @future, no Queueable, no Batch, no Schedulable and no Platform Event.

- Tree: `standards/decision-trees/async-selection.md` branch **Q1**
```text
Q1. How many records / how long?
    ├── < 2,000 records, < 60s          → Q2
    ├── 2k – 50k, < 5 min                → Q5 (Queueable)
    ├── > 50k OR > 5 min                 → Q8 (Batch Apex)
    └── Truly massive, one-off ETL       → Bulk API 2.0 (async SOQL / external job)
```
- Rationale: The worst case anyone described is the daily email peak of ~400 cases (Q15), and those arrive as individual API inserts, never as one 2,000-record transaction. Q1's first band applies and the tree never reaches an async tier.
- Rejected: Queueable entitlement stamping, Batch Apex nightly SLA sweep, Platform Event fan-out to Tier 2
- Consequences: Every automation in the plan runs inside the creating transaction, so the before-save flow in M4-S03 is on the critical path of every intake. If volume grows past the Q1 first band, this decision is the one to revisit.
- `adr_required`: `false` · closes answers Q15, Q76 · steps M4-S03

### D9 — Case is treated as an ordinary object: no skinny table, no custom index request and no archival design in this phase.

- Tree: `standards/decision-trees/performance-tuning.md` branch **Q10**
```text
Q10. What stage of LDV are you in?
    ├── Designing a new high-volume object           → architect/large-data-volume-architecture (skinny + indexes from day one)
```
- Rationale: The tree was entered because the requirement names a volume (Q15: ~480 cases/day). Q1's symptom router has no branch for a greenfield design with no reported symptom, so Q10's design-stage branch is the only reachable entry. ~480/day is roughly 175k Cases a year, well below the thresholds that branch exists for, so the answer is 'not this'.
- Rejected: Skinny table on Case from day one, Custom index request on Origin, Big Object archival of closed cases
- Consequences: The escalation monitoring report (M5-S01) and the queue list views (M5-S01) are unindexed selective queries today. Q76 already asked which acceptance criteria depend on volume; if the report degrades, this decision is where the revisit starts.
- `adr_required`: `false` · closes answers Q15, Q76 · steps M5-S01

## 9. Process observations

- **healthy** (info, checker-coverage) — Every one of the 20 steps could name a real skill-local checker: 26 distinct check_*.py files resolved on disk across the plan, so no step had to fall back to xml-and-manifest alone.
- **healthy** (info, milestone-decomposition) — The five milestones fell out of the configuration-workbook section order without forcing: data model, access, validation-and-routing, SLA, then UI-proof-docs, with every depends_on edge pointing backwards.
- **healthy** (info, answer-quality) — The 72 answered clarifications arrived with volume, sharing layer and channel already stated, so no step had to size automation for an unknown record count.
- **concerning** (high, decision-grounding) — Four of nine decisions (D3 assignment rules, D4 Omni-Channel, D6 native Web-to-Case, D7 escalation rules) had to be recorded adr_required because no decision tree carries a leaf for a native Service Cloud rule engine; all three were resolved by a skill reference file instead.
- **concerning** (high, plan-validation) — build_plan.py validate does not check that decisions[].decision_tree resolves on disk: a plan citing standards/decision-trees/THIS-TREE-DOES-NOT-EXIST.md with branch Q99 validated OK with 0 errors, although both AGENT.md Step 4 and build-plan.schema.json state the field is validated to exist.
- **concerning** (medium, answer-completeness) — M3-S05 (Omni-Channel) carries four deferred blocking answers (Q32-Q35) covering capacity release, capacity units, routing model and push timeout - the whole substance of a routing configuration - so the step is buildable only against provisional numbers no skill supplies.
- **concerning** (medium, requirement-coverage) — The requirement asks for Priority to be set 'from what the form or email tells us', but no answer says how an inbound email conveys priority; the plan closes the Web-to-Case half and leaves the email half as a partial fit-gap rather than inventing a subject-line parser.
- **concerning** (low, skill-depth) — Three skills the metadata steps depend on have no references/metadata-examples.md - admin/business-hours-and-holidays, admin/email-templates-and-alerts and admin/case-management-setup - which is the file metadata-builder is contracted to build artefacts from.

- **ambiguous** (low, step-ownership) — M5-S02 (UAT pack plus sandbox proof) is type custom and could equally be owned by story-drafter or by metadata-builder; story-drafter was chosen because its frontmatter already declares all four cited skills.
- **ambiguous** (low, fit-tier) — Three fit-gap rows sit between Configuration and Low-Code - the finance-case restriction, the regional calendar resolution and the priority default - because each is point-and-click plus one small piece of declarative logic.
