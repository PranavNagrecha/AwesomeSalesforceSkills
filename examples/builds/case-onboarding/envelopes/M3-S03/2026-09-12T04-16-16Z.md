prose:

  routing address writes the single org-level `defaultCaseOwner`, so two addresses fight over one
  slot. Ownership is expressed once per channel as `caseOrigin` + an M3-S04 assignment-rule entry.

  per-channel priority value**, and no `CasePriority` value set exists under `artefacts/`.
- **Q20 → assumption A3 — threading.** The Lightning pair is set and the legacy pair is absent,

  is wrong, only this file changes.
- **Q88 vs gotcha 8 — `notifyDefaultCaseOwner`.** Written `true` on gotcha 8's explicit "make the
  fallback loud", on the reading that an unrouted case is a routing *failure* rather than the
  routine queue work Q88 exempts from email. Two UNVERIFIED parts behind that; see § 7.
- **Requirement / knowledge out of scope.** `enableSuggestedSolutions` and
  `enableSuggestedArticlesApplication` are both explicitly `false` rather than omitted, because the

## 7. Deploy-order note — reproduced in outline

Full text: `artefacts/M3-S03/deploy-order.md`. The load-bearing parts:

**Prerequisites, all resolving by name at deploy time.** `StandardValueSet:CaseOrigin` (M1-S01) for
all three `caseOrigin` values → `CustomObject:Case` record types and processes (M1-S01) → queue
`Tier_1_General` (M2-S04) → **this file**. Queue `Billing` is *not* a prerequisite of this file; it
becomes one for M3-S04.

**The hazard this file creates.** It turns all three channels on. Deployed before M3-S04, live
traffic arrives with no routing and no acknowledgement — an auto-response fires only when an
assignment rule fires. The safe sequence deploys M3-S04 **before** this file, and the real switch is
the human step after it: pointing the mail-server forwarding at the Salesforce-generated
`emailServicesAddress` and publishing the web form. And it is one-way: once Email-to-Case is
enabled it cannot be disabled.

**Ungrounded and open — five items.** (1) `CaseSettings` child ordering is UNVERIFIED; the order here
follows the guide's sample as reproduced by the two skills, not the alphabetical shape a retrieve
returns. (2) `newEntityRecordType` was **not** written although gotcha 9 instructs it, because no
cited file shows whether the value is `Support` or `Case.Support` — so email and web cases land on
the handling context's default record type and nothing in the build stamps one. (3) No `CasePriority`
value set and no per-channel priority answer. (4) `notifyDefaultCaseOwner` `true` is either inert
(the queue has no `<email>`) or contrary to Q88, and the guide does not say which. (5) The declared
decision tree has no branch for a native platform intake endpoint, so the direct-post path was
grounded in the skill rather than routed.
