## 10. Process Observations

**Healthy**
- Both directions of the manifest/file check pass across the whole build tree: 56 members all
  resolve, all 62 deployable files are covered. (`artefacts/`)
- The `CompactLayout` member form that manifest-mode validation rejected at M1 (F-13, bare
  `Case_Intake`) is the object-qualified `Case.Case_Intake` in M1-S01's rebuilt step manifest, so the
  union inherits the fix. The stale bare form still sits in `reports/MILESTONE-M1-package.xml`,
  which predates the rebuild. (`artefacts/M1-S01/package.xml`)

**Concerning**
- This manifest is the first in the build to carry the Apex, so the Apex members have never been
  validated through a merged manifest — G4's F-43 note says so. Source mode compiled the classes;
  manifest mode reads a different document, and the one time it ran in this build it found a defect
  source mode had missed. (`reports/MOCK-DEPLOY-M4.md`)
- Six org prerequisites now travel with this manifest and not one is a metadata file any step could
  ship. A release owner reading only `package.xml` would see none of them.
  (`artefacts/M5-S05/deploy-order.md` § 5.2)
- `settings/Entitlement.settings-meta.xml` is declared in no step's `outputs[]`, so the one switch
  three of M4's five steps depend on cannot appear here even though `Settings` already has three
  members. G4 decision 2 accepted this as a Setup prerequisite. (`plan.json steps[].outputs`)

**Ambiguous**
- Two cited sources disagree on whether manifest order decides deploy order inside one request.
  Reported in `deploy-order.md` § 3.2, not resolved.
  (`skills/admin/case-management-setup/references/metadata-examples.md`)
- `artefacts/M5-S04/deploy-order.md` puts `Settings:Case` ahead of the routing rules;
  `artefacts/M3-S03/deploy-order.md` § 3 states the reverse as the safe sequence. This file follows
  M3-S03 and names the divergence rather than re-ordering M5-S04's table.
