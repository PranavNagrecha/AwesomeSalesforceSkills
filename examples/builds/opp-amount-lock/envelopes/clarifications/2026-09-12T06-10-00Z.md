## Process Observations

- **Healthy** — The requirement, though one line, already states enough for `admin/validation-rules`' whole table to apply cleanly: the object (Opportunity), the field (Amount), the trigger condition (Closed Won), and the direction of the guard (can't decrease) are all explicit, so no clarification had to be invented from nothing. A directly-on-point worked example already exists in the corpus (`skills/admin/user-story-writing-for-salesforce/references/metadata-examples.md`, story `US-OPP-014 — Block Closed Won Opportunities With No Amount`, with a ready `<validationRules>` XML block using `ISPICKVAL(StageName, "Closed Won")`), which is strong independent confirmation that this exact pattern is well-trodden in the library.
- **Concerning** — `standards/build-orchestration.md` § 3.1's own worked example for this exact requirement ("add a validation rule so Opportunity Amount can't go down after Closed Won") cites `admin/formula-fields-and-rollups` as the second skill (S=2). That skill id does not resolve: `skills/admin/formula-fields-and-rollups/` does not exist on disk. The real skill is `skills/admin/formula-fields/` (no "-and-rollups", and it never surfaced as a top result for any search phrase this run tried). Per `agents/requirements-clarifier/AGENT.md`'s own rule ("Never invents a skill path — every `source_skill` id is confirmed to resolve to a real `skills/<domain>/<slug>/SKILL.md` on disk"), this run did not cite the fictional id, but the standards doc's own worked example — the one place a new operator of this agent is most likely to read before running it — names a path that fails that exact check. Worth fixing at the source (`standards/build-orchestration.md` § 3.1) so the next run doesn't anchor on it.
- **Ambiguous** — Whether `admin/opportunity-management` and `admin/sales-process-mapping` should have been kept is a genuine judgment call this run made narrowly. `agents/requirements-clarifier/AGENT.md` Step 3 reads mechanically ("For every skill in the top results of any search... keep every skill that has [a table]. Drop the rest [meaning: those without a table]") — a literal reading would keep both, since they surfaced in a top-3 list and both carry tables, which would push S from 1 to 3 (still `ask`-tier, since the bound is S≤3) but would also inject roughly 14 additional rows — none of which trace to anything this build changes (forecast buckets, business-process/record-type counts, splits, team access, `IsPrivate`, field-history tracking) — into a one-line ask's clarification round. This run applied `agents/_shared/AGENT_CONTRACT.md`'s citation-quality bar ("a citation should answer 'the agent's output would be wrong without this skill in this scenario'") instead, and excluded both. A stricter operator could reasonably require the literal Step 3 reading; if so, the counts would still land at `ask` (S=3) but the question count would roughly triple. Flagging this as a spec gap: Step 3 does not currently say whether a search that returns a table-bearing skill for reasons of shared vocabulary (here: the word "stage" and "Closed Won") rather than shared capability should be filtered by the citation-quality bar, and both readings are defensible from the text as written.
  - Similarly ambiguous: `default_source: none` on 6 of 7 blocking questions (Q1, Q2, Q3, Q5, Q6, Q7) — each because no invented Salesforce fact would be honest, but it means most of what reaches the human at G1 has no one-click accept path.
