# Configuration Workbook — Section 3

Per-step slice, written by the build doc keeper after `M2-S01` was tested. This build is
`build_mode: design-only`, so per `standards/build-orchestration.md` § 4 every `access` step routes
to `metadata-builder`; `recommended_agent` below names the step's owning agent (`metadata-builder`),
not the Section 3 default (`permission-set-architect`), per `agents/build-doc-keeper/AGENT.md`
Step 4.

Row schema and section list: `skills/admin/configuration-workbook-authoring` SKILL.md Concepts 1–3.
`REQ-011` and `REQ-012` are minted in this run, continuing from `REQ-001`–`REQ-010`
(`M1-S01`, `workbook/01-objects-and-fields.md`; `M1-S02`, `workbook/02-page-layouts-and-lightning-pages.md`).
Both requirements serve the escape-hatch half of `requirement.md` items 2–3 (the discount-cap and
product-count rules must be bypassable by exactly the sales-ops admin, per clarification Q13) — a
`CustomPermission` and the one `PermissionSet` that grants it, per `agents/build-doc-keeper/AGENT.md`
Step 4's routing of an `access` step's artefacts to this section, regardless of the general skill's
per-artefact-type breakdown (Section 5's "bypass reference" note describes how a validation-rule row
*cites* a custom permission, not where the permission's own row lands). `owner` on both rows is the
Sales Operations lead — Q13's `owner_role` answer, and the same name the artefact's own
`<description>` element records ("Owner: Sales Operations lead") — rather than the generic
"Sales-ops admin (role)" filler `workbook/01-objects-and-fields.md` and
`workbook/02-page-layouts-and-lightning-pages.md` used where no more specific owner was on file.
Multi-value cells use `;`, the same convention the other per-step workbook slices use, because
`check_workbook.py` splits a row on every bare `|` with no escape handling.

**One thing a reader should know about these two rows.** Nothing in this build assigns
`Sales_Ops_Validation_Bypass` to anyone — `PermissionSetAssignment` is record data, not metadata —
and no cited checker can see the escape hatch actually wired to a validation rule at this step's own
scope: `M2-S03` and `M2-S04`, the two rules this permission is meant to bypass, do not exist yet.
Both gaps are named in full in `decisions.md` **O-M2S01-01** and in the builder's own medium-severity
Process Observation (a green deploy of this step alone proves nothing about the escape hatch; only a
run carrying `M2-S03` alongside it is evidence).

**Two more rows were added after `M2-S02` (`CWB-PERM-003`–`004`).** `REQ-013` and `REQ-014` are
minted in this run, continuing from `REQ-001`–`REQ-012`. Both close the selectability gap
`decisions.md` **O-M1S01-03** named at the M1 gate: `CWB-PERM-003` is the permission set that makes
the two `M1-S01` record types visible to the Sales User persona; `CWB-PERM-004` is the profile
overlay that assigns each record type's `M1-S02` layout and leaves the org's existing default
record type untouched. **Both rows were repaired once, after the first mock-deploy dry run.**
Field-level security for `Discount__c`/`Approval_Status__c` was granted by neither row as first
built (`decisions.md` **D-M2S02-01**, **O-M2S02-01**, HIGH) — the repair closed that gap by adding
two `fieldPermissions` blocks to `CWB-PERM-003`, by requester decision (`decisions.md`
**D-M2S02-03**); separately, `CWB-PERM-004`'s `recordTypeVisibilities` block was dropped entirely
after the org rejected it (N3-F-05: a profile's stated record-type block must name a default or mark
every listed type invisible, and neither option was safe here) — record-type visibility is now
carried solely by `CWB-PERM-003` (`decisions.md` **D-M2S02-02**). `reports/MOCK-DEPLOY-M2.md` run 3
(2026-09-19T15:26:20Z, `checkOnly`) is the org evidence both repairs deploy clean.
