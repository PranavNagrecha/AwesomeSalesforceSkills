## 7. Deploy order (reproduced)

Full note: `artefacts/M2-S01/deploy-order.md`.

1. `CustomPermission:Bypass_Opportunity_Sales_Validation` — a permission set naming a custom permission
   that does not yet exist fails the deploy, so the definition ships before the grant.
2. `PermissionSet:Sales_Ops_Validation_Bypass` — the grant. Both are in one `package.xml`, so a single
   manifest deploy satisfies the ordering.

Outside this step: nothing must exist first (the files reference no object, field, record type, tab,
app, class, flow or licence), but this step must deploy **before or with M2-S03 and M2-S04**. A
`$Permission` token naming a permission the org lacks does not fail the deploy — it evaluates to `false`
silently (`custom-permissions` gotcha 4) — so M2-S03 landing first means the discount cap is live with
no escape hatch for anyone, the sales-ops admin included.

Field-level security, stated explicitly: this is a **bypass/function set, not a persona set**. It carries
no `objectPermissions` and therefore no `fieldPermissions`, so `PSVP-FLS-01` does not apply to it. The
sales-ops admin's field access comes from their System Administrator profile (Q19); the rule that a
persona set must list every field its users need — standard fields carry FLS too — governs M2-S02's
work, not this file.
