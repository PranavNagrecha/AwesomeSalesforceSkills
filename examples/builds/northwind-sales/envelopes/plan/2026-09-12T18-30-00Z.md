## Scope

### In (14)

- Two Opportunity sales processes for the Enterprise team - Enterprise (Qualify, Discover, Propose, Negotiate, Closed Won, Closed Lost) and Renewal (Renewal Review, Renewal Proposed, Closed Won, Closed Lost) - each with the probabilities and forecast buckets the requester signed off (requirement.md item 1; Q5, Q6, Q21, Q36).
- Two Opportunity record types (Enterprise, Renewal) bound to those two Sales Processes, plus the eight stage values they need added to the OpportunityStage standard value set (requirement.md item 1; Q8, Q36, Q40).
- Two header fields on Opportunity: Discount__c (Percent) typed by the rep, and Approval_Status__c (restricted picklist Pending/Approved/Rejected) written only by the approval process (requirement.md items 2-4; Q12, Q22).
- One page layout per new record type carrying the platform-required standard fields, Discount__c and Approval_Status__c (requirement.md item 4; Q14, Q20).
- A Path per record type with per-stage key fields and the exit checklist wording the requester dictated (requirement.md item 1; Q2, Q11, Q46, Q48, Q49).
- A validation rule blocking Closed Won above a 20% discount unless the approval is Approved, with a Custom Permission bypass granted by permission set to the sales-ops admin only (requirement.md item 2; Q13, Q15, Q17).
- A validation rule requiring at least one product line before Propose - planned, and BLOCKED on a library coverage gap rather than guessed (requirement.md item 2; Q11, Q42).
- A declarative Approval Process on Opportunity: entry above a 20% discount, approver = the rep's manager through the user hierarchy, record locked while pending with AdminOnly editability, recall allowed, and the four action sets the requester specified (requirement.md item 3; Q27, Q28, Q31, Q32, Q33, Q58, Q59, Q60, Q61).
- Three Classic email templates in a public folder plus the two workflow alerts and four field updates the approval process fires (requirement.md item 3; Q33).
- An Apex service, an @AuraEnabled controller and an @InvocableMethod action that submit exactly one Opportunity into that process, with the test class the requester asked for (requirement.md item 4; Q29, Q30, Q34, Q35).
- A record-page LWC showing the discount and the approval status with a Submit-for-approval button enabled only when the rule requires it, plus its Jest suite (requirement.md item 4; Q22, Q34, Q35, Q51, Q52).
- A Lightning record page carrying the Path and that component, with the org-default record-page assignment (requirement.md item 4; Q50).
- A custom report type, a summary report of open Enterprise pipeline by stage with amount and discount, a pipeline-by-close-month dashboard, and the two folders shared to the Enterprise Managers public group (requirement.md item 5; Q23, Q24, Q25, Q54, Q55, Q56, Q57, Q63).
- A configuration workbook, traceability matrix, acceptance criteria, UAT case pack, build-level package.xml and a go-live runbook covering the 140-deal record-type reassignment, folder sharing, approval process order and the record-page activation (Q8, Q25, Q26).

### Out (10)

- Any change to the SMB generic sales process, its record type, its two list views or its pipeline report - explicitly descoped by Q4 and Q9; the build adds stage values and record types beside it and touches none of its metadata.
- Any sharing change: no org-wide default change, no sharing rule, no role-hierarchy edit. Q4 answered that the separation is process guidance only and Q24 answered that manager visibility already comes from the role hierarchy.
- Opportunity splits, opportunity teams and the Private flag - Q7 answered no to all three.
- Any integration, inbound or outbound - requirement.md item 6, confirmed by Q38 and Q65.
- Any data migration. The 140 open Enterprise deals are reassigned by the sales-ops admin as a post-go-live runbook step, not by a build step - Q8.
- Cleaning up the ~20 open Enterprise deals with no products and the 6 with discounts above 20%: Q16 answered that the rules apply on the next save only and no clean-up is in scope.
- Creating Product2, Pricebook2 or PricebookEntry records. requirement.md states the org already has Sales Cloud Enterprise, Product2 and a Standard Price Book; this build uses the catalogue rather than building it.
- Notifying Finance or Customer Success when a deal closes - Q3 answered that both read the record and the report covers it, with no notification build in scope.
- Subscriptions, scheduled emails and exports of the report or dashboard - Q53 was informational and was left unanswered with no documented default, so nothing is built for it (assumption A30).
- Creating the Enterprise Managers public group membership. Group metadata carries no members (admin/queues-and-public-groups); the group ships empty and the sales-ops admin adds the two managers and the VP in Setup (assumption A32).

## Assumptions

39 rows, each with the steps it constrains. Six carry `risk: high` or are pre-deploy prerequisites that would fail silently:

- **A24** (high) — The OpportunityStage standardValueSet file this build deploys must be the UNION of the org's currently active stage values and the eight new ones. A partial file deactivates every value it omits, which would strip the SMB pipeline of its stages. _Steps: M1-S01, M4-S03, M4-S04._
- **A28** (high) — The report's column codes are provisional Object$Field strings. They are report-type-specific, cannot be verified offline, and must be diffed against a retrieve of a working report on the same report type before deploy. _Steps: M4-S01, M4-S02, M4-S03, M4-S04._
- **A29** (high) — Nobody supplied the VP's username, so the dashboard ships with dashboardType SpecifiedUser and no runningUser element. On deploy the platform fills it with the DEPLOYING user's username, which is wrong; setting it is a mandatory pre-deploy step in the deploy-order note. _Steps: M4-S02, M4-S03, M4-S04._

The remaining 33 are in `plan.json` → `assumptions[]` and rendered in `PLAN.md`. Every row's `because` names the `Qn` it came from or the org fact nobody supplied.

### Concerning

- **high** — One step is blocked on a library gap: no skill documents how a validation rule counts OpportunityLineItem rows, so the requirement's product-before-Propose gate ships as Path guidance text only. Four searches were run and recorded on the step.
- **high** — Three artefacts cannot be finished offline and all three would fail silently rather than loudly: the OpportunityStage value set needs the org's current active values or it mass-deactivates the SMB stages, the report's six column codes are report-type-specific, and the dashboard's runningUser is replaced with the deploying user's when absent.
- **medium** — check_opportunity_management.py reads fixed paths under --manifest-dir with glob rather than rglob, so it is vacuous at build scope and forced four artefact families into one step to stay meaningful. check_approval_design.py and check_approval_process_apex_patterns.py have the mirror problem and need both --manifest-dir and a positional path to work at all.
- **medium** — admin/products-and-pricebooks carries no Questions-to-Ask table and no references/metadata-examples.md, so the one capability the requirement names as central - reps adding products - is the one with the thinnest grounding in the library.
- **medium** — The Opportunity Products related-list API name and the platform's layout-required field set for Opportunity are both absent from the library, so two of M1-S02's artefact details are deferred to a retrieve and to iterated dry runs.
- **low** — M4-S01's only acceptance tests are manual. The step writes one markdown runbook and no checker in the library lints a probe runbook, so check-outputs plus two tickable statements are the whole test surface.

### Ambiguous

- **medium** — The fit_gap verdict enum has no value for 'the platform can do this but the library cannot', which is exactly M2-S04's state. It is recorded as fit with a blocked step and an explicit note, because gap would misreport the platform and partial would misreport the requirement.

Build-planner Step 6 rule 6 says object-level children belong to the object-model step; nothing collides here, but the rule and the checker pull in opposite directions.
