## 8. Process Observations

### Healthy

- **The build's own record was sufficient to write the decision entries from sources.** Every org
  message is quoted verbatim in `reports/MOCK-DEPLOY-M1.md`, each of the three fixes has its own
  `metadata-builder` envelope with a `decision_record` naming the gotcha it rests on, and
  `deploy-order.md` § 6 carries a write-up per round. Nothing in `D-M1S02-07` had to be inferred.
- **The library's previous investment paid off in a different object's build.** The same failure was
  worked end to end on Case in `examples/builds/case-onboarding/decisions.md` **D-M1S02-05**, and the
  remedy that closed it — `gotchas.md` #12 and #13 plus checker rules RL-REQ-01/02 — is exactly what
  let this build's builder read run 1's message correctly on the first try and write `Required`
  rather than `Edit`, pre-empting a fourth round.

### Concerning

- **The checker's layout-required rules are still Case-only, by construction.**
  `CASE_LAYOUT_REQUIRED_ITEMS` is a three-name tuple carrying the comment *"do not extend this to
  another object without a dry run"*, and `RL-REQ-03` is only an ADVISORY name-like-field smoke test
  for every other standard object. The four Opportunity facts this build bought with four
  mock-deploy rounds are not yet encoded where a checker can enforce them, so the next Opportunity
  build in this library will rediscover them the same way unless Cursor task 18 lands. The step's
  declared checker passing clean both before and after the repairs is correct behaviour for a rule
  set that does not cover Opportunity — and is also precisely why no gate in this loop caught it.
- **An instruction in the mock-deploy report named an agent that cannot carry it out.** Run 4's note
  that the `UNVERIFIED` marker "resolves to confirmed at the next doc-keeper pass" assumes the doc
  keeper edits `artefacts/`, which its contract forbids; and the evidence would not support the edit
  anyway (sufficiency, not necessity). Recorded as `O-M1S02-04` rather than silently skipped.
- **Emphasis markup inside an enum cell suppressed a rule.** `**In Build**` fell outside
  `check_rtm.py`'s closed status enum, and the linter waives a coverage gap on a status it does not
  recognise as a build status — so the bold had been hiding a real ERROR since 2026-09-15. Worth
  knowing before the compile run at `M4-S03` assembles these files.
- **23 § 5 checker-coverage WARNs printed on `set-status`, two of them this step's**
  (`admin/opportunity-management` and `admin/products-and-pricebooks` each ship a checker no
  acceptance test on the step or on milestone M1 runs). Unchanged from the tester's run and not a
  defect in the artefacts — but the M1 gate is where a human sees the count, and
  `amend-step --add-checker` is the one-line remedy for the two on this step.

### Ambiguous

- **`check_rtm.py`'s 14 warnings are mostly a convention disagreement, not defects.** Every `source`
  cell in this matrix is multi-valued (`Q20, Q14, Q22, D2`) and every `decision_ref` uses the doc
  keeper's own `D-M<m>S<nn>-<nn>` ids rather than the plan's bare `D<n>`. Changing either would lose
  information, so nothing was changed. Whether the linter or the convention should move belongs to
  whoever owns the RTM skill.
- **The merge question is exactly as open as it was.** Both layouts are still byte-identical after
  all three repairs — they were repaired identically and share one digest — so `O-M1S02-03` stands.
  The repairs are mild evidence *for* merging, since the platform's required set is a property of the
  object rather than of the record type; but nothing the org said differentiates the pair, and this
  pass asserts no answer. A human's call at the M1 gate.
