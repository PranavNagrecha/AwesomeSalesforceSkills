## 4. Decision record

The full nine-row table is in the envelope under `extensions.decision_record`. The four that changed
what got written:

1. **No field on either layout carries `behavior=Required`.** Q11 puts the must-fill enforcement in
   the M2-S03 / M2-S04 validation rules, and layout `Required` binds to that layout only — API,
   Flow and every other layout ignore it (`gotchas.md` #11). Marking a field Required here would
   look like enforcement and enforce nothing.
2. **The platform's layout-required set for Opportunity is not asserted.** Q20's five fields are
   present because the requester asked for them. The platform's own set is a different question:
   `metadata-examples.md` says in bold not to extrapolate the Case set, and `gotchas.md` #13 names
   this build's exact temptation — *"Do not generalise `Status` to `StageName` on Opportunity …
   without a dry run against the target org."* Assumption **A25**; discovery procedure in
   `deploy-order.md` §3 item 2.
3. **Neither file carries a `relatedLists` block.** The Opportunity Products related-list API name
   is in no skill here, and `admin/opportunity-management` §4 marks the related-list names
   `UNVERIFIED` and says related-list `fields` are retrieval aliases that must never be
   hand-authored. Assumption **A26**; retrieve-and-copy instruction in `deploy-order.md` §0.
4. **`Approval_Status__c` is `Readonly`, `Discount__c` is `Edit`.** The approval field is written by
   the M3 process, not by a rep — its own field definition and Q22 both say so — and a field update
   sets it regardless of the layout item's behavior, so `Readonly` costs the approval process
   nothing.

The three Case-only layout switches in the skill's worked example — `showEmailCheckbox`,
`showRunAssignmentRulesCheckbox`, `showKnowledgeComponent` — appear in neither file: the skill
states each is allowed only on specific objects and that deploying one on the wrong object fails.

**Concerning**

- *(medium)* Both layout files are **byte-for-byte identical**, differing only in file name. The
  skill lists an identical layout pair as a merge candidate to surface proactively. Nothing in the
  step's inputs, Q14 or Q20 differentiates them; the second file exists because D2 produced two
  record types. Carried as item 4 of `deploy-order.md` §3 for a human to sign.
- *(medium)* A cited skill supplied nothing writable: `admin/products-and-pricebooks` carries no
  fenced XML anywhere, no Questions-to-Ask table, and no mention of a page layout or a related list.
  It is cited for the product-line half of Q14 — exactly the element this step cannot write.
- *(low)* Both layouts ship incomplete against requirement item 2: with no `relatedLists` block a
  deployed layout shows no Opportunity Products, so a rep cannot add a product line from the page.
  Deliberate (A26), but a reader who takes "the M1 layouts are built" as "reps can add products"
  will be wrong — the same shape as M1-S01's open item O-M1S01-03.

**Ambiguous**

- *(medium)* A25 and the step's second manual acceptance test both name `scripts/mock_deploy.py --dry-run`,
  and **that flag does not exist**. The script's `--help` states it is validation-only, always runs
  `sf project deploy start --dry-run`, and that "there is no flag to disable `--dry-run` and no
  `--deploy` option; that is by design." `deploy-order.md` §3 item 2 carries the runnable form and
  says so explicitly, so the manual tick can be made truthfully — but the plan text is worth
  correcting.
- *(medium)* AGENT.md Step 3's gap rule says it fires "on one condition only: the grep in item 2
