## 4. The field-access decision, in full

`deploy-order.md` § 0 carries the argument. In short:

**Decision — record-type visibility only.** Three grounds:

1. **Q19** names the persona's access source: *"Reps and managers: the standard Sales User profile with
   a Sales Cloud permission set."* That Sales Cloud set is not an artefact of this build and no step
   declares it. `Enterprise_Sales_Record_Types` layers the two new record types on top of it.
2. **The step's `inputs{}` bind no field.** Per AGENT.md Step 4 the planner's explicit binding is the
   highest-priority source, and it names a permission set, a profile, two record types and two layout
   assignments.
3. **`PSVP-FLS-01`'s shape is absent.** That rule fires on a permission set granting `allowCreate` or
   `allowEdit` on an object with no standard-field FLS. This set grants no object permissions at all.
   The checker confirms it: step-scope run exits 0 with `PSVP-FLS-01` silent.

**What the decision leaves open, and it is high-risk.** FLS for `Opportunity.Discount__c` and
`Opportunity.Approval_Status__c` — the two fields M1-S01 created and M1-S02's layouts place — is
granted by no file in this build. Three access files exist across all sixteen steps
(`M2-S01`'s set and this step's two) and none carries a `fieldPermissions` block;
`reports/MILESTONE-M1-REPORT.md` records the same zero and points at "M2-S01 / M2-S02". The step gate's
own note predicts the failure mode: *"the deploying user has no FLS on fields shipped in the same
package."* On deploy day both fields are invisible to every rep **and** to the admin who deployed them,
which reads as a layout bug. The two remedies are in `deploy-order.md` § 0; both are a human's call,
and the second one requires rejecting and re-signing this step's gate.

## 9. Process Observations

**Healthy**

- The plan split this step into two files for the right reason and said so in `inputs.note` before the
  builder opened a skill: a permission set can carry `recordType` + `visible` only, and
  `layoutAssignments` plus the default record type exist solely on `Profile`. The element split the
  skill documents and the split the plan declared agree exactly, so nothing had to be re-derived.
  (`skills/admin/record-types-and-page-layouts/references/metadata-examples.md`.)
- All four cross-references — two layout names, two record-type names — were copied
  character-for-character from M1-S01's and M1-S02's file names rather than retyped. M1-S02's own
  deploy-order note had already flagged a mismatch there as `INVALID_CROSS_REFERENCE_KEY`, and the
  warning did its job one step later.

**Concerning**

- **(high)** FLS for `Opportunity.Discount__c` and `Opportunity.Approval_Status__c` is granted by no
  file in this build — three access files across sixteen steps, zero `fieldPermissions` blocks — while
  `reports/MILESTONE-M1-REPORT.md` records the same zero and points forward at "M2-S01 / M2-S02". This
  step declined to absorb the grant silently (§ 4 above) and recorded it instead. It needs a human
  decision before the M2 gate, not after.
- **(low)** The step's own acceptance-test description for `check_record_type_layouts.py` quotes a
  planning fixture that printed `0 finding(s) detected`; the same command over the same tree now prints
  1. The exit code and the declared `expected: exit 0` are unaffected, and the finding was already
  adjudicated at the M1 gate — but the quoted fixture no longer reproduces, which is a prose drift
  `amend-step --prose-only` exists for. Planner's call, not this agent's.

**Ambiguous**

- **(low)** `PSVP-FLS-02` stands as a WARN on the overlay by design. The checker asserts only that some
  `PermissionSetGroup` exists somewhere in the tree; this build designs none and the access source is a
  pre-existing Sales Cloud permission set outside it. A human should accept the WARN at the gate rather
  than close it by inventing a group.
- **(low)** The Profile member and file stem are written as `Sales User`, with its space, per the
  step's `manifest` acceptance test. No cited file shows a space-carrying profile member, so the form
  follows from the stem-equals-member rule rather than from an example, and Q19's phrase "the standard
  Sales User profile" is the only evidence the org's profile is named exactly that. Marked
  `UNVERIFIED (2026-09-19)` inline in `deploy-order.md` § 3.
