## 7. Deploy order — the short form

Full note at `artefacts/M2-S05/deploy-order.md` (9 sections). The load-bearing parts:

1. **Order inside the step:** either path, then either path, then `Settings:PathAssistant` last —
   "make it visible last, so nobody sees a half-built path" (metadata-examples § 6). All three are in
   one `package.xml`, so a manifest deploy satisfies it by itself.
2. **Outside the step:** everything in **M1-S01** must exist in the target org first, by exact string —
   both record types, both business processes, the `OpportunityStage` values, and `Discount__c` /
   `Approval_Status__c`. `recordTypeName` is not updateable (api_meta.txt L94529), so a wrong one is a
   delete-and-recreate. A mismatched `picklistValueName` is *not* a deploy error — the step just never
   renders (api_meta.txt L94525–94526).
3. **What a green deploy does not prove** — the step's second manual acceptance test, and § 3 of the
   note says it in those words: it proves neither that Path is enabled nor that the component is on the
   record page. **M3-S05** is the step that puts `runtime_sales_pathassistant:pathAssistant` on a page,
   it is `pending`, and it builds the **Enterprise page only**.
4. **Validate-only command for a human** — `scripts/mock_deploy.py` hard-codes `--dry-run` internally;
   there is no flag to turn it off and none for anyone to pass:

   ```bash
   python3 scripts/mock_deploy.py .sfskills/builds/northwind-sales/plan.json \
     --org-alias <your-sandbox-alias> \
     --milestone M1 \
     --step M2-S05 \
     --mode manifest
   ```

   Together with M1, because a `--dry-run` never saved M1's earlier runs and both paths would fail on
   `recordTypeName` against an org that has never received it.
