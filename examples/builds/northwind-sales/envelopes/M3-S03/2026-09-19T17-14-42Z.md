## 1. Summary

Four authored Apex classes plus a verbatim copy of `templates/apex/tests/TestDataFactory.cls`
and its meta XML — ten files, all ten declared in the step's `outputs[]`, all ten written.
`OpportunityApprovalService` holds the submission body, `OpportunityApprovalController`
is the `@AuraEnabled` entry point the M3-S04 LWC will import, `OpportunityApprovalSubmitAction`
holds the single `@InvocableMethod` for Flow, and `OpportunityApprovalServiceTest` covers all
three including three refusal paths. The split is decision D6, not a preference: an LWC can
only import an `@AuraEnabled` method and *"The only annotation that can be used with the
InvocableMethod annotation is Deprecated"* (apexdev L5430).

All three declared `checker` acceptance tests exit 0, and each was proven live against a
deliberately broken scratch copy rather than trusted on a zero-finding line. Two of those
three probes failed on the first attempt and exposed real defects — one in the emitted code,
one in the way a checker reads it. Both are written up in § 8; neither is cosmetic.

## 5. Integration notes

Nothing in this step modifies an existing file. Six things the human has to carry:

1. **API version, and what `mock_deploy.py` will do with it.** The declarative steps in this
   build carry `62.0` in their `package.xml`. `scripts/mock_deploy.py` copies the selected
   steps' trees whole and deploys *"at the highest `<version>` any selected step's
   `package.xml` declares"* (`standards/build-orchestration.md` § 5). This step declares no
   `package.xml`, so it contributes no version to that scan, and an M3 run will validate at
   `62.0` unless `--api-version` overrides it. The per-class `apiVersion` in each
   `.cls-meta.xml` is what governs the Apex, independently of the deploy version, and that is
   the number the security idiom is gated on (`AGENT_CONTRACT.md` § *Apex security idiom by
   API version*). Mixed API versions in one deploy are legal.
2. **The instruction to build at 67.0 was refused, and here is why.** This run was told to
   stamp `67.0` as the earlier scenarios' Apex did. `plan.json` says otherwise in three
   independent places: `steps[M3-S03].inputs.api_version` is `"62.0"`; the step's `note`
   argues the 62.0/67.0 split at length and calls it *"a deliberate split recorded in this
   step's note, not a slip"*; and manual acceptance test 6 **pins** it — it is ticked only if
   the four authored classes carry `62.0` while `TestDataFactory` carries `67.0`. The plan is
   the single shared state (§ 2) and a runner does not overrule it, so 62.0 it is. Raising the
   build's API version stays a plan-level decision, exactly as M1-S02, M2-S05, M3-S01 and
   M3-S02 each recorded. **If 67.0 is genuinely wanted, it is an `amend-step` plus a re-read
   of the service's read idiom, not a runner-side edit** — see § 8, ambiguity 1.
3. **`ApexClass` members belong to M4-S04.** This step ships no manifest, per § 4 borrowed-agent
   condition 2 and § 5's *Apex exception*. M4-S04 `depends_on` this step and must aggregate
   five members: `OpportunityApprovalService`, `OpportunityApprovalController`,
   `OpportunityApprovalSubmitAction`, `OpportunityApprovalServiceTest`, `TestDataFactory`.
4. **Deploy order.** After M1-S01 (`Discount__c`, the `Enterprise` record type, the
   `Enterprise_Sales_Process` stages), after M2-S02 (the `Enterprise_Sales_Record_Types`
   permission set and the `Sales User` profile overlay) and after M3-S02 (the approval process
   itself). The test queries the permission set by name at `@TestSetup` time, so a deploy that
   runs the Apex tests before that permission set exists fails in setup, not in an assertion.
5. **What M3-S04 imports.** `OpportunityApprovalController.submitForApproval(Id)`, returning an
   `OpportunityApprovalService.SubmitOutcome` with four `@AuraEnabled` members —
   `opportunityId`, `success`, `message`, `instanceStatus`. It is **not** `cacheable=true`
   (it mutates) and it does **not** throw `AuraHandledException` on refusal: per Q30 the rep
   sees the reason inline, so a refusal comes back as `success=false` with a `message` rather
   than as an exception the component has to unwrap.
6. **Apex class access is a separate grant.** `skills/apex/invocable-methods` gotcha *"Apex
   Class Access Is A Separate Grant, And Its Absence Looks Like A Flow Bug"* applies to the
   controller and the action alike. Neither `Enterprise_Sales_Record_Types` nor
   `Sales_Ops_Validation_Bypass` carries a `classAccesses` block today. That is an M2-S02
   question, not something this step may write.

## 6. Governor-limit budget

Per invocation, for the single-record path the requirement actually uses (`inputs` says one
record; A23 records very low volume):

| Class | SOQL | DML statements | Rows | CPU |
|---|---|---|---|---|
| `OpportunityApprovalService.submitOne` / `submitBatch` | **1** (one `WHERE Id IN :ids`, whatever the input size) | **1** (`Approval.process`) | 1 per input | negligible — three linear passes over the input list, no nested loops |
| `OpportunityApprovalController.submitForApproval` | 0 of its own | 0 of its own | — | one delegation |
| `OpportunityApprovalSubmitAction.submit` | 0 of its own | 0 of its own | — | two linear passes over the input list |

The shape is flat in input size by construction: the query is built from the whole id list and
`Approval.process(requests, false)` is *"ONE DML statement against the 150 limit"*
(`approval-process-apex-patterns/references/metadata-examples.md`). No chunking loop is
emitted, because A23 records single-record entry and a 12-rep org; the ceiling that would
force one is 10,000 rows per `Approval.process` call, far above anything this build sees.
`check_invocable_methods.py` IM005 is the standing guard that no SOQL or DML drifts into a
loop here, and it is declared as an acceptance test.

`OpportunityApprovalServiceTest`, one `@TestSetup` and six `@IsTest` methods:

| Method | Covers | Asserts |
|---|---|---|

| `invocableReturnsOneResultPerRequestInInputOrder` | `OpportunityApprovalSubmitAction` | two inputs in, two outputs out, output 0 the refusal and output 1 the success — the size-**and**-order rule (apexdev L5456-5458) |
| `unreadableOpportunityIsReportedWithoutASubmission` | the seeded not-readable outcome | `success=false`, non-null `message`, no instance created |

Methods 2 and 7 of the step's `acceptance_tests[]` — the two `manual` lines — are both
satisfied by the file: manual test 7 asks for exactly methods 1 and 2 above.

**Fixture shape**, driven by `apex/test-class-standards` gotchas 13, 14 and 15:
setup-object DML (`User`, `PermissionSetAssignment`) sits inside the self-user `runAs` fence;
`Account` and `Opportunity` are seeded **outside** any persona block through
`TestDataFactory.insertAsSystem` (system mode); only the submission itself runs inside
`System.runAs(persona())`. The persona is a `Sales User` (Q19) holding
`Enterprise_Sales_Record_Types` (M2-S02), with a manager set on `ManagerId` because the
approval process routes to the owner's Manager.

Two fixture details that would have failed silently and are worth naming:
- the seeded opportunities are at stage **`Qualify`**, not the factory default `Prospecting`.
  The `Enterprise_Sales_Process` built by M1-S01 carries Qualify / Discover / Propose /
  Negotiate / Closed Won / Closed Lost, and `Prospecting` is not one of them.
- neither validation rule blocks the seed. `Opportunity_Discount_Requires_Approval` fires only
  at `Closed Won`; `Opportunity_Products_Required_At_Propose` requires `NOT(ISNEW())` and
  `ISCHANGED(StageName)`. Both were read, not assumed.

**Expected coverage** — an estimate, because no compile or test run was possible (§ 9):
service ~90%, controller 100%, action 100%. The one branch expected to stay uncovered is the
`catch (DmlException)` block in `submitBatch` — with `allOrNone=false` the platform returns
per-row errors rather than throwing, so that path is reached only if it rejects the whole
call. It is four statements; it does not put any class near the 75% `RunSpecifiedTests` floor.

## 8. Process Observations

### What was healthy

- **The plan had already done the hard thinking, and it held up.** `steps[M3-S03].inputs.note`
  settles the three-class split, the template closure, the API-version split and the absence
  of a `package.xml`, each with the rule it follows. Every one of those held on contact. The
  note's claim that `SecurityUtils` and `ApplicationLogger` are deliberately *not* cited —
  because `SecurityUtils` references `ApplicationLogger`, which references `Application_Log__c`
  and `Logger_Setting__mdt`, a closure no step in this plan ships — is exactly the check
  `agents/apex-builder/AGENT.md` Step 6 would have forced, done one step earlier.
- **The upstream artefacts were specific enough to build against without guessing.** The
  approval process gave `allowedSubmitters type=owner` (which is what makes
  `setSubmitterId(record.OwnerId)` legal rather than hopeful, per gotcha 11), the
  `nextAutomatedApprover` Manager routing (which is why the fixture builds two users), and
  `recordEditability AdminOnly`. The permission set gave `Approval_Status__c` as
  `editable=false`, which is consistent with the field being written only by the process's own
  field updates — so the service correctly never writes it.

### What was concerning

- **A declared acceptance test was passing while checking nothing, and only a liveness probe
  found it.** The first draft read the process name from a `private static final` constant and
  passed it to `setProcessDefinitionNameOrId(PROCESS_DEVELOPER_NAME)`. That is ordinarily
  better Apex. But `check_approval_process_apex_patterns.py`'s `RE_PROCESS_NAME` only matches a
  **string literal inside the call**, so the constant hid the name entirely: the checker saw no
  process name in the Apex, skipped its resolution rule, and exited 0. Probe C — renaming the
  process to `Discount_Approval_Typo` — did not fire, which is how it surfaced. The name is now
  inline, with a comment saying why, and probe C fires `HIGH` at exit 1. The plan's own note
  assumed this ("check_approval_process_apex_patterns.py resolved that string against
  `Opportunity.Discount_Approval.approvalProcess-meta.xml` in a fixture run"); a constant would
  have quietly withdrawn that.
- **`check_test_class_standards.py` reads comments as code on its `runAs` path, in both
  directions.** `has_permissioned_runas`, `runas_arguments` and `find_fixture_seeded_as_persona`
  all call `strip_literals(text)` on the raw file and never `strip_comments`, although the same
  module defines an offset-preserving `strip_comments` for exactly this reason. Two consequences,
  both observed on this step's own file:
  (a) *false pass* — the first draft's header contained the prose `System.runAs(<permissioned rep>)`,
  and that comment alone satisfied the `user-mode-test-without-runas` ERROR. Probe B (replacing
  every real persona `runAs` with the self-user form) did not fire.
  (b) *false fail* — once that prose was removed, the rule fired on a class with **seven** real
  `System.runAs(` calls, because 97 apostrophes in ordinary possessive comments ("the running
  user's FLS") each opened a phantom string literal and `strip_literals` blanked every one of
  the seven calls. Measured: `raw runAs: 7 | after strip_literals: 0`.
  The file is now written without possessive apostrophes in comments and without a spelled-out
  `runAs` call in prose, and both probes behave: `has_permissioned_runas` sees all seven, and
  probe B fires ERROR at exit 1. **That is a workaround in this build, not a fix.** The fix is in
  the library: those three functions should strip comments before stripping literals. This is
  the same class of defect `skills/apex/apex-security-patterns/references/gotchas.md` already
  names — *"A Checker That Reads Comments As Code Flags Safe Classes"* — and the 2026-09-16
  comment-aware sweep evidently did not reach this path.
- **A skill is cited in `skills[]` with no test that runs its checker, and declaring one today
  would block the step.** `build_plan.py next` prints the advice for `apex/apex-security-patterns`.
  Run by hand for information, `check_apex_security_patterns.py --manifest-dir artefacts/M3-S03`
  exits 1 with three findings, and none of them is fixable inside this step:
  two `HIGH` *"user-facing entry point lacks obvious read-access enforcement"* on the controller
  and the action — a **per-file** heuristic meeting the deliberate three-class split of D6, where
  the enforcement lives one call away in the service — and one `MEDIUM` *"public/global Apex class
  has no explicit sharing declaration (apiVersion 67.0)"* against `TestDataFactory.cls`, which is
  the canonical template shipped verbatim by contract. Widening `scope` to `build` does not help,
  because the rule never leaves the file.

### What was ambiguous

1. **67.0 versus 62.0.** The run instruction said 67.0; `plan.json` says 62.0 in three places
   including a pinning manual test. The plan won. A human should settle whether the build's Apex
   really is meant to sit at 62.0 — it changes the security idiom, not just a number. At 62.0 the
   default access mode is system mode and the explicit `WITH USER_MODE` on the service's SOQL is
   what enforces FLS; at 67.0 user mode is the default and the keyword becomes a statement of
   intent rather than the mechanism. The code is correct either way, but only by accident at 67.0.
   Route: `amend-step` on `inputs.api_version` **and** on manual test 6, then re-run this step.
2. **The Percent reading (A35), still unconfirmed.** `QUALIFYING_DISCOUNT = 25` and
   `BELOW_THRESHOLD_DISCOUNT = 10` are the Apex half of an assumption only half of which is
   grounded in this library. Marked `UNVERIFIED (2026-09-19)` inline at the constants. If a
   retrieved record shows Apex reading `0.25`, those two literals are the only thing that changes.
3. **`submitBatch` is a method the single-record requirement did not ask for.** The feature
   summary says *"Submit exactly one"*, and by `agents/apex-builder/AGENT.md` Step 7 anything
   beyond the approved requirement is a deviation to surface rather than a bonus. It is here
   because `@InvocableMethod` is a List-in / List-out contract and Flow hands the action a whole
   batch of interviews — looping `submitOne` would have put one SOQL and one `Approval.process`
   per input inside a loop, which is a real defect the declared checkers would **not** have caught
   (`IM005` matches literal SOQL brackets and DML keywords, not a service call that performs them).
   `submitOne` remains the requirement's capability and the only thing the controller calls.
4. **The `Sales User` profile name.** The test queries `Profile WHERE Name = 'Sales User'`, from
   Q19 and `artefacts/M2-S02/profiles/Sales User.profile-meta.xml`. M2-S02's own deploy-order
   already carries the caveat that the exact name has to be confirmed in the target org; here a
   mismatch surfaces as a `QueryException` in `@TestSetup` rather than as a deploy error. Marked
   `UNVERIFIED` inline.
