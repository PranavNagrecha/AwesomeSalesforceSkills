## Where AGENT.md / the CLI did not fully carry § 3.1 at this tier (driver's-log material)

1. **§ 3.1's D/S/O/X counts are not fully mechanizable.** Three judgment calls were needed that neither AGENT.md nor § 3.1 resolve on their own: (a) whether the build-level `package.xml` aggregator step — required only because an Apex step exists, per § 5's Apex exception — counts toward D; (b) whether `OpportunityLineItem` counts as a distinct O object when the requirement only says "opportunity products," never the API name; (c) whether Product2/Pricebook2 setup is its own metadata-deployable step at all, given the org already has Sales Cloud Enterprise provisioned and the requirement frames products/price-book as existing capability being *used*, not built. All three read the same way here under "round up, never down," and none changed the final tier — but a differently-reasoned run of this same agent could plausibly land D=6-8 or O=2-4 from identical requirement text. The sizing rule is deterministic in its *thresholds*, not in what counts as a countable unit.
2. **`standards/decision-trees/automation-selection.md` has no formal branch for Approval Process, and no branch at all for Validation Rule.** The task asked this agent to consult that tree "for the approval/validation split." The tree's only mention of Approval Process is an unnumbered cheat-sheet row; its numbered Q-tree's Q1 trigger list (record change / button click / NL request / scheduled clock / external push / internal event) has no option for "a business decision needing one person's sign-off," so Approval Process is not reachable via the formal decision path at all. Validation Rule does not appear anywhere in the tree, because the tree's stated scope is six specific engines (Flow, Apex, Agentforce, Approvals, Platform Events, Batch, External) and Validation Rule is not one of them. The citation in this envelope names the cheat-sheet row honestly rather than inventing a `Q<n>` that does not exist.
3. **AGENT.md's `scale: ask`/`scale: feature` branches (informational pre-fill, capped rounds, `gate go`/`accept` aliases) do not apply at `project`**, which is the intentional, unchanged, pre-3.1 baseline — so there was nothing for those branches to under-support here. The friction in this run was entirely in step 1 above, not in any CLI subcommand: `set-scale`, `set-clarifications`, `validate` and `render` all behaved exactly as documented, with zero ERRORs at any point.
4. **The envelope schema's `process_observations` items require `evidence` even for `suggested_followup` entries**, which is not obvious from AGENT_CONTRACT.md's prose description of the block (it reads as most load-bearing for `concerning`/`ambiguous` categories) — caught by `validate_envelope.py` on the first attempt, fixed by adding a minimal `evidence.source` to both follow-up observations.
