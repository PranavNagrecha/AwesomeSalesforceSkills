## 4. Data strategy note

**Read: the platform, twice over, and Apex not at all.** `lightning-record-view-form` renders
`Discount__c` and `Approval_Status__c` with the platform's own labels, Percent formatting and
per-field FLS — a field the running user cannot read is simply absent rather than an error — and
`@wire(getRecord, { recordId: '$recordId', fields: FIELDS })` provisions the same two fields so
the button rule can be computed in JavaScript. Both go through Lightning Data Service and share
its cache, so this is one read model expressed twice, not two round trips.
`skills/lwc/wire-service-patterns` Decision Guidance: *"Standard record read with strong platform
security defaults -> UI API wire adapter or LDS base component."* The output fields are direct
children of the form, because nested anywhere else they render nothing (`lwc_guide L11727`).

**Write: imperative Apex.** *"User clicks Save or Submit and writes data -> Imperative call …
Writes cannot be `cacheable=true`, so they cannot be wired."* The shape is
`templates/lwc/patterns/imperativeApexPattern.js`, copy-renamed: loading flag set before the
call, cleared in `finally`, errors surfaced through `ShowToastEvent` rather than the console.

**Refresh: `notifyRecordUpdateAvailable([{ recordId }])`, never `refreshApex`.** The stale read
is a UI API wire, and *"`refreshApex()` on a non-Apex wire adapter is deprecated"*
(wire-service-patterns gotcha 7). This is Q34's *"the component refreshes the record after
submit"*, and it reaches the record detail and every other LDS wire on the record, which
`refreshApex` would not.

**Both refusal shapes are handled.** `submitForApproval` returns a `SubmitOutcome`
(`{ opportunityId, success, message, instanceStatus }`) and refuses by returning
`success = false` with a `message` rather than by throwing — Q30's answer, and the reason the
controller does not raise an `AuraHandledException`. The ordinary refusal path therefore never
reaches `catch`; the component branches on `outcome.success` first and treats a thrown error as
the exceptional case. On a refusal nothing is refreshed, because nothing changed.

**Decision tree.** `standards/decision-trees/automation-selection.md` Q8 — *"Can the action
complete in under 10s without custom UI? No -> LWC calling imperative Apex (see
`templates/lwc/patterns/imperativeApexPattern.js`)"* — recorded as plan decision D5.

## 5. Exposure matrix and the API version

| | |
|---|---|
| `isExposed` | `true` |
| `targets` | `lightning__RecordPage` |
| `targetConfig` objects | `Opportunity` — omitting it would make the panel droppable on every UI-API-supported object (`lwc_guide L19363`), and it reads two fields that exist nowhere else |
| `supportedFormFactors` | `Large`, `Small` — assumption A17 (Q51's default). Safe because the bundle contains no `lightning-datatable` and no `lightning-tree-grid` |
| Design attributes | one: `discountThreshold`, `type="Integer"`, `default="20"`, description naming `Opportunity_Discount_Requires_Approval` |

`type="Integer"` is one of the three types a `lightning__RecordPage` `targetConfig` accepts
(`Boolean`, `Integer`, `String` — `lwc_guide L18972-L18975`). No `min`/`max`: those cannot be
changed while the component is in use on a Lightning page (`L9907`) and no requirement fixes a
legal range. App Builder hands even an `Integer` property over as a **string**, so every read of
it goes through a `threshold` getter that coerces with `Number()`; `25 > '20'` untouched is a
silent false.

**The API version, and the one place this brief and `plan.json` disagree.** The run brief said to
read this step's API version from `plan.json` `inputs` and use exactly that. `steps[M3-S04].inputs{}`
carries no `api_version` — M3-S03 is the only step in the plan that does. `plan.json` wins, so the
version was resolved by `agents/lwc-builder/AGENT.md` Step 6's order instead: no sibling LWC bundle
exists anywhere in this build, the repo has no `sfdx-project.json`, and no org alias was supplied,
which lands on Step 6's fourth rung — state the version and say how it was derived. **62.0**, because
all nine `package.xml` files under `artefacts/` declare `<version>62.0</version>` and M3-S03's four
authored classes, including the controller this bundle imports, are pinned at 62.0 by decision
D-M3S03-01. 62.0 is above the 58.0 floor below which the platform treats a bundle as 58.0 anyway,
and base components are not versioned, so nothing in the bundle is rolled back by it.

## 7. Process Observations

**Healthy.** The upstream artefacts were precise enough to build against without a single guess —
the controller's signature and parameter name, the picklist's exact three values, and the fact
that blank means nothing was ever submitted all came off files in this build. The plan's step
note had already settled the data strategy, the refresh call, the toast module and the design
attribute against the rule each one follows, and predicted the checker's output line word for
word. And M2-S03's validation rule already tells the rep to *"submit for approval from the
Discount panel"*, so the blocked save and the panel name each other across two milestones —
coherence nothing in the plan forced.

**Concerning.** Two of the three checkers `next` advises declaring here cannot assert anything
about this step, and following the printed advice verbatim would block a correct one
(`M3S04-F-01`). The only offline syntax check available for an emitted LWC module fails open on
precisely the file shape LWC modules have (`M3S04-F-02`). And
`templates/lwc/component-skeleton/componentSkeleton.html` — the repo's canonical bundle shell —
still uses legacy `if:true` in three places, which `agents/lwc-builder/AGENT.md` Step 4 and
`skills/lwc/lwc-conditional-rendering` both forbid in new bundles: copying the template
faithfully would produce a template the skill rejects.

**Ambiguous.** The brief asked for an API version the plan does not carry, so 62.0 is derived and
recorded rather than declared (§ 5). Assumption A35's UI API half is still unconfirmed, so this
component compares a Percent field against `20` while the validation rule and the approval entry
criteria in the same build compare the same threshold against `0.20`; if a retrieved record shows
the UI API returning the fraction, the `threshold` getter and two Jest literals are the whole of
the change, and the suite is what fails first. Q51 and Q52 were both defaults applied at G1
(A17, A18), which between them fix the panel as read-only and its toast module as
`platformShowToastEvent` — adding an Experience Cloud target later changes the import, not just
the meta XML. Finally, the panel's user-facing strings are hard-coded English because no step in
this plan ships a `CustomLabel` (`M3S04-F-03`).

**Suggested follow-up.** `lwc-auditor`, because the builder auditing its own bundle is the
weakest form of the check, and it runs `check_lwc_accessibility.py` and the security rules this
step never declared.
