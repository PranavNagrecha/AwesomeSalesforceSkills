# Installing SfSkills as a Claude Code plugin

**Who this is for:** Claude Code users installing SfSkills as a plugin, and
maintainers changing the plugin build.

The plugin artifacts are generated by
[`scripts/build_plugin.py`](../scripts/build_plugin.py). The shipped version is
whatever `.claude-plugin/plugin.json` says; read it there rather than from this
page.

Before you rely on the output: 55 of the 70 run-time agents the plugin ships are
`experimental` (ungraded), and most skill packages have not been claims-audited
against official Salesforce guides yet. See
[`agents/_shared/RUNTIME_VS_BUILD.md`](../agents/_shared/RUNTIME_VS_BUILD.md).

---

## Install

### From GitHub (normal path)

Inside Claude Code:

```
/plugin marketplace add PranavNagrecha/AwesomeSalesforceSkills
/plugin install sfskills@sfskills
```

Or from a shell:

```bash
claude plugin marketplace add PranavNagrecha/AwesomeSalesforceSkills
claude plugin install sfskills@sfskills
```

### From a local clone

The repository is its own marketplace, so a clone works as a source with no
extra setup. Use this when you want to install a working tree you are editing:

```bash
git clone https://github.com/PranavNagrecha/AwesomeSalesforceSkills.git
claude plugin marketplace add ./AwesomeSalesforceSkills
claude plugin install sfskills@sfskills
```

Run these from a directory that is **not** the clone (see the next section). A
local-path install copies the whole working tree, gitignored files included,
into the plugin cache; clear `exports/` and `vector_index/` first if the size
matters. A GitHub install fetches tracked files only.

### The plugin does not ship an MCP server

`.claude-plugin/plugin.json` declares no `mcpServers` key, and a clean install
reports `MCP servers (0)`. The `sfskills-mcp` server is a separate, manual setup —
see [installing.md §5](./installing.md#5-mcp-install-paths). Nothing on this page
depends on it: the zero-setup lookup path is the shipped roster.

## Verify the plugin path

Claude Code loads `.claude/skills/` and `.claude/agents/` **from your current
working directory** whenever you are in a trusted project, plugin or no plugin.
Checked from inside a clone, routers and subagents appear whether or not the
plugin works. Both copies are byte-identical and the project-local one wins
inside a clone, so only `claude plugin details`, run from outside, can tell.

Run this from a directory that is not this repository and has no `.claude/` of
its own. The `CLAUDE_CONFIG_DIR` override keeps the experiment out of your real
configuration:

```bash
export CLAUDE_CONFIG_DIR="$(mktemp -d)"      # throwaway config
cd "$(mktemp -d)"                            # NOT the repo, no .claude/ here

claude plugin marketplace add /absolute/path/to/AwesomeSalesforceSkills
claude plugin install sfskills@sfskills --scope user
claude plugin details sfskills
claude plugin list
```

What to look for:

- **`Source: sfskills@sfskills`** — `plugin details` only knows installed
  plugins, so any output at all is plugin-path evidence.
- **`Skills (n)`** — the routers from `.claude/skills/` plus one per file in
  `commands/`.
- **`Agents (n)`** — one per active run-time agent, from the flat
  `agents/<id>.md` loaders.
- **`MCP servers (0)`** — expected.
- **`Always-on: ~N tok`** — Claude Code's own accounting of what the install adds
  to every session.
- `claude plugin list` reports `Status: ✔ enabled`. A malformed manifest reports
  `✘ failed to load` here even when its components seem to work in a session
  (because project-local loading picked them up). Treat `plugin list` and
  `plugin details` as the source of truth.

Tear the experiment down:

```bash
claude plugin uninstall sfskills
claude plugin marketplace remove sfskills
rm -rf "$CLAUDE_CONFIG_DIR"; unset CLAUDE_CONFIG_DIR
```

The repo-side equivalent is `python3 scripts/build_plugin.py --audit-install`:
it projects the installed inventory from the repo's own files and exits 1 for
any component the plugin cannot deliver. It is a model of the loader, not a
reading of it; when in doubt, run the install.

## What loads into context

Claude Code loads every skill's and agent's `name` and `description` at session
start. A flat export of every skill package would put well over a hundred
thousand tokens of descriptions in front of every session, so the plugin is
tiered: only the router skills, the slash commands and the agent loaders are
always on (frontmatter only). Skill packages and the per-domain rosters
(`.claude/skills/salesforce-<domain>/references/skill-index.md`) are read on
demand, and an agent's `agents/<id>/AGENT.md` playbook is read when the agent is
invoked. `python3 scripts/build_plugin.py --measure` prints the current
always-on estimate against its budget; the token model is explained in
[architecture.md](architecture.md#why-the-library-is-tiered-at-all).

## Regenerating the artifacts

Everything under `.claude-plugin/`, `.claude/skills/` and `.claude/agents/` is
generated, and so are the flat `agents/<id>.md` loaders. Do not hand-edit any of
it; to change the version, bump `PLUGIN_VERSION` in `scripts/build_plugin.py`.
The `agents/<id>/AGENT.md` packages and `agents/_shared/` are hand-authored and
never touched by the build; it prunes only top-level `agents/*.md` files that
carry its generated marker.

```bash
python3 scripts/build_plugin.py                 # build in place
python3 scripts/build_plugin.py --check         # drift gate; exit 1 on any diff
python3 scripts/build_plugin.py --measure       # token budget; exit 1 if over
python3 scripts/build_plugin.py --verify-seeds  # resolve the curated seed table
python3 scripts/build_plugin.py --audit-install # installed inventory; exit 1 on a gap
```

The single hand-authored input is the seed table at the top of
`scripts/build_plugin.py` (featured skills per domain, decision-tree pointers,
trigger vocabulary). Every seed is resolved against `registry/skills.json` and
the filesystem at build time, so a renamed skill fails the build. When you edit
`DOMAIN_META`, count where the packages actually are in `registry/skills.json`
and make each router's keyword list match; a router that advertises a keyword
whose packages live in another domain sends the reader to a roster that cannot
answer.

If you add a router, re-add the new files with `git add -f` (`.claude/` is
ignored by default, with negations for `agents/`, `skills/` and `workflows/`).

## Known limitations

1. **The `agents` manifest key does not work.** Probed on Claude Code 2.1.209:
   only a flat `*.md` directly inside `<plugin root>/agents/` ships a subagent,
   and declaring the `agents` key suppresses even that. So the manifest omits the
   key and the build writes each loader twice — `agents/<id>.md` for the plugin,
   `.claude/agents/<id>.md` for anyone whose cwd is a clone. Deleting either set
   breaks one of those paths. Re-probe on a newer Claude Code before changing it.
2. **`.claude/commands/` is not tracked.** The plugin ships commands from the
   tracked `commands/` directory (`"commands": ["./commands/"]`);
   `.claude/commands/` is a local copy that `python3 scripts/bootstrap.py`
   writes.
3. **No search index ships.** `vector_index/chunks.jsonl` and
   `vector_index/lexical.sqlite` are gitignored, so after a GitHub install
   `scripts/search_knowledge.py` cannot answer until you build the index once
   (see [installing.md §1](./installing.md#1-install)). The routers do not need
   it: each domain router ships a roster of its packages, one gloss each.
4. **Every command ships**, including the nine deprecated `LEGACY ALIAS`
   commands and the library-maintenance commands (`/new-skill`, `/new-agent`,
   `/build-skills`, `/onboard-source`, `/add-skill`, …) that mean nothing to
   someone who installed the plugin to use the library. Trimming them means
   listing the keepers in `PLUGIN_COMMANDS_PATH`.

## Uninstall

```bash
claude plugin uninstall sfskills
claude plugin marketplace remove sfskills
```

Removing the marketplace does not delete the plugin cache directory
(`<CLAUDE_CONFIG_DIR>/plugins/cache/`); remove it yourself if you want the space
back.
