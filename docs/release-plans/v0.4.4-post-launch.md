## Context

v0.4.4 closes the 18-item punch list from the two pre-prod QA reports
([`qa-pre-prod-report-2026-05-10.md`](.planning/qa-pre-prod-report-2026-05-10.md)
and [`qa-content-report-2026-05-10.md`](.planning/qa-content-report-2026-05-10.md))
— 6 MCP P0 release blockers, 9 MCP P1 polish items, 3 MCP P2 housekeeping
items, 2 content P0 issues, and 2 content P1 issues. All fixes were
verified locally (248/248 unit tests, `validate_repo.py` reports 0 errors)
but the original gating signal — running the QA harness against the
real `ExampleOrg Dev PN` sandbox — has NOT been re-run against the fixed
code yet.

This document describes what happens between "tests pass locally" and
"users are running v0.4.4 in production."

Passive monitoring. No code changes unless one of the triggers fires.

## Week 2–3 — First follow-up wave

Order is impact-per-hour, not report ordering.

### L2-1 — Complete 5–10 highest-traffic stubs

The 50 stubs are flagged with `status: stub` so consumers can filter them,
but completing them is the long-term right answer. Pick the most
retrievable ones first:

- `admin/activity-and-task-patterns`
- `apex/apex-future-method-patterns`
- `apex/apex-savepoint-and-rollback`
- `lwc/lwc-wire-refresh-patterns`
- `lwc/lwc-navigation-mixin`
- `flow/flow-cross-object-updates`
- `integration/platform-event-publish-patterns`

For each: fill `references/examples.md`, `references/gotchas.md`,
`references/well-architected.md`. Flip `status: stub` → remove the
field (the default is `stable`). Run `skill_sync.py` + `validate_repo.py`.

**Effort:** 1–2 hours per skill. Plan for ~1 week of background work
for the first 10.

### L2-2 — Browser-UA URL re-verification

The QA report flagged 1,209 URLs at `developer.salesforce.com` /
`architect.salesforce.com` as unverifiable (Cloudflare bot detection
returns 403 even with a browser User-Agent set via Python). A manual
spot-check of 5 returned 200 in a real browser.

Build a Playwright-driven verifier:

```python
# .planning/tools/url-revalidator.py
from playwright.sync_api import sync_playwright
# load .planning/qa-execution/results/content_phase1_recheck_403_2026-05-11.json
# for each URL, navigate, capture final status + URL after redirect
# anything still 403 after a real browser → confirmed dead
```

**Effort:** 1 day to build the tool, then runs unattended overnight.

### L2-3 — Cross-reference resolver

Phase 3 of content QA was inconclusive because the regex matched
JavaScript object literals inside code fences. A proper extractor needs to:

1. Strip fenced code blocks (line-anchored — see `_AP_FENCE_RE` in
   `pipelines/validators.py` for the right regex).
2. Extract markdown links `[label](path)` AND bare references like
   `see skills/admin/X` or `skills/admin/X/SKILL.md`.
3. Resolve relative paths against the file location.
4. Verify each resolved path exists.

**Effort:** ~½ day.

### L2-4 — Tier-3-cloud feature grounding

Skills covering Marketing Cloud, Data Cloud, Industries Clouds, etc.
reference features not present in `ExampleOrg Dev PN`. Their
org-grounding has not been verified.

Provision a second sandbox with those features enabled and re-run
`content_phase4_to_7.py` against it for those skills.

**Effort:** 1 day for sandbox provisioning + ~1 hour test.

## Hotfix protocol (when something P0 breaks in the wild)

If a downstream user reports a P0 within the first 7 days of v0.4.4
being live, follow this sequence — never skip steps because "this looks
small."

1. **Reproduce in `ExampleOrg Dev PN` first.** Never trust a remote bug
   report without local repro. The reporter may have a non-standard org
   shape; the fix needs to match THIS org's behavior.
2. **Branch from main as `hotfix/0.4.5`.** Don't fix on main directly —
   any in-flight Wave-11 work stays clean.
3. **Bump to 0.4.5** in `mcp/sfskills-mcp/pyproject.toml` +
   `mcp/sfskills-mcp/src/sfskills_mcp/__init__.py`. Patch-level because
   it's a fix, not a feature.
4. **Run the FULL pre-prod harness again, not a scoped subset.**
   Hotfixes are exactly when shortcuts bite. The fix may interact with
   a code path the focused repro didn't exercise.
5. **Publish to PyPI**, `git push`, `git tag v0.4.5`, write a one-line
   CHANGELOG addendum in `__init__.py`.

The MCP server's `health()` tool returns version + skill_count, so when
chasing a remote report, the first question to the reporter is "what
does `health` say?" — that confirms which version is actually installed.

## What's deliberately NOT in this plan

- **Push to PyPI before L0-1 / L0-2 / L0-3 complete.** Don't do it.
- **Marketing or external announcement.** This is a patch release; the
  audience is existing users via PyPI auto-update notification.
- **Fixing all 50 stubs before publish.** `status: stub` is the
  pre-publish signal; completing them is post-publish work.
- **Touching the `developer.salesforce.com` / `architect.salesforce.com`
  URLs that were flagged as unverifiable.** They're likely fine; we'll
  re-verify in L2-2 with a real browser.
