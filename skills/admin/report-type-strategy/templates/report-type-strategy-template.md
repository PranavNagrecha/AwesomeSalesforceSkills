## 2. Join chain

One row per **child** relationship, in the order the joins are applied. Maximum four objects total,
including the base object.

| # | Relationship name (child relationship, e.g. `Cases`) | Parent may have zero? | `outerJoin` | Mandatory or optional |
|---|---|---|---|---|
| 1 | | yes / no | true / false | |
| 2 | | yes / no | true / false | |
| 3 | | yes / no | true / false | |

Legality check — both must be true before proceeding:

- [ ] Objects in the chain, including `baseObject`, total **four or fewer**.
- [ ] No row with `outerJoin: false` appears **after** a row with `outerJoin: true`.

If the second check fails, the mandatory relationships must be reordered ahead of the optional ones,
or the requirement needs two report types. Record which.

**Resolution:** _(reorder / split into two types / requirement relaxed)_

## 6. Pre-deploy checklist

- [ ] Existing types retrieved with the wildcard manifest; no existing type has this `baseObject`
      **and** this topology.
- [ ] `baseObject` settled and named in the label.
- [ ] Join chain passes both legality checks in section 2.
- [ ] Every lookup parent moved out of the join chain into section 3.
- [ ] Every section has at least one column and a `masterLabel`.
- [ ] `description` written for the picker, not for the ticket.
- [ ] `deployed` set to `true` if anyone without Manage Custom Report Types must see it.
- [ ] `python3 scripts/check_report_type_strategy.py --manifest-dir <dx-root>` returns no ERROR.
- [ ] `sf project deploy start --dry-run` passes.
- [ ] Autogenerated (historical-trending) types excluded from this change.
