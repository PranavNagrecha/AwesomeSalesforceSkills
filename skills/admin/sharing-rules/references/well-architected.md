# Well-Architected Notes — Sharing Rules

## Relevant Pillars

- **Security** — A sharing rule is a standing grant, not a one-off decision, so it must be justified the way a permission set is. The two places over-sharing enters through this mechanism are `accountSettings` on Account rules (three required child access levels that an admin can accept without reading) and `sharedTo` → `allInternalUsers`, documented as "a group containing all internal and nonportal users." Both are legitimate configurations; neither should ever appear without a written reason. The Security review question is not "does this rule work" but "what is the smallest population and lowest access level that satisfies the requirement," and whether the rule *replaces* a broader grant (`View All`, `Modify All`, a relaxed OWD) rather than sitting alongside it.

- **Scalability** — Access is precomputed, so the platform's read path stays fast while the *change* path carries the cost. That cost scales with matched records multiplied by resolved group membership, and Salesforce is explicit that "the size and complexity of an organization's queues and hierarchies directly affect the duration of record access calculations." Scalability work in this domain is therefore about the shape of the change, not the shape of the query: choosing stable criteria fields, keeping target groups flat, and batching structural change behind deferred sharing calculation so one job runs instead of hundreds.

- **Operational Excellence** — Rules accumulate silently. Nothing expires, nothing reports on itself, and a rule written for an org shape that no longer exists keeps deploying to every sandbox and keeps consuming the object's rule budget. The operational practice that matters is an inventory: rule name, type, source group, target group, access level, and the requirement it satisfies, maintained as metadata in version control rather than rediscovered in Setup. Deploying rules as `<Object>.sharingRules-meta.xml` under source control makes that inventory a diff instead of an archaeology exercise.

- **Reliability** — The failure mode here is quiet rather than loud. Recalculation runs asynchronously on a Setup page nobody thinks to open, an ownership change deletes grants nobody associated with sharing, and a write-once field locks a mistake in permanently. Reliability comes from watching Background Jobs until the recalculation clears and then verifying against the share table with SOQL — including a negative test as a non-member — rather than from the rule saving without an error.

## Architectural Tradeoffs

**Owner-based versus criteria-based.** Owner-based rules follow the organisation and survive reorgs without maintenance, but they can only express access that genuinely tracks ownership. Criteria-based rules express access that tracks data, at the cost of coupling sharing maintenance to data maintenance — every edit to a criteria field is a potential share-table write. The decision rule that holds up in practice: if the requirement is a sentence about people, use owner-based; if it is a sentence about records, use criteria-based; if the criteria field is one that changes on most records regularly, the requirement is probably being modelled at the wrong layer.

**Sharing rules versus a looser OWD.** A single OWD change is one decision and one recalculation; a family of sharing rules is many decisions and continuous maintenance. The tradeoff is precision against operational weight. The honest test is whether the rules are carving exceptions out of a baseline that is nearly right, or reconstructing a baseline that is wrong. A rule count that climbs every quarter on one object is evidence of the second case, and the fix is upstream in `admin/sharing-and-visibility`, not another rule.

**Sharing rules versus Apex managed sharing.** Declarative rules are visible, deployable, auditable by non-developers, and maintained by the platform. Apex managed sharing handles logic that criteria cannot express — cross-object conditions, computed populations, per-record recipients — and it survives ownership change, which manual shares do not. The cost is a code artefact that must be tested, a recalculation class that must be registered, and access logic that no admin can read in Setup. Reach for Apex only when a criteria expression genuinely cannot state the condition, not when it would merely be tidier.

**Declarative addition versus restriction rules.** Sharing rules only add. When the requirement contains the word "except," the model needs a subtractive mechanism, and stacking more sharing rules to route around a grant produces an unreadable model in which nobody can say why a user has access. Route to `admin/restriction-rules`.

## Anti-Patterns

1. **Rules layered on top of a `View All` grant.** The rule is written, the permission set that made it unnecessary is left in place, and the org now has both the narrow mechanism and the broad one. The audit finding survives, the rule changes nothing, and the next admin cannot tell which one is load-bearing. Remove the broad grant in the same change that introduces the rule.

2. **A rule per requirement instead of a group per population.** Ten rules targeting ten roles, where one public group containing those roles would do. Every additional rule is another object to recalculate on every structural change, and the rule count consumes a documented per-object budget of 300 rules, at most 50 of which may be criteria-based or guest user rules.

3. **Criteria fields chosen for expressiveness rather than stability.** `StageName`, `Status`, and `Priority` describe the record accurately and change constantly. A rule on one of them is correct and expensive, and the cost surfaces as unexplained slowness in bulk operations long after the rule ships.

4. **Guest access built as an ordinary criteria-based rule.** `SharingGuestRule` is a distinct metadata type with an access ceiling the platform enforces. Approximating it with a normal rule aimed at a group containing the guest user gives up that guardrail on exactly the access path where a mistake is public.

## Contradiction Log

### Ownership of sharing-rule guidance — overlap with `admin/sharing-and-visibility`

**This skill says:** sharing rules — both types, their metadata, their recalculation behaviour, and the `__Share` rows they produce — are owned here.

**`admin/sharing-and-visibility` says:** it declares `'sharing rule'` among its own trigger keywords and carries a Record Access Decision Matrix row for owner-based and criteria-based rules.

**Context where this skill applies:** any request to design, build, deploy, audit, or debug a specific sharing rule.

**Context where `admin/sharing-and-visibility` applies:** choosing the baseline — OWD, role hierarchy, teams, bypass permissions — and explaining the layered model in which sharing rules are one layer.

**Resolution status:** Needs human review. This is a deliberate carve-out, not an accident: at the time this package was authored, the query `sharing rules` returned `admin/compliant-data-sharing-setup` (a Financial Services Cloud package) as its top hit and did not return `admin/sharing-and-visibility` at all, despite the umbrella declaring the keyword. The umbrella's `description` and its Record Access Decision Matrix should be retargeted to the baseline model and point here for the rules themselves; until that edit lands, both packages claim the vocabulary and the umbrella wins nothing with it.

### Corrections applied during review

Two claims in the first draft of this package were wrong and have been replaced from source.

1. **"The rule-count caps are unpublished / edition-specific."** The first draft omitted the per-object caps entirely and justified the omission by asserting that the Security Guide had moved to `help.salesforce.com` and that the limits PDF on `resources.docs.salesforce.com` failed TLS verification. Neither was true: `salesforce_security_impl_guide.pdf` fetches cleanly from `resources.docs.salesforce.com/262/...` and carries the cap verbatim — "You can define up to 300 total sharing rules for each object, including up to 50 criteria-based or guest user sharing rules, if available for the object." The numbers are now stated in `SKILL.md`, in `references/gotchas.md` Gotcha 11, and as defaults in `scripts/check_sharing_rules.py`. What varies by edition is object availability, not the caps.

2. **"Recalculation has no progress indicator."** The first draft asserted repeatedly that Setup shows no job, no percentage and no completion signal, and even carried a `[STALE-RISK]` marker admitting the doubt. The Security Guide documents the opposite: "You can monitor the progress of your parallel sharing rule or organization-wide default recalculation on the Background Jobs page or view recent sharing operations on the View Setup Audit Trail page," and "You receive an email notification when the recalculation is completed for all affected objects." Every occurrence has been corrected. The underlying advice — do not promise instant access, verify against the share table — is unchanged and still correct; only the reason was wrong.

### Genuine omissions

Deferred sharing calculation is described here only as far as the Large Data Volumes guide and the Security Guide document it. The Setup mechanics of enabling the permission belong to `data/sharing-recalculation-performance`. Criteria-based sharing field restrictions ("you can't use lookup fields, encrypted fields, formula fields, or fields whose values are derived from other fields on the record") are noted in the decision guidance but not enumerated per object; object-by-object availability lives on the Sharing Settings Setup page in the target org and is deliberately not mirrored here.
