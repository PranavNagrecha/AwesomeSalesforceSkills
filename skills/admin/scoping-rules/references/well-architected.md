# Well-Architected Notes — Scoping Rules

## Relevant Pillars

- **User Experience** — This is the pillar the feature exists to serve. A scoping rule is the platform's answer to "the default view returns too much", and it answers it without the collateral damage of the alternatives: no per-user personal list views to govern, no per-team duplicate views to maintain, no access removed to solve a clutter problem. The specific thing to watch is that the benefit is invisible until someone sets `filterScope` on the list views and `scope` on the reports. A rule shipped without that step is a design that scored well in review and changed nothing for a user.
- **Performance** — Scope criteria are evaluated on list view render, report run, and unqualified SOQL against the target object, so the cost lands on the org's hottest paths. Salesforce reserves the right to disable a rule that is inefficient or that runs against a data model large enough to cause slowness when the rule is applied. That is an unusual contract: the platform may withdraw the feature rather than degrade, which means the failure mode is silent reversion to the unscoped view, not a slow page. Design for selectivity, measure the criteria as a standalone query at production scale, and treat "is this rule still active" as an operational check on high-volume objects.
- **Security** — Relevant by negation, and that is the highest-value thing this skill has to say. Scoping rules "don't restrict the access that your users have to records. Your users can still open and report on all the records that they can access according to your org's sharing settings." A scoping rule adopted as a confidentiality control is a control that the protected user can switch off, and one whose official surface table names only List Views, Reports and SOQL — Search and SOSL, which the restriction-rule documentation names explicitly, do not appear. The pillar guidance is therefore a routing rule, not a hardening rule: when the requirement is "must not see", the artefact is the sharing model or a restriction rule, and this skill's job is to refuse the work and say so.

## Architectural Tradeoffs

**One parameterised rule vs one rule per population.** The literal approach — a rule per department, per region, per branch — is easier to read and easier to explain to a stakeholder. It also collides with two constraints at once: the per-object active-rule cap ("create up to two active scoping rules per object in Developer editions", "create up to five active scoping rules per object in Performance and Unlimited editions") and the one-rule-per-object-per-user constraint, which every additional rule makes harder to guarantee. The parameterised alternative — `Field = $User.Field` plus a mutable User attribute — is one rule regardless of population size, but moves the correctness burden onto data quality in the User object. In any org with more than a handful of populations, take the parameterised design and invest in keeping the User field accurate.

**Object Manager vs API authoring.** Setup is faster, needs no deploy, and is legible to an admin who will maintain it. It also cannot express the SOQL operator at all, so the choice is made by the criterion rather than by preference. The deeper tradeoff is governance: a rule built in Setup exists only in the org and drifts silently between environments, while a `.rule` file in source control is reviewable, diffable and promotable — at the cost of a deploy step and an ID remap on every hop. For anything a compliance or audit function will ever ask about, take the source-controlled path even when Object Manager could build it.

**Durable attributes vs org-specific IDs in criteria.** `$User.UserRoleId = '00E...'` is precise and is what the documented examples use, because the criteria language has no name-based alternative for role, profile or record type references. It is also the single most reliable way to ship a rule that matches nobody in production. A custom permission, a custom User field, or `$User.Department` survives promotion unchanged and reads better in review, at the cost of an extra artefact to provision. Prefer the durable attribute wherever the criterion can be expressed against one; where it cannot, the ID remap belongs in the deploy runbook as a required step rather than in someone's memory.

**Scoping now vs restricting later.** A scoping rule is cheap to add and cheap to remove, which makes it a reasonable first response to a "too much noise" complaint while the real requirement is still being understood. The risk is that it reads to a non-technical stakeholder as though the problem is solved, and the language ("users only see their own region") is indistinguishable from an access guarantee. Mitigate in writing, at the point of delivery, not in the design doc: state that users retain full access and can switch scope, and get that acknowledged.

## Anti-Patterns

1. **Scoping rule as a compliance control.** Shipping a scoping rule in response to "team A must not see team B's records". The user can select a different scope, the rule never touched global search, and the sharing model always granted the access. If the requirement survives the question "is it acceptable that they *could* see it, just not by default?", the answer is `admin/restriction-rules` or the sharing model.

2. **Authoring a `ScopingRule` metadata type.** There isn't one. A scoping rule is `RestrictionRule` with `enforcementType` set to `Scoping`, deployed from `restrictionRules/` with a `.rule` suffix, and retrieved with `<name>RestrictionRule</name>` in `package.xml`. A `scopingRules/` directory or a `<ScopingRule>` root element will not deploy.

3. **Declaring done at rule activation.** The rule is half the work. List views and reports honour it only when **Filter by scope** is selected, so an active rule with no `filterScope` on any list view is a change nobody experiences. Verify by logging in as a user matched by `userCriteria`, not by reading the Setup page.

4. **Disabling the rule before unwinding its references.** Removal runs in the reverse order of the build, and the documented instruction is stronger than "edit them first": "To disable a scoping rule, first delete the list views and reports that have **Filter by scope** selected. After a scoping rule is disabled, the list views and reports aren't functional nor modifiable." The repair window closes with the rule. The same asymmetry applies to components the criteria reference — deleting a custom permission or a picklist value that a rule depends on breaks the rule.

5. **`USING SCOPE EVERYTHING` on the outer `SELECT` only.** The requirement is recursive — every nested `SELECT` needs it too, because SOQL is scoped by default and a subquery inside a rule's own criteria would otherwise be filtered by the rule being defined.

6. **Designing a compound criterion for a declarative build.** "Unless you use SOQL, scoping rules support only the EQUALS operator. The AND and OR operators aren't supported." A design that promises "open opportunities in my region" as an Object Manager click-path is undeliverable; the honest options are a precomputed field the criterion can equal, or the SOQL operator with its API-only build path and its own constraint list.

7. **Designing scoping and restriction rules on the same object independently.** They share the one-rule-per-object-per-user constraint. Two teams shipping a scoping rule and a restriction rule on Task in the same release can produce overlapping `userCriteria` with no error and unpredictable behaviour. Inventory both rule kinds on the object before adding either.

## Contradiction Log

### Edition availability — conflict between two official Salesforce pages

The Scoping Rules Developer Guide is split down the middle, three pages to three.

**Saying Performance, Unlimited *and* Developer:** the Scoping Rules overview ("Available in: Lightning Experience in **Performance**,**Unlimited**, and **Developer** editions."), Before You Start, and the Display a Department's Records by Default example.

**Saying Performance and Unlimited only:** Considerations for Scoping Rules ("Available in: Lightning Experience in **Performance** and **Unlimited** Editions"), Create a Branch Management Scoping Rule Using the Metadata API, and Use the SOQL Operator in Scoping Rule Record Criteria.

The Considerations page argues against its own banner in its own body: "Create up to two active scoping rules per object in Developer editions."

**Which wins:** The three pages naming Developer, supported by the limits sentence on the conflicting page itself. All six are Tier 1 official documentation, so the tier ladder does not resolve it; the tie-break is internal consistency — a page that publishes a Developer-edition per-object cap is asserting Developer-edition support in its own body, which makes the omission in its banner the likelier error. The banner text is also identical across the three restrictive pages, which reads like one stale boilerplate block copied three times rather than three independent assertions.

**Practical resolution:** This skill states Performance, Unlimited and Developer, and instructs the reader to confirm in the target org (Object Manager → the object → Scoping Rules) rather than rely on either banner. Enterprise edition appears in neither scoping-rule list and must not be inferred from the restriction-rule limits, which do name Enterprise.

**Resolution status:** Resolved, with a verification step. Documented in `gotchas.md` Gotcha 8.

### `USING SCOPE EVERYTHING` in nested SELECTs — the rule contradicts every nested example

**Use the SOQL Operator in Scoping Rule Record Criteria says:** "The SELECT statement, including nested SELECT statements, must include USING SCOPE EVERYTHING. USING SCOPE EVERYTHING is the only valid scope clause syntax for scoping rules." Considerations for Scoping Rules repeats it.

**Every documented example that actually nests a SELECT does the opposite.** The Branch Management quick start's `BranchRuleOnAccount` and `BranchRuleOnLead` rules, and the same string reproduced on the SOQL-operator page, all carry two `SELECT` statements and exactly one `USING SCOPE EVERYTHING`, on the outer query only. The examples that do comply (`SOQL(Id, SELECT Account.id FROM AccountAdvisors USING SCOPE EVERYTHING WHERE userid = $User.Id)`, `SOQL(OwnerId, Select Id from User USING SCOPE Everything LIMIT 2)`) have no nested SELECT to test the rule against. There is no published example that both nests and complies.

**Which wins:** Neither can be dismissed — a normative sentence and a copy-pasteable working example are both Tier 1, and the example is the one customers deploy. This skill teaches the compliant form (the clause on every `SELECT`), because it satisfies the stated rule and is a strict superset of the documented example, so it is correct under either reading. What this skill does **not** do is treat the documented form as broken: the checker script reports the mismatch as WARN, not ERROR, precisely so it does not fail Salesforce's own published metadata.

**Resolution status:** Unresolved upstream; mitigated by writing the superset form and verifying in a sandbox. Documented in `gotchas.md` Gotcha 5.

### Naming — this skill vs `apex/soql-using-scope-clause`

**This skill covers:** the Setup and Metadata API feature — `RestrictionRule` with `enforcementType: Scoping`.

**`apex/soql-using-scope-clause` covers:** the SOQL `USING SCOPE filterScope` clause, including its `scopingRule` value and the `USING SCOPE EVERYTHING` requirement inside a scoping rule's SOQL operator.

**Not a contradiction — a shared boundary.** The two features intersect at exactly one point and both skills describe that point consistently: scope filters, it does not enforce. This skill's `description` carries an explicit `NOT for the SOQL USING SCOPE clause - use apex/soql-using-scope-clause` redirect, and it survives the shipped gloss clip. The redirect is not yet symmetric: `apex/soql-using-scope-clause` ends its description with "NOT for authoring scoping rules beyond their SOQL-operator criteria" — an exclusion without a named destination, and one that falls outside its own gloss clip. Naming `admin/scoping-rules` there is an open item on that package, not on this one.

**Resolution status:** Resolved by reciprocal redirects.
