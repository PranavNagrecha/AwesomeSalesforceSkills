# Well-Architected Notes — Territory Design Requirements

## Relevant Pillars

- **Scalability** — Territory design is the most significant scalability decision in ETM. Hierarchy depth, territory count, assignment rule complexity, and coverage ratios all determine whether the model degrades as the org and team grow. Poor territory design becomes increasingly expensive to change after go-live, because a realignment is a build-alongside-then-cut-over exercise rather than an edit.

- **Operational Excellence** — A well-designed territory model is one sales operations can maintain without developer involvement. Requirements must produce criteria that are stable, auditable, and tied to Account fields that are reliably populated. Two documented constraints set the operational shape: a rule holds at most 10 rule items, and "Rules can't be run via Metadata API" — the rule run is always a named person's job.

- **Security** — Territory membership is additive access. A territory grants access to records "that are assigned to this territory and are otherwise inaccessible" (`Territory2` › `accountAccessLevel`), so it cannot restrict below the org-wide default. Requirements must confirm that OWD and sharing rules are the mechanism for any restriction intent, and that the chosen access levels are legal for the current sharing model — with Public Read/Write accounts, "valid values are only `Edit` and `All`."

- **Performance** — Activation and realignment run as background work across the whole model, and the completion signal is `Territory2AlignmentLog`, not the model page. UNVERIFIED (2026-09-05): the specific claim that criteria counts above ten, or text-pattern-match conditions, degrade rule execution time is a field observation and is not stated in the Metadata API guide, the Object Reference or the App Limits Cheat Sheet. What *is* documented is the ceiling itself — ten rule items per rule — which caps the complexity a single rule can carry regardless.

- **Reliability** — Rules "run automatically when object records are created and edited"; a change to a rule is not a change to a record, so nothing is re-evaluated until someone runs the rules. Requirements must include the runbook for how realignment events are managed without coverage or forecast gaps, and must treat archiving as irreversible.

## Architectural Tradeoffs

**Hierarchy depth vs. forecast granularity:** Deeper hierarchies give more rollup granularity and cost more to maintain. The decidable test is not a number of levels but a named reader per level: a node nobody reviews a forecast at is maintenance with no consumer. Depth also compounds with the `TerritoryAndSubordinates` group, which spans a territory "and users in territories subordinate to the specified territory" — every extra level widens what a branch's members can reach.

**Rule-based vs. manual assignment:** Rules scale well where criteria are stable; named-account and strategic lists change faster than rules can be edited, and each edit is followed by a manual rule run. Manual assignment stays identifiable afterwards — `ObjectTerritory2Association.AssociationCause` distinguishes `Territory2AssignmentRule` from `Territory2Manual`, and `AccountShare.RowCause` distinguishes `Territory` from `Territory2AssociationManual` — so the design can commit to a mix and still audit it.

**One rule with many items vs. a proxy field:** Collapsing an enumeration into a proxy picklist on Account moves complexity from the territory model into data maintenance. That is usually the right trade: the rule ceiling is hard at ten items, item order is positional ("The sort order of rule items is implicitly derived from the position of the rule items in the XML"), and a `booleanFilter` whose numbering "must start at 1 and must be contiguous" is fragile to edits. A field is easier to report on, easier to fix in bulk, and easier to test.

**Geographic contiguity vs. operational convenience:** The platform has no notion of adjacency — rule items are field predicates, with `within` documented for "DISTANCE criteria only". Non-contiguous coverage is therefore always technically possible and never flagged. Where the business genuinely needs it, document the rationale so the map that confuses a new rep is a decision rather than an accident.

**Single active model vs. transition planning:** UNVERIFIED (2026-09-05): the "only one model can be Active at a time" statement is not written in the Metadata API guide or Object Reference sections for `Territory2Model`, though the state machine and the forecast hierarchy both assume it. What is documented is decisive for planning either way: a new model starts in `Planning`, `deploy()` works only on `Planning` or `Active` models, and a same-named model in `Archived` in the target org blocks the deploy permanently. Realignment is therefore a parallel build with a dated cutover and a rollback position of "do not archive the outgoing model yet."

## Anti-Patterns

1. **Mirroring the role hierarchy in territory structure** — Designing territories to match the role hierarchy, one territory per role node named after the person in it, creates fragility: when roles change, the territory structure has to change, and territory names stop describing coverage. `Territory2.ParentTerritory2Id` has no relationship to `UserRole`; the two hierarchies should be designed against their own purposes even where their shapes converge.

2. **Using ETM access to enforce restriction instead of OWD** — Specifying that reps see only their assigned accounts, while leaving Account OWD at Public Read/Write, does not work in the direction intended and can also fail at deploy: territory access only grants access to records that are otherwise inaccessible, and the Public Read/Write account model narrows the legal `accountAccessLevel` values to `Edit` and `All`.

3. **Sizing the model on a headcount ratio alone** — A territories-per-user figure is a review trigger, not a finding. The numbers that decide are accounts per leaf territory and users per leaf territory, and a membership count read from `UserTerritory2Association` without an `IsActive = true` filter counts people who left the territory months ago.

4. **Signing off a design with an undecided release path** — Every Sales Territories metadata type carries the same Usage sentence: components "don't support packaging or change sets and aren't supported in CRUD calls." A design whose delivery plan assumes a change set has a date it cannot meet, regardless of how good the coverage model is.
