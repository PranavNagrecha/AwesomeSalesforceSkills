# Well-Architected Notes — Lightning Record Page Configuration

## Relevant Pillars

**User Experience.** The record page is where most Salesforce users spend most of their day, and the assignment model decides who gets which one. The pillar concern here is not visual polish but *coherence*: an org with eleven record pages on Opportunity, assigned across three apps and six profiles, cannot describe its own user experience, let alone change it deliberately. Practitioners should watch the count of distinct pages per object and treat every new one as a maintenance liability that must justify itself against a component-visibility rule on an existing page.

**Operational Excellence.** Assignment is invisible in the place people look for it. The page's Setup record says nothing about who sees it; the overrides live inside `CustomObject` and each `CustomApplication`. Nothing in the platform renders the full matrix in one view. That makes a written assignment matrix an operational artifact, not documentation overhead — it is the only place the resolution order exists in readable form. Orgs that skip it rediscover their own configuration through incident tickets.

**Performance.** This skill's contribution to page performance is structural, made at build time: how many components sit in a region, how much is deferred behind `flexipage:tab` facets, and how many visibility rules run before first paint. A region tolerates up to 100 components, which is a ceiling, not a target. Measurement, EPT analysis, and remediation of an already-slow page belong to `admin/lightning-page-performance-tuning`; the decision that puts fifteen components above the fold belongs here.

**Security.** Component visibility filters are a *presentation* control, not an access control. Hiding a field with a `visibilityRule` does not restrict it — the field remains readable through the API, reports, list views, and any Lightning component that queries it. Field-level security and sharing are the enforcement mechanisms; visibility rules only reduce noise. The one genuinely security-relevant choice on this surface is preferring `{!$Permission.CustomPermission.<name>}` over profile-scoped page assignment, because a custom permission is assignable from a permission set and therefore auditable alongside the rest of the access model.

## Architectural Tradeoffs

**One page with visibility rules vs. many pages with narrow assignments.** One page concentrates complexity into filters that render on every page load and must each stay within a five-field expression span. Many pages spread complexity into an assignment matrix that no single Setup screen displays. The deciding question is whether the difference is *structural* (different components, different tabs, different information architecture) or *field-level*. Field-level differences belong in visibility rules. Structural differences justify a second page. In practice, most orgs over-index on the second answer because the App Builder makes cloning a page easy and makes auditing assignments hard.

**App-scoped assignment vs. profile-scoped assignment.** App scope tracks the workspace a user is in; profile scope tracks who they are. App scope is cheaper to maintain because apps change far less often than profiles, and it does not tie the page model to a profile inventory an org may be actively shrinking. Reach for profile scope only when two populations use the same app and genuinely need different structures.

**Dynamic Forms vs. the record-detail component.** Dynamic Forms buys per-field placement and per-field visibility at the cost of a larger, denser `.flexipage` file: every field becomes an `itemInstance` with an `identifier`, and the file grows from tens of lines to hundreds. That file is what deploys, diffs, and merges. Teams doing source-driven development should expect record page merge conflicts to become a real category of work after conversion, and should decide who owns the file before starting.

**Deploying assignments vs. configuring them per environment.** Shipping `CustomObject` and `CustomApplication` overrides makes assignment reproducible and reviewable, but it also means a deploy can overwrite an assignment a production admin set by hand. Orgs that let admins activate pages directly in production should either stop doing that or accept that the repo is not the source of truth for assignment. Pick one; drifting between the two produces changes that reappear after every release.

## Anti-Patterns

1. **Treating component visibility as a security boundary.** Hiding a compensation field behind a `visibilityRule` leaves it fully readable via the API, reports, and any custom component. Use field-level security to restrict, and visibility rules only to declutter.

2. **Cloning a page to serve one exception.** The second page needs its own assignment, its own deployment entry, and its own future maintenance, and it will diverge from the original within two releases. Try the visibility rule first; clone only when the information architecture genuinely differs.

3. **Assigning pages by profile in an org migrating to permission sets.** Page assignment metadata has no permission-set dimension, so profile-scoped assignments quietly convert profiles into load-bearing infrastructure that the migration then cannot retire.

4. **Deploying `FlexiPage` without `CustomObject` and `CustomApplication`.** The deploy succeeds and the change does not appear. This is the most common failure in the domain precisely because nothing reports it.

5. **Filling a region because 100 components are allowed.** The cap is a platform maximum, not a design budget. Every visible component competes for the same first paint.

## Contradiction Log

### Scope boundary — overlap with `admin/lightning-app-builder-advanced`
**This skill says:** how a Lightning page is built and, above all, how it is assigned and how the assignment resolves — page types, the three assignment rungs and their precedence, activation, deployment across orgs, and the visibility-filter grammar needed to build a page.
**`admin/lightning-app-builder-advanced` says:** advanced App Builder technique — custom Aura page templates, LWC `targetConfig` constraints on record pages, and deeper component-visibility patterns.
**Context where this skill applies:** the page does not exist yet, or it exists and the wrong users are seeing it.
**Context where the other skill applies:** the page and its assignment are correct, and the remaining problem is a custom template, an LWC exposure constraint, or a filter pattern.
**Resolution status:** Resolved — no factual conflict. Assignment and precedence are documented here only; custom templates and `targetConfig` are documented there only.

### `pageOrSobjectType` value space — conflict inside one reference page
**Scope note:** two subtypes spell this field the same way, and only one of them is disputed.

**The app-level half is NOT in conflict.** `AppActionOverride.pageOrSobjectType`, used inside `<actionOverrides>`, is documented in the CustomApplication reference as *"The name of the sObject type being overridden. Valid values are standard and custom. This value must be standard-home when actionName is tab."* Salesforce's published `trailheadapps/dreamhouse-lwc` `Dreamhouse.app-meta.xml` carries `<pageOrSobjectType>Property__c</pageOrSobjectType>` in that block, which matches the description. That file contains no `profileActionOverrides` element, so it says nothing about the profile-scoped subtype and must not be cited as if it did.

**The profile-level half contradicts itself, within a single page.**
**The `ProfileActionOverride` field description says:** *"Required. The name of the page being overridden. The only valid values are record-home and standard-home."*
**The sample `<profileActionOverrides>` XML printed on that same reference page says:** `<pageOrSobjectType>TestObj__c</pageOrSobjectType>` — an object API name, not `record-home`.
**Context where the description applies:** unresolved. No published Salesforce artifact settles which value a real org accepts in a `profileActionOverrides` entry.
**Resolution status:** Needs human review. This skill teaches the empirical rule — take the value from a file retrieved out of the target org — and `gotchas.md` Gotcha 2 states the conflict outright rather than picking a side. Do not let an agent generate this element from memory.

Where Salesforce Help and the Metadata API reference describe the same behaviour, the Metadata API reference was used here, because it names the elements a deployment actually carries.
