# Well-Architected Notes — Permission Set Expiration

## Relevant Pillars

- **Security** — Time-boxing is the control that converts standing privilege into bounded privilege. `PermissionSetAssignment.ExpirationDate` is the only platform-native mechanism in this family that does it: no other assignment object in the permission model carries a date. What practitioners must watch is *exclusivity*, not the date. The Security Guide's rule — "to revoke a permission, you must remove all instances of the permission from the user" — means an expiry reduces privilege only when the expiring assignment is the sole grant. A time-boxing programme that attaches dates to broad job-function permission sets produces audit paperwork and no privilege reduction. Design the elevation permission set narrow enough that expiring it is a real revocation, then prove exclusivity with a `Permissions<PermissionName>` filter before the grant, not after the lapse.

- **Operational Excellence** — The platform stores the date and nothing else. It does not store who approved the elevation, why, or what the renewal criteria are, and it does not notify anyone when the date approaches. That metadata has to live in the request system, and the assignment has to be traceable back to it. The two operational failure modes are symmetrical: elevations granted with no date at all (nothing rejects a null `ExpirationDate` — the field is `Nillable`), and elevations renewed reflexively because nobody re-tested the need. Both are found by the same quarterly query pair, and neither is found by looking at the org's permission set list.

- **Reliability** — The alternative to `ExpirationDate` is a scheduled job that unassigns. That trade is almost always wrong, and the reason is a reliability argument rather than an effort argument: a scheduled Apex or Flow job that fails leaves standing privilege in place and reports nothing, which is the exact outcome the control exists to prevent. A platform-enforced date has no failure path of its own. The reliability risk that remains is in the *renewal* path — a bulk delete-and-insert renewal can strand users with no assignment when the insert half fails partway, which is why extension must be a single-field `update` on the updateable `ExpirationDate`.

## Architectural Tradeoffs

**Date-bounded versus session-bounded elevation.** `ExpirationDate` bounds a window; a session-based permission set bounds actual presence. The date is cheaper to operate — no activation step, no Flow, no user training — but it keeps privilege alive for hours or weeks the user may never be at the keyboard for. Session activation is tighter but adds an activation surface and a reader that needs Setup-read privilege. There is also a trap in combining them: including a session-based permission set inside a permission set group removes the activation requirement for users assigned to the group, so the "tighter" control silently becomes the looser one during a consolidation project.

**Permission set versus permission set group as the unit of expiry.** A group gives one assignment row, one date, and one thing to review — attractive at scale. It is also, usually, the user's day job. Expiring a group that carries permanent access removes permanent access. The group is the right unit of expiry only when the entire group is temporary: a project role, a migration cutover role, an audit-window reader role. Otherwise the correct unit is a single-purpose permission set that contains the elevated capability and nothing else, which costs an extra assignment and buys a revocation that actually revokes.

**Criteria-driven revocation versus date-driven expiry.** User access policies are the supported no-code assignment engine, and they can `Revoke` as well as `Grant`. But `UserAccessPolicyAction` carries only `action`, `target`, and `type` — there is no date attribute anywhere in the policy metadata. A policy therefore expresses "access follows the attribute" and cannot express "access lasts ninety days." Orgs that adopt policies for provisioning still need `ExpirationDate` for elevation, and must then handle two terminal states in every audit: `IsActive = false` from a lapsed date, and `IsRevoked = true` from a policy, the latter requiring `ALL ROWS` to retrieve.

**API-first versus Setup-first grants.** The Setup path is discoverable and leaves a familiar audit trail, but it is gated on `psaExpirationUIEnabled` (documented default `false`), the expiration step appears only on the permission-set-side assignment flow, and guest, Self-Service, integration, and system users are not available on the Manage Assignments page at all. The API path has none of those constraints and lets the caller write an explicit `dateTime` rather than accepting whatever the UI's date picker resolves to. Orgs that time-box integration users have no choice; orgs that time-box employees should still prefer the API for anything scripted or bulk.

## Anti-Patterns

1. **Reimplementing expiry as a scheduled job.** A nightly Flow or Batch Apex that queries assignments and deletes them duplicates a platform primitive, adds a failure path that fails silently, and has to correctly model the Create-only fields on `PermissionSetAssignment`. Use `ExpirationDate`.

2. **Hanging the date on the job-function group.** Expiring a permission set group that carries the user's normal access removes their normal access. Attach the expiry to the smallest grant that contains only the temporary capability.

3. **Treating "an assignment row exists" as "the user has access."** Liveness is carried by `IsActive`, a platform-owned read-only field. Every legacy query and integration written before the org adopted expiry needs re-auditing.

4. **Time-boxing the permission set but not what it depends on.** `PermissionSetLicenseAssign` has no `ExpirationDate` and does not support `update()`. `GroupMember` has two fields and no date. A design that expires the permission set while the licence or the group membership stands has not time-boxed anything.

5. **Designing an audit control on a beta audit-trail entry.** The Setup Audit Trail line for expiration-date changes is still labelled "(beta)" in the Summer '26 Security Guide. Verify it in the target org before it becomes the sole evidence for a control, and export within the 180-day retention window either way.

6. **Renewing by delete-and-insert.** `ExpirationDate` is updateable. Delete-and-insert is required only when a Create-only field changes, and in bulk it risks leaving users with no assignment at all.

## Contradiction Log

### Retrieval of date-expired assignments — conflict with `skills/security/privileged-access-management`

**This skill says:** The Object Reference documents the `ALL ROWS` requirement for exactly one case — assignments revoked by a user access policy, where "the `PermissionSetAssignment` record isn't deleted." It makes no statement about whether a *date-expired* assignment is returned by an ordinary query. This skill therefore recommends writing lapsed-assignment queries with `ALL ROWS` because that is correct under either behaviour, and verifying the row count against a known expired assignment in the target org before signing off an audit.

**`security/privileged-access-management` says:** Expired assignments are treated as soft deletes; ordinary SOQL does not return user assignment information for assignments that have expired; retrieving them requires `ALL ROWS`.

**Context where this skill applies:** Writing or reviewing an audit query, where a wrong assumption in either direction produces a wrong population count.

**Context where the other skill applies:** Privileged-access programme design, where the practical warning — that an "expired elevations" report can return zero rows and read as a clean bill of health — is directionally correct regardless of which retrieval behaviour is true.

**Why it is unresolved:** The claim traces to `help.salesforce.com`, which does not render to any fetcher (it returns an Aura shell). It was not re-verified during this skill's research. The Object Reference, the Metadata API guide, and the Security Guide were all fetched as PDFs and none of them states it. The two positions are not contradictory in effect — both lead to adding `ALL ROWS` — but they differ on whether it is required or merely harmless.

**Resolution status:** Needs human review, or an org test. The test is one query against a permission set with a known lapsed assignment, run with and without `ALL ROWS`.

### Assignment-time expiry semantics — deliberately not stated

The exact clock time and time-zone semantics that the Setup assignment screen applies to an expiration date are documented only in Salesforce Help ("Set Assignment Expiration Details for Users in Permission Sets and Permission Set Groups"), which the Security Guide defers to by name and which cannot be fetched. No specific time of day is asserted anywhere in this skill. The guidance instead instructs practitioners to write an explicit `dateTime` through the API, where the instant is unambiguous, and to verify the UI's behaviour in the target org before promising an auditor a cutoff time.
