# Well-Architected Notes — Messaging and Chat Setup

## Relevant Pillars

- **Security** — CORS and CSP Trusted Sites are not optional performance optimizations; they are the browser-enforced security controls that prevent unauthorized domains from accessing the Salesforce API and loading the widget script. Misconfiguration (overly broad wildcards in CORS, or missing CSP entries) either blocks legitimate use or opens the org to cross-origin attacks. Every deployment domain must be explicitly registered and reviewed during security assessments.
- **Reliability** — The platform already forces a fallback: `sessionHandlerQueue` is Required and becomes the fallback whenever `sessionHandlerFlow` is set. That means the reliability question is never "is the field filled in" — it is whether the queue behind it can accept work. A populated `sessionHandlerQueue` with no routing configuration, no members, or no agent whose presence status covers the messaging channel is a silent sink: sessions leave the flow and stop. Reliable deployments own the fallback queue as a staffed destination and monitor the `Waiting` and `Error` session statuses, because neither surfaces as an error anywhere else.
- **Adaptable** — The split between the two records is a real change-isolation boundary, but not where teams assume. Routing (`sessionHandlerType`, `sessionHandlerFlow`, `sessionHandlerQueue`), auto-responses and the pre-chat *parameters* live on the Messaging Channel; the pre-chat *form* that renders those parameters, the branding pointer and the site binding live on the Embedded Service Deployment. Changing which queue answers costs one channel deploy and no widget change. Adding a pre-chat question costs both records, because a form field must match a parameter declared on the channel. Knowing which of the two a request touches is what makes the estimate honest.

## Architectural Tradeoffs

**Queue-Based vs Flow-Based Routing:** Queue-based routing is simple and observable (queue depth is visible in the Omni-Channel supervisor). Flow-based routing is flexible but adds a layer that must be monitored for faults. For organizations with simple routing needs, Flow-based routing adds complexity without benefit. For organizations with multi-skill or business-hours requirements, the queue-only path forces workarounds (multiple channels, manual transfers) that are worse than a well-designed Flow.

**Status-Based vs Tab-Based Capacity:** Under `TAB_BASED`, capacity is released when the work tab closes in the service console; under `STATUS_BASED`, it stays applied until the work is completed or reassigned. Asynchronous messaging outlives a tab, so `TAB_BASED` over-assigns exactly when volume is highest. The decision has two homes since API 65.0 — the org gate `OmniChannelSettings.enableOmniStatusCapModel` and the per-channel `ServiceChannel.capacityModel` — and a design that sets one without the other produces the behaviour it was trying to avoid. Both belong to the service-channel design in `admin/omni-channel-routing-setup`; this package only has to state which model the messaging channel assumes.

**Single Channel vs Channel Per Use Case:** A common temptation is to create one Messaging Channel and one Embedded Service Deployment for the entire org. This works initially but becomes brittle when different product lines, regions, or languages need different routing, branding, or pre-chat fields. A better pattern is one Messaging Channel per logical routing domain, with shared queues where possible, and separate Embedded Service Deployments only where branding differs.

## Anti-Patterns

1. **Reusing a Legacy Chat Deployment for MIAW** — `deploymentFeature` is an enum with `LiveAgent` and `EmbeddedMessaging` as separate values, and the MIAW-only `embeddedServiceMessagingChannel` block applies only to the latter. Legacy Chat also cannot express Omni-Channel routing through the Metadata API at all. Build a net-new deployment.

2. **Writing Contact Identity onto the Session** — `MessagingSession.EndUserContactId` is not createable or updateable. Automation that targets it fails or no-ops, and the symptom (anonymous conversations) points at pre-chat rather than at the write target. The writeable field is `MessagingEndUser.ContactId`.

3. **Treating the Fallback Queue as a Checkbox** — `sessionHandlerQueue` is Required, so it is never blank; a design review that confirms "the field is populated" has confirmed nothing. The reliability property is that the queue has a routing configuration, members, and an agent whose presence status covers the messaging channel.

4. **Branding a MIAW Deployment with `EmbeddedServiceBranding`** — that type serves the legacy chat products only. The change deploys, the window does not change, and the team spends the next hour on cache theories. Point `EmbeddedServiceConfig.branding` at a `BrandingSet`.

5. **Building the Package with Wildcards** — `EmbeddedServiceConfig` and `EmbeddedServiceBranding` do not support `*` in `package.xml`, while the neighbouring messaging and trusted-site types do. A wildcard-built change set moves everything except the deployment, and reports success.

6. **Registering Only Production Origins** — a non-allowlisted origin receives HTTP 404, which reads as a broken URL rather than a missing allowlist entry. Non-production hosts therefore fail in a way that sends the team to the snippet instead of to Setup. Register environments as a set, or use one wildcard pattern that legitimately covers them.

- Metadata API Developer Guide (v62 PDF), *ServiceChannel* and *OmniChannelSettings* — same PDF (`capacityModel` `STATUS_BASED` / `TAB_BASED` from API 65.0 and the org-level `enableOmniStatusCapModel`, which is the corrected basis for the Status-Based vs Tab-Based tradeoff below)
- Object Reference for Salesforce and Lightning Platform (v62 PDF), *MessagingSession*, *MessagingEndUser* and *ConversationEntry* — https://resources.docs.salesforce.com/262/latest/en-us/sfdc/pdf/object_reference.pdf (`EndUserContactId` field properties behind anti-pattern 2; the `Status` / `Origin` / `AgentType` / `ChannelType` picklists used for verification and monitoring; the note that the on-platform `ConversationEntry` schema covers legacy chat only, which constrains transcript-level reporting design)
