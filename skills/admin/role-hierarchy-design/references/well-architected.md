# Well-Architected Notes — Role Hierarchy Design

## Relevant Pillars

- **Security** — The hierarchy is the one access mechanism that grants by *position* rather than by *rule*, which makes it the easiest one to over-grant with. Every user placed in a role inherits everything owned by or shared with everyone below them, permanently, with no per-record evidence in the share tables. The security-relevant design questions are therefore: who is in the top role and why; does any branch sit above data it has no business reading; and for each custom object, has the Grant Access Using Hierarchies decision been made deliberately rather than left at its default. Access certification is the weak point — an auditor who reads only `__Share` rows will certify an over-granted org as clean, because inherited grants are not rows. Certify by role chain plus impersonation.

- **Performance** — Depth and breadth are paid for at write time, not read time. Salesforce materialises up to three system-defined groups per role and stores every user above a role as an indirect member of that role's group, precisely so that read-time access checks do not have to walk the tree. The cost lands on structural change instead: reparenting a role forces the platform to redo, for every user in that role and all their data, the work it would do for a single user's role change. Deep hierarchies with intermediate roles that grant nothing are pure overhead — they add membership rows and widen every future reorg without delivering access.

- **Scalability** — Two ceilings govern how far a design can grow. The role count is capped at 5,000 in orgs created in Spring '21 or later and at 500 in older orgs, raisable through Salesforce Customer Support. Less visibly, each portal-enabled account appends 1–3 roles below its owner's role, so an Experience Cloud rollout consumes hierarchy capacity that never appears on the Setup Roles page. The other scalability constraint is concurrency: granular locking allows unrelated group operations to proceed in parallel, but reparenting blocks almost all other group updates, so a hierarchy that needs frequent restructuring will throttle user provisioning and deployments in the same org.

- **Reliability** — Role changes are asynchronous and quiet. The Setup UI returns immediately while recalculation continues in the background; the documented place to watch it is the Background Jobs page, and the completion email that Salesforce documents for org-wide-default recalculation should not be assumed to arrive for a role change. A team that treats a role change as an instant operation will assert access too early, ship a broken cutover, and see intermittent "could not acquire lock" and "Group membership operation already in progress" failures in whatever integration happens to be running. Reliability here is procedural: a maintenance window, retry logic, Background Jobs monitoring, and verification after the fact.

- **Operational Excellence** — The object-level Grant Access Using Hierarchies setting is not on the `CustomObject` metadata type, so it does not deploy, does not diff, and does not survive a scratch-org build. Orgs that rely on it need an explicit register of which objects are opted out, an owner for that register, and a post-refresh verification step. The Setup Audit Trail does record changes to it, which makes drift detectable after the fact even though it cannot be prevented by source control.

## Architectural Tradeoffs

**Hierarchy depth versus role-change cost.** A deeper hierarchy expresses finer-grained "who sees whom" distinctions, but every level multiplies the indirect membership that has to be rewritten when anything moves. The tradeoff is resolved by asking, per role, which records it sees that its parent does not already see. A role with no answer is expressible as its parent and should be removed. The sourced guidance points the same way: set up roles based on data access and eliminate any roles that aren't needed.

**Branch separation versus sharing rules.** Two teams that must not see each other can be separated structurally (siblings under a thin root) or left together and narrowed later. Structural separation is cheaper at runtime and self-documenting, but it forces every genuine cross-team requirement through a sharing rule. Leaving them together and relying on rules produces a shorter hierarchy but a larger rule surface, and rules that grant to a role also grant to everyone above it unless the object's inheritance is off. Prefer structural separation when the exclusion is a policy, and rules when the sharing is an exception.

**Roles versus territories.** A role is single-parent: a user holds exactly one, and access flows up exactly one chain. Enterprise Territory Management exists because real account coverage is frequently many-to-many — a rep covers accounts by geography and by segment and by product line at once. Modelling that in roles requires either duplicated roles or over-granting through a common ancestor. The tradeoff is that territories add a second hierarchy with its own maintenance, its own recalculation profile, and its own set of reparenting operations that also block group updates. Choose territories when the coverage axis is the account, not the person.

**Concentrated ownership versus role membership.** Parking large volumes of records on a single service user is operationally convenient and is the documented cause of the worst sharing recalculations. Distributing ownership is the primary fix. When it is not possible, the tradeoff is deliberately accepting a top-of-hierarchy placement for that user — which grants them access to everything below — in exchange for never having to move them.

**Opting a custom object out of inheritance versus restriction rules.** Deselecting Grant Access Using Hierarchies is one switch that closes the path for everybody, which is right when the policy is "nobody inherits this". Restriction rules narrow specified users, which is right when only some personas must be limited — but only on the objects that support them: custom objects, external objects, contracts, events, quotes, tasks, time sheets and time sheet entries. The comparison is a live one for a custom object and does not exist at all for Account, Opportunity, Case, Contact or Lead. The opt-out is invisible to source control; restriction rules are metadata. Trade the deployability of restriction rules against the completeness of the object-level switch.

## Anti-Patterns

1. **The org-chart hierarchy.** Transcribing reporting lines into roles produces intermediate levels that grant nothing and cost recalculation on every reorg. Design from access requirements; add a level only when a named viewer needs records owned by a named group.

2. **The shared parent role.** Creating a common ancestor so two peer teams can see each other's records grants that ancestor everything under both branches. It is over-granting dressed as a structural fix. Horizontal access belongs to sharing rules and public groups.

3. **The unbudgeted portal rollout.** Enabling partner or customer portals across a large account base appends roles that never appear in Setup and cannot be edited, while making every subsequent account-owner change an expensive reparenting operation. Inventory portal roles by query and treat portal-account ownership changes as scheduled maintenance.

4. **The undeclared opt-out.** Relying on Grant Access Using Hierarchies being off for a sensitive custom object without recording it outside the metadata. The setting does not deploy, so any environment built from source rather than copied from production — a scratch org, a fresh developer org, a package install into a new org — comes up with upward inheritance fully on for the object you were protecting, and nothing in the deployment log says so.

5. **The share-table audit.** Certifying record access by querying `__Share` objects. Inherited grants leave no rows, so this method systematically under-reports exactly the access the hierarchy creates.

## Deliberate Omissions

Two numbers commonly asserted about this topic are absent from this skill because no source fetched during authoring supports them:

- **A maximum number of hierarchy levels.** The sources document a maximum role *count*, not a level count. `references/llm-anti-patterns.md` Anti-Pattern 1 exists specifically to stop an assistant from supplying the missing number from memory.
- **Whether portal roles count against the same org role ceiling as internal roles.** The 1–3-roles-per-portal-account figure is sourced; its interaction with the 500/5,000 ceiling is not. Flagged inline in `references/gotchas.md` Gotcha 5.
