# Well-Architected Notes — Restriction Rules

## Relevant Pillars

**Security — the pillar this skill exists for, and the one it most often gets misapplied under.**
A restriction rule reduces the blast radius of a sharing model that is too generous, which is real security value. What it is not is a control that survives an adversary or an unaudited integration. Salesforce documents that the rule is not applied to code executed in system mode and does not apply to holders of View All / Modify All Records or Data. In Well-Architected terms that makes it a *defence-in-depth* layer, not a *trust boundary*. The security posture question to ask on every design is: if this rule were silently deactivated tomorrow, who would gain access, and would anything detect it? If the answer is "nobody would notice," the rule is carrying more weight than its enforcement model can bear and the OWD underneath needs to change.

**Operational Excellence — the rule is invisible when it is wrong.**
There is no error, no notification, and no partial-success message when a `recordFilter` removes more rows than intended. The user simply stops seeing a record they saw yesterday. The operational practices that make this survivable are all pre-activation: deploy with `active` false, run the record filter as a query, compare the surviving row count against an expected number written down in advance, and keep an Id remap table so the same file behaves identically in every org. Post-activation, the fact that `UserRecordAccess` reports the pre-restriction answer means the org's normal access-audit tooling will not tell you the rule is working — that has to be documented wherever the tooling output is displayed, or the next admin will chase a phantom bug.

**Reliability — the failure mode is a slow query, not an outage.**
Salesforce's own guidance is to budget "three to five percent overhead to the record filter's performance" on objects with large data volumes, and to test by running the record criteria as a query in an API client. On external objects the cost is different in kind rather than degree: editing or deleting a rule causes an additional database call, and search against external object records requires additional calls each time. A rule whose `recordFilter` traverses an unindexed field on a multi-million-row object is a latency regression on every list view, report, and API call that touches the object.

## Architectural Tradeoffs

**Restriction rule versus fixing the OWD.** The restriction rule is cheap, reversible, and scoped to one profile; the OWD change is expensive, wide-blast-radius, and permanent. That asymmetry makes the rule the default choice and it is usually correct — but the rule buys a filter, not a boundary. The decision hinges on one question: does the requirement come from a regulator, a contract, or a customer commitment? If yes, the enforcement gaps are disqualifying and the OWD change has to be funded. If the requirement is "reduce noise and honour an internal norm," the rule is the right economics.

**One precomputed field versus several rules.** The criteria language supports one EQUALS test, so any multi-condition requirement is either precomputed into a stored field by automation or not expressible. Precomputing adds a flow, a field, a backfill, and a new failure mode (the field going stale). It also consumes only one of the two or five active-rule slots and keeps the composition constraint — one rule per object per user — satisfiable. Splitting into multiple rules avoids the automation but cannot express AND at all: where both rules match the same user, "only one of the active rules is observed." That is not a tradeoff so much as a common mistake dressed as one.

**Restriction rule versus scoping rule.** Both ship as `RestrictionRule` metadata differing only in `enforcementType`, which makes them look interchangeable in a repository diff. They are not. `Restrict` filters access across nine surfaces including SOQL and SOSL; `Scoping` sets the default record set in list views and reports and removes no access whatsoever. Choosing `Scoping` when the requirement was confidentiality produces a change that reviews cleanly, deploys cleanly, and protects nothing. See `admin/scoping-rules`.

## Anti-Patterns

1. **Selling the rule as a compliance control.** The eight documented gaps in it (see `gotchas.md` Gotcha 1) are not edge cases — system mode and Modify All Data describe the average nightly integration. A restriction rule presented to an auditor as the control that prevents access will not survive the first question about service accounts.

2. **Reaching for a restriction rule on Account, Opportunity, Case, or Lead.** Those are not valid `targetEntity` values for `enforcementType` `Restrict`. The impulse to look for one there is a reliable signal that the real problem is an OWD set too wide years ago, and that the sharing model is the thing that needs work.

3. **Deploying a rule with 18-character or org-specific Ids and no remap table.** The rule deploys successfully, matches a different profile in the target org, and restricts the wrong population. Nothing in the pipeline catches it.

4. **Activating on a populated object without measuring first.** An over-tight filter removes rows with no error and no notification. The row count the filter returns has to be compared against an expected number *before* `active` goes true.

5. **Treating the rule as inherited by child objects.** It is not. Each object needs its own rule, and each child has to be checked against the supported-object list separately.

## Contradiction Log

### Restriction rules as a "security boundary" — conflict with `standards/decision-trees/sharing-selection.md`

**This skill says:** A restriction rule is a run-time visibility filter enforced on nine surfaces, with eight documented gaps in it. It is a defence-in-depth layer, not a trust boundary, and it must not be the sole control behind a compliance or contractual commitment.

**The decision tree originally said:** In commit `67c6da3c0`, the "Restriction Rules vs Scoping Rules" table carried the row `Enforcement | Security boundary — user cannot see excluded records via any entry point`, and the Q8 branch read `Restriction Rule (trumps sharing; evaluated per-query)`. Both claims are contradicted by the Considerations page: restriction rules are not applied for code executed in system mode, and View All / Modify All holders see the records regardless.

**Resolution status:** Resolved in the tree. Commit `645243346` replaced the "security boundary" row with the correct enforcement and bypass detail and added the paragraph beginning "Do not call a restriction rule an absolute security boundary." This skill is now the deeper authority for the same claim, and the tree's summary agrees with it.

**Residual tension — closed during fact-check review.** Two defects survived at HEAD and have now been fixed in the tree itself:

1. The tree said "Choose Restriction Rules for compliance and data segregation" four lines above the paragraph warning they are not a security boundary. Those sentences pulled in opposite directions for exactly the reader who needs the distinction most. The compliance sentence is now qualified: choose them "for data segregation where a defence-in-depth filter is sufficient; where an auditor will test the control, change the OWD instead."
2. The tree undercounted the gaps. Its Bypassed-by row named three (system mode, View All / Modify All, calendar Show Details) and the prose below it said "three documented ways around it." Salesforce documents eight. The row now lists all eight and points at this skill's `gotchas.md` Gotcha 1 for the verbatim quotes, and the prose reads "eight documented ways around it."

The tree's Active-rules-per-object row also now records that the restriction and scoping ceilings are separate budgets. No open contradiction remains between this skill and the tree.

**Context where this skill applies:** designing, reviewing, or deploying an individual restriction rule.
**Context where the tree applies:** choosing between sharing mechanisms before any of them is built.

### Not sourced, deliberately omitted

- The exact Setup click path to the Restriction Rules node. The Developer Guide says only "set up restriction rules in Salesforce by navigating to a supported object in the Object Manager," and the fuller Setup instructions live on a Salesforce Help page that does not fetch. This skill therefore describes the metadata and API paths, which are fully sourced, and does not invent a click trail.
- Behaviour of `enforcementType` `FieldRestrict`. The Metadata API reference lists it as an enum value and says exactly one thing about it — "FieldRestrict—Don't use." — which this skill repeats verbatim and the checker enforces. No page reached during authoring describes what the value actually does, so nothing further is claimed about it.
- The release in which restriction rules reached GA. API version 52.0 is sourced as the first version supporting the metadata type; the marketing GA release is not, so it is not stated.
