# LLM Anti-Patterns — LWC Mobile Offline and Briefcase

Common mistakes AI coding assistants make when generating or advising on LWC offline UX and Briefcase Builder rules. These patterns help the consuming agent self-check its own output.

---

## Anti-Pattern 1: Assuming all referenced data is offline-available

**What the LLM generates:** Code that wires up `lightning-record-edit-form` for an Account, populates a related-list of Contacts via imperative Apex, and calls a custom `getRelatedRecommendations` method — all without any thought to which paths work offline.

```javascript
// Generated by an LLM that didn't think about offline:
import getRecommendations from '@salesforce/apex/RecCtrl.getRecommendations';

async connectedCallback() {
    this.recs = await getRecommendations({ accountId: this.recordId });
    // ...silently breaks offline. No fallback. No empty state.
}
```

**Why it happens:** LLMs default to "the network is always available" because the vast majority of LWC training-data examples assume online execution. Salesforce LWC documentation also presents online behavior as the default and offline as an extension topic.

**Correct pattern:** Branch every imperative Apex call. Either re-architect through LDS (preferred), or handle the offline case explicitly:

```javascript
async connectedCallback() {
    try {
        this.recs = await getRecommendations({ accountId: this.recordId });
    } catch (err) {
        if (!navigator.onLine) {
            this.offlineMode = true;       // show empty-state UI
        } else {
            throw err;                      // genuine failure
        }
    }
}
```

**Detection hint:** Any LWC method body containing `await get*` from `@salesforce/apex/...` without a `try`/`catch` that distinguishes offline from real errors.

## Anti-Pattern 2: Not testing the offline UX, only "designing for it"

**What the LLM generates:** A 3-paragraph code-comment about offline behavior, an LDS wire, and a comment "// Test offline by toggling network in DevTools." No actual test plan, no real-device verification, no airplane-mode scenario walkthrough.

**Why it happens:** "Offline support" sounds completed when the code mentions LDS and includes a fallback branch. The LLM doesn't have access to a real device and substitutes documentation for verification.

**Correct pattern:** When advising, always include a concrete real-device test plan as part of the deliverable:

1. Install the Salesforce Mobile App on a real iOS or Android device.
2. Open the LWC while online; verify it loads.
3. Enable airplane mode in OS settings (not just DevTools throttling).
4. Re-open the LWC. Verify all read paths work.
5. Exercise write paths. Verify the queued-changes indicator appears.
6. Force-quit the app. Re-open. Verify queued changes are still pending.
7. Disable airplane mode. Verify queued writes complete and any sync failures appear in the app's Pending Issues view.

DevTools throttling does **not** reproduce mobile-app offline behavior — the WebView caches differently from a desktop browser, and the LDS adapter behavior differs.

**Detection hint:** Any "offline LWC" recommendation that omits a real-device test plan or only references DevTools network throttling.

## Anti-Pattern 3: Treating last-write-wins as acceptable without saying so

**What the LLM generates:** An offline write flow using `lightning-record-edit-form` with no mention of conflict resolution. The user-facing rollout doc, when generated, doesn't mention that concurrent edits will silently overwrite.

**Why it happens:** Last-write-wins is the platform default and the LLM doesn't realize this is a *choice* worth surfacing. It treats "the form saves offline" as the spec being met.

**Correct pattern:** Always state the conflict-resolution semantics explicitly. If the use case can tolerate last-write-wins, document it:

```markdown
## Conflict resolution
This LWC uses last-write-wins reconciliation. If a user edits the
Account offline while the same Account is edited online by another
user, the offline user's changes will overwrite the online edits when
the device reconnects, with no warning surfaced to either user.
This is acceptable for the visit-notes use case because notes are
single-author by convention.
```

If the use case cannot tolerate it, recommend the snapshot-based detection pattern (see Example 3 in `references/examples.md`) and budget for the build cost.

**Detection hint:** Any offline-write recommendation that doesn't include the words "last-write-wins" or "conflict" in the user-facing documentation.

## Anti-Pattern 4: Confusing Briefcase Builder with Field Service offline priming

**What the LLM generates:** A user asks about offline support for service technicians using Field Service Lightning. The LLM responds with a Briefcase Builder rule and references Briefcase docs. Or vice versa: the user asks about Briefcase for a sales team and the LLM cites FSL offline-priming docs.

**Why it happens:** Both topics involve "offline data on a mobile device" and share vocabulary. The LLM blends them.

**Correct pattern:** Distinguish at the start of the response:

- **Standard Salesforce Mobile App** (in App Store / Play Store, used by sales reps, support reps, internal users) → Briefcase Builder.
- **Field Service Mobile** (separate FSL-branded app for technicians) → FSL offline priming pipeline (`Field Service Mobile Settings → Data Sync`), nothing to do with Briefcase Builder.

If the user's container is unclear, ask before designing the rule. Don't assume.

**Detection hint:** Any response that mixes Briefcase terminology (priming rules, audience, root object) with FSL terminology (priming hierarchy, page references, ServiceResource root).

## Anti-Pattern 5: Ignoring the conflict-resolution UI burden

**What the LLM generates:** "Add conflict detection by capturing `LastModifiedDate` and comparing on save." Implementation sketch is shown for the *server* side. No mention of the UI work to actually present a conflict resolution choice to the user.

**Why it happens:** The interesting part is the timestamp comparison; the boring part is the UI. The LLM optimizes for the interesting part.

**Correct pattern:** Quote the UX cost upfront. Conflict detection without conflict-resolution UI is worse than last-write-wins because the user gets a generic error and no recovery path. The minimum viable resolver UI is:

- A side-by-side display of "your offline changes" and "current server values."
- A field-level pick between the two, with a "use mine," "use server," and "merge manually" affordance.
- A confirmation step that re-validates against the latest server state before final save.

This is typically 2–5 days of additional LWC + UX work. If the budget doesn't include it, recommend last-write-wins instead.

**Detection hint:** Any conflict-detection recommendation that mentions only the server-side check without describing the resolution UI.

## Anti-Pattern 6: Generating Briefcase rules that exceed soft limits

**What the LLM generates:** A Briefcase rule with no estimate of records-per-user, often using broad filters like `WHERE OwnerId = $User.Id` on Lead or Case without scoping by status or date. For a busy account, this can prime tens of thousands of records per user.

**Why it happens:** SOQL examples in training data are typically write-once filters with no offline-volume context. The LLM doesn't think about the per-user denormalization that priming creates.

**Correct pattern:** Always include a records-per-user estimate as part of the recommendation:

```markdown
Estimated records primed per user:
  - Case: ~35 (open, last 90 days, owned by user)
  - Account: ~20 (deduped parents)
  - Contact: ~25 (one per case + shared)
  - CaseComment: ~175 (5 per case)
  Total: ~255 records — within soft limits.
```

If the estimate exceeds the published per-object soft limit (~400 per user, subject to change), narrow the filter rather than assuming the platform will gracefully degrade.

**Detection hint:** Any Briefcase rule recommendation with no records-per-user math.

## Anti-Pattern 7: Recommending `localStorage` for sensitive data without flagging the risk

**What the LLM generates:** A draft-persistence pattern using `localStorage` for an LWC handling SSN, payment card data, or other regulated fields, with no security note.

**Why it happens:** `localStorage` is the obvious answer to "persist client-side state," and the LLM applies the pattern without considering the data classification.

**Correct pattern:** `localStorage` is unencrypted, browser-scoped, and not subject to Salesforce field-level security. For PII, payment data, healthcare data, or anything else that would normally be FLS-controlled, recommend a server-side draft endpoint (custom object with appropriate sharing + a custom Apex `@AuraEnabled` save method) instead. Even if it costs the offline-write capability — the offline-write capability is incompatible with the data classification.

If the LLM is unsure of the data classification, ask before generating the pattern.

**Detection hint:** Any `localStorage.setItem` recommendation in a flow that handles user-identifying or regulated data fields.
