# Well-Architected Notes — LWC App Builder Config

## Relevant Pillars

- **Operational Excellence** — meta.xml is how admins (not developers) interact with the component over time. `masterLabel` and `description` are user-facing in Setup list views and as builder tooltips (`reference-configuration-tags` L18710, L18714), so a blank or engineer-facing value is a support cost. Property-level `description` should explain expected data, format, and range, because that text is the i-bubble in the property editor (`use-config-for-app-builder-tips` L9898).
- **Reliability** — `<objects>` on record-page targets prevents admins from dropping the component on incompatible sObjects; without it the component supports every supported object (`targets-lightning-record-page` L19363). Declaring form factors deliberately prevents a desktop-only layout from being offered on phones, and the guide strongly recommends including form-factor information for all components (L19000, L9896). Giving required properties defaults prevents the component from appearing invalid the moment it is placed (L9899).
- **Security** — design attributes decide which records, fields, or Apex callables the component touches, and an `apex://` datasource enumerates schema at design time. Filter what the datasource offers, and keep debug or feature-flag toggles out of the property panel entirely — anything exposed on a `lightningCommunity__Default` target is visible to every site admin. UNVERIFIED (2026-09-05): neither the LWC guide nor the Apex Reference Guide documents the execution context of a `VisualEditor.DynamicPickList` invoked from a builder property panel, so treat CRUD/FLS checks in that class as defence in depth rather than as a documented requirement.

## Architectural Tradeoffs

- **One bundle, many surfaces vs. one bundle per surface.** A single bundle with per-target `targetConfig` blocks is efficient, but only when the component's JS is genuinely generic — and the per-target subtag rules differ enough that "generic" is narrower than it looks (`lightning__Tab` takes no properties at all, L7987; `lightning__RecordAction` takes none either, L19307). As soon as surface-specific branching fills the JS, split the bundle. See the "Swiss-Army-Knife" anti-pattern in `examples.md`.
- **Static CSV datasource vs. Apex `DynamicPickList`.** Static is zero-runtime-cost and fine for truly stable lists. Dynamic Apex lists reflect schema changes without a deploy, at the cost of an Apex invocation each time the property panel opens, a hard dependency on a class the meta file cannot declare, and a 200-value display ceiling with type-ahead limited to those values unless `containsAllRows` is set (`apexrefguide` L248021–L248025).
- **Permissive exposure vs. strict scoping.** Leaving off `<objects>` is faster to ship but invites misplacement — and it is not symmetrically reversible: you cannot remove an object tag while the component is in use on a record page for that object (L9905). Scoping up front is cheaper than un-scoping later, because un-scoping is sometimes not possible at all.
- **Ship-then-tighten vs. get-it-right-first.** For a component that will enter a managed package or a published Experience Cloud site, "ship then tighten" is not available: `isExposed` moves only `false → true` after release (L7812), an exposed packaged component cannot drop a target or an `@api` property (L7818), and a site forbids adding `required=true` or tightening `min`/`max` (L8128–L8137).

## Anti-Patterns

1. **Shipping a record-page component with no `<objects>` scope.** Admins drop it on Case, Lead, or Contact and it fails at runtime or shows the wrong data. The fix ("add an `<objects>` element") is trivial in a scratch org and impossible in production once the component is placed on those objects' record pages (L9905).

2. **Using design attributes to hide debug or feature-flag toggles.** A `<property name="enableRawLogging" type="Boolean" default="false"/>` visible to every admin is both a support risk and, on an Experience Cloud target, a wider exposure than intended. Use custom metadata or permission-gated logic instead of admin-facing toggles.

3. **Treating the meta file's `default` as a runtime guarantee.** It is the value App Builder pre-fills, not a JavaScript initializer, and Jest tests never see it because they run independently of Salesforce (`unit-testing-using-jest-create-tests` L12326). Mirror every default in the JS class and pin it with a test.

4. **Adding targets speculatively.** Each extra `<target>` is a surface someone must verify on every deploy, and page-type support cannot be withdrawn while the component is in use on that page type (L9906).

5. **Trusting the deploy to catch a contract mismatch.** App Builder validates `apiVersion` and destructive changes, but the `event` tag metadata is not validated against the `.js` file (L9881), and a JS/config type mismatch is resolved silently in favour of the config (L18972, L9840). Cross-checking `property name` against `@api` is the checker's job, not the platform's.
