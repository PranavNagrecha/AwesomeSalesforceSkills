# Well-Architected Notes — LWC Toast And Notifications

## Relevant Pillars

- **User Experience** — The primary pillar for this skill. Choosing the wrong notification primitive (a persistent toast for a routine success, a blocking alert where a toast is sufficient, three toasts where one summary belongs) degrades the experience even when the implementation is technically correct. Toast and confirm patterns are the main mechanism for communicating system state changes in Lightning Experience.
- **Reliability** — Notifications that fail silently are worse than notifications that fail loudly. The `lightning/platformShowToastEvent` module renders nothing in LWR sites and throws no error, so the defect survives code review, survives unit tests, and surfaces only when a customer does not see a confirmation. Choosing the module from the bundle's declared targets converts that class of failure into a deploy-time decision.
- **Security** — Indirect. A promise-returning confirm before a destructive DML call is a UX safeguard against accidental data loss, not an authorisation control; it does not replace server-side permission checks. On the server side, the Send Custom Notifications user permission is a real access control: without it `send()` fails, so the permission set has to ship with the feature rather than be granted reactively.

## Architectural Tradeoffs

**Declared surface versus runtime detection.** A component that branches on a sniffed environment carries a code path nobody exercises. Declaring the surface — a `.js-meta.xml` property, or simply defaulting to `lightning/toast` everywhere — makes the choice reviewable in the diff and testable in Jest. The cost is one more configuration value an admin can set wrongly; the benefit is that the wrong setting is visible in Setup instead of invisible in production.

**Toast versus alert.** Toast is non-blocking; the user keeps working while it is visible. `LightningAlert.open()` returns a promise, so execution resumes only after dismissal. Overusing alert trains users to dismiss dialogs reflexively, which spends the attention you will need for the one message that matters.

**Confirm versus modal for destructive gates.** `lightning/confirm` is right when the decision is one binary question. When the user needs additional context, a record name to verify, or a second option (archive versus delete), the interaction needs a container, not a dialog line — use `LightningModal` and let `lwc/lwc-modal-and-overlay` own it.

**Toast versus custom notification.** A toast is free and instantaneous, and reaches exactly the person looking at that page at that moment. A custom notification costs a metadata type, a permission, and an Apex path, and reaches a user on desktop or mobile who is somewhere else entirely. Sending a custom notification for something the user just did on screen is noise; sending a toast for something they need to know an hour from now reaches nobody.

**One summary versus per-record messages.** The toast container caps a page at three concurrent toasts by default and queues the rest. Summarising a batch outcome into one message with the detail rendered on the page is not just tidier — it is the only design whose output is fully visible.

## Anti-Patterns

1. **Choosing the module before reading the targets.** `lightning/platformShowToastEvent` in a bundle exposed to an LWR Experience Cloud page is a silent no-op. The failure has no error, no log line, and no test that catches it.
2. **Persistent modes on every toast.** Treating every system message as equally urgent dilutes the signal for the ones that require attention; users learn to dismiss all toasts instantly.
3. **`window.alert()` / `window.confirm()` / `window.prompt()` in LWC.** The HTML specification has deprecated these in third-party contexts and browsers do not support them in cross-origin iframes; the platform modules are the replacement, and because they return promises rather than blocking, the code around them has to change too.
4. **Asserting the toast in Jest and calling the container covered.** The test proves the component dispatched an event. Whether a host caught and rendered it is a property of the container, which Jest does not run.
5. **Sending custom notifications one recipient at a time.** The recipient set takes group and queue ids as single values; enumerating users burns through the 500-value ceiling and duplicates membership logic that already lives in Setup.
6. **Stating `variant` and `mode` values as though they were documented.** The Developer Guide names the properties but not their accepted values. Repeating a remembered enum without checking the Component Library is how a wrong literal ships as a silently ignored one.
