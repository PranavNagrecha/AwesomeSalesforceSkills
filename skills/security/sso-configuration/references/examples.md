# Examples — SSO Configuration

## Example 1: SP-Initiated SAML From Microsoft Entra ID for 1,400 Employees

**Context:** A manufacturer runs 1,400 internal Salesforce users. Identity is authoritative in Microsoft Entra ID, which already fronts the corporate laptop estate with MFA. Users currently sign in to Salesforce with a separate password. The security team wants Entra ID to be the only route in by the end of the quarter, and the service desk wants email deep links to keep working.

**Problem:** The org has never used Federation IDs. The Entra ID team asks for "the audience and the reply URL" and the Salesforce admin is not certain which Setup value maps to either. A first attempt configured IdP-initiated login only, and every case link in an email notification dumped the user on the Salesforce home page.

**Solution:**

Step 1 — populate and prove the matching key. Entra ID will send the user's `objectId` as the `NameID`. Load it into `User.FederationIdentifier`, then confirm no blanks and no duplicates before anything else happens:

```soql
-- In-scope active users with no Federation ID
SELECT Id, Username, Name
FROM User
WHERE IsActive = true
  AND Profile.UserLicense.Name = 'Salesforce'
  AND FederationIdentifier = null
```

```soql
-- Collisions: any value used by more than one user
SELECT FederationIdentifier, COUNT(Id)
FROM User
WHERE IsActive = true AND FederationIdentifier != null
GROUP BY FederationIdentifier
HAVING COUNT(Id) > 1
```

Step 2 — create the SAML setting. In Setup → Single Sign-On Settings, enable SAML and create the configuration from the identity provider's metadata file rather than by hand, uploading the federation metadata XML exported from the Entra ID enterprise application. That import populates `issuer`, `loginUrl` and `validationCert` and removes three transcription errors. The deployable result:

```xml
<!-- force-app/main/default/samlssoconfigs/Entra_ID.samlssoconfig-meta.xml -->
<?xml version="1.0" encoding="UTF-8"?>
<SamlSsoConfig xmlns="http://soap.sforce.com/2006/04/metadata">
    <name>Entra ID</name>
    <samlVersion>SAML2_0</samlVersion>
    <issuer>https://sts.windows.net/8f3a1c4e-0000-0000-0000-000000000000/</issuer>
    <samlEntityId>https://acme.my.salesforce.com</samlEntityId>
    <identityMapping>FederationId</identityMapping>
    <identityLocation>SubjectNameId</identityLocation>
    <validationCert>Entra_ID_Signing_2026</validationCert>
    <loginUrl>https://login.microsoftonline.com/8f3a1c4e-0000-0000-0000-000000000000/saml2</loginUrl>
    <logoutUrl>https://acme.example.com/signed-out</logoutUrl>
    <errorUrl>https://acme.example.com/sso-error</errorUrl>
    <redirectBinding>false</redirectBinding>
    <requestSignatureMethod>RSA-SHA256</requestSignatureMethod>
    <userProvisioning>false</userProvisioning>
</SamlSsoConfig>
```

Step 3 — answer the IdP team precisely. The two values they asked for map like this:

| Entra ID field | Salesforce value | Where it comes from |
|---|---|---|
| Identifier (Entity ID) | `https://acme.my.salesforce.com` | The `samlEntityId` you set above — documented as "the expected audience of any inbound SAML Responses" |
| Reply URL (Assertion Consumer Service URL) | The Salesforce Login URL shown on the saved SAML configuration | Generated by Salesforce; read it off the configuration detail page, do not construct it |
| Sign on URL | The org's My Domain login URL | Enables the Entra ID app tile to work as well |
| Unique User Identifier (Name ID) | `user.objectid` | Must match what was loaded into `FederationIdentifier` |

Step 4 — test in this order, with the login form still available: SP-initiated from the My Domain login URL; an email deep link to a specific record; IdP-initiated from the Entra ID app tile; logout. Confirm each attempt in Setup → Login History and check the Login URL column shows the My Domain host.

Step 5 — only after all four pass, change the My Domain login policy so the generic hostnames stop accepting logins, having first proven the break-glass account through the My Domain URL.

**Why it works:** `samlEntityId` is defined in the Metadata API as both the issuer of Salesforce-generated requests and "the expected audience of any inbound SAML Responses," which is why it is the single value the IdP must be given as its audience. Populating `loginUrl` is what makes SP-initiated possible at all — the field is documented as "the URL where Salesforce sends a SAML request to start the login sequence," and it is the SP-initiated round trip that preserves the requested destination through `RelayState`. Deep links then survive authentication, which was the service desk's actual requirement.

**Source:** [T1] Metadata API Developer Guide, `SamlSsoConfig` — https://developer.salesforce.com/docs/atlas.en-us.api_meta.meta/api_meta/meta_samlssoconfig.htm

## Example 2: OpenID Connect Sign-In for a Partner Portal, With a Registration Handler

**Context:** A distributor runs an Experience Cloud partner portal. Partner staff already have accounts in the distributor's customer identity platform, which speaks OpenID Connect and does not issue SAML. None of those people exist as Salesforce users, and the portal cannot ask 3,000 partner staff to complete a Salesforce registration form.

**Problem:** A SAML Single Sign-On Setting cannot consume an `id_token`, so the SAML path is unavailable. Standard Just-in-Time provisioning is also unavailable in practice, because an Experience Cloud external user must be linked to a Contact on an Account before the User record can be inserted, and there is nowhere in standard JIT to perform that resolution.

**Solution:**

Step 1 — register the app at the OIDC provider, and capture the client id and client secret. Salesforce publishes the callback URL on the Auth. Provider detail page after the provider is saved; the URL suffix is derived from the provider file name, so name it once and do not rename it.

Step 2 — write the registration handler. `Auth.RegistrationHandler` has exactly two methods, `User createUser(Id portalId, Auth.UserData data)` and `void updateUser(Id userId, Id portalId, Auth.UserData data)`:

```apex
global class PartnerPortalRegistrationHandler implements Auth.RegistrationHandler {

    global User createUser(Id portalId, Auth.UserData data) {
        // Resolve the Contact by the claim the IdP guarantees to be stable.
        String partnerRef = data.attributeMap.get('partner_reference');
        List<Contact> matches = [
            SELECT Id, AccountId, FirstName, LastName, Email
            FROM Contact
            WHERE Partner_Reference__c = :partnerRef
            LIMIT 1
        ];
        if (matches.isEmpty()) {
            // Fail loudly: a silent null here becomes an unexplained login error.
            throw new PartnerProvisioningException(
                'No Contact found for partner_reference ' + partnerRef);
        }
        Contact c = matches[0];

        User u = new User();
        u.ContactId = c.Id;
        u.Username  = data.email;
        u.Email     = data.email;
        u.FirstName = data.firstName;
        u.LastName  = data.lastName;
        u.Alias     = data.lastName.left(8);   // Alias must be 8 characters or less
        u.ProfileId = [SELECT Id FROM Profile
                       WHERE Name = 'Partner Community Login User' LIMIT 1].Id;
        u.TimeZoneSidKey    = 'Europe/London';
        u.LocaleSidKey      = 'en_GB';
        u.EmailEncodingKey  = 'UTF-8';
        u.LanguageLocaleKey = 'en_US';
        return u;   // Salesforce inserts the returned User.
    }

    global void updateUser(Id userId, Id portalId, Auth.UserData data) {
        update new User(Id = userId, Email = data.email,
                        FirstName = data.firstName, LastName = data.lastName);
    }

    public class PartnerProvisioningException extends Exception {}
}
```

Step 3 — create the auth provider:

```xml
<!-- force-app/main/default/authproviders/PartnerIdp.authprovider-meta.xml -->
<?xml version="1.0" encoding="UTF-8"?>
<AuthProvider xmlns="http://soap.sforce.com/2006/04/metadata">
    <friendlyName>Partner Identity</friendlyName>
    <providerType>OpenIdConnect</providerType>
    <authorizeUrl>https://id.distributor.example/oauth2/v1/authorize</authorizeUrl>
    <tokenUrl>https://id.distributor.example/oauth2/v1/token</tokenUrl>
    <userInfoUrl>https://id.distributor.example/oauth2/v1/userinfo</userInfoUrl>
    <idTokenIssuer>https://id.distributor.example</idTokenIssuer>
    <defaultScopes>openid profile email partner_reference</defaultScopes>
    <sendClientCredentialsInHeader>true</sendClientCredentialsInHeader>
    <sendAccessTokenInHeader>true</sendAccessTokenInHeader>
    <isPkceEnabled>true</isPkceEnabled>
    <registrationHandler>PartnerPortalRegistrationHandler</registrationHandler>
    <executionUser>identity.admin@acme.com</executionUser>
</AuthProvider>
```

Step 4 — add the provider to the site's login options, and set `allowInternalUserLogin` deliberately. The Metadata API defines it as determining "whether internal users can log in with their internal credentials on the site login page" — leaving it on means an employee can bypass the partner IdP on the portal login page, which may or may not be what the security model intends.

Step 5 — write Apex tests that cover the unhappy path: a `partner_reference` claim that matches no Contact, and a claim absent from the map entirely.

**Why it works:** the registration handler is the only place where the Contact-to-Account resolution can happen before the User insert, which is why standard JIT cannot serve an external-user portal. `defaultScopes` is documented as "the scopes to send with the authorization request, if not specified when a flow starts," so requesting `partner_reference` there is what causes the claim to be present in `Auth.UserData.attributeMap` at all. `executionUser` is documented as "the username of the Salesforce admin or system user who runs the Apex handler or flow" and must hold Manage Users — the handler's SOQL and DML run in that context, not the partner's.

**Source:** [T1] Metadata API Developer Guide, `AuthProvider` — https://developer.salesforce.com/docs/atlas.en-us.api_meta.meta/api_meta/meta_authproviders.htm ; [T1] Apex Reference Guide, `Auth.RegistrationHandler` and `Auth.UserData` — https://developer.salesforce.com/docs/atlas.en-us.apexref.meta/apexref/apex_class_Auth_UserData.htm

## Example 3 (Failure and Recovery): The SSO-Only Cutover That Locked Out the Admin Team

**Context:** A services firm completed a SAML rollout, verified pilot logins, and closed the generic login hostnames on a Friday afternoon. On Saturday the IdP tenant hit an outage. Nobody in the firm could reach Salesforce, including the three system administrators, all of whom were themselves in scope for SSO.

**Problem:** The team had treated "an admin exists" as equivalent to "a break-glass path exists." All three admin accounts authenticated through the same IdP that was down. There was no account that could complete a username-and-password login, and the one candidate account had never been tested against the My Domain login URL, so nobody knew whether its password still worked or whether it had been swept up in an earlier password-expiry policy.

**What went wrong, mechanically:** closing the generic hostnames removes `login.salesforce.com` as a route but does not create an alternative. Password authentication survives on the My Domain login URL for accounts that are not forced through the IdP — but only if such an account exists, its password is known, and its identity-verification method (MFA, device activation) is reachable. Provisioning that account *after* the outage begins is not possible, because provisioning requires a session.

**Recovery:**
1. Salesforce Support restored access through the standard org-access process, which took hours rather than minutes because it is an out-of-band procedure, not a self-service toggle.
2. The team created a dedicated break-glass administrator: a non-human account, licensed, with a generated password stored in the corporate secrets vault and a registered MFA method held by two named people.
3. They proved the account end to end through the My Domain login URL, from a machine with no corporate session, and recorded the exact URL and the verification steps in the runbook.
4. They put a recurring calendar item on the account to re-test the path each quarter and after every password or MFA policy change.
5. They separated the two changes permanently in their change process: enabling SSO and closing the generic hostnames now ship as distinct approvals on distinct days.

**Why it works:** the failure mode being protected against is the identity provider being unavailable, which is precisely the moment when an IdP-authenticated administrator cannot help. A break-glass account is only meaningful if it authenticates through a path with no dependency on the failed component, and if that path has been executed recently enough that its credentials and verification methods are known to work.

**Source:** [T1] First-Generation Managed Packaging Developer Guide v66.0 (Spring '26), on the login-policy options that make the My Domain login URL mandatory; [T1] Salesforce Security Guide v67.0 (Summer '26), Monitor Login History.

## Anti-Pattern: Building an OAuth Connected App and Calling It Single Sign-On

**What practitioners do:** Asked to "set up SSO," an admin creates a connected app, enables OAuth settings, adds scopes such as `full` and `refresh_token`, and hands the consumer key and secret to the identity team. The reasoning is that both features live under authentication in Setup and both involve a third party.

**What goes wrong:** OAuth in a connected app governs an *application's* delegated access to Salesforce data — the surface `admin/connected-apps-and-auth` and `security/oauth-token-management` cover. It does not make an external identity provider authoritative for interactive user logins. Users keep seeing the Salesforce password prompt because nothing changed about how a browser session is established. Meanwhile the org has acquired a connected app with broad scopes that nobody planned to govern, and from Spring '26 the Security Guide records that "connected apps creation is restricted," so the wrong artefact may not even be creatable.

**Correct approach:** decide which of two questions is being asked.

| Question | Artefact | Skill |
|---|---|---|
| "How does a person sign in to Salesforce?" | `SamlSsoConfig` or `AuthProvider` | This skill |
| "How does an application get a token to call Salesforce?" | Connected app / external client app with OAuth settings | `admin/connected-apps-and-auth` |
| "Why is this token failing or being revoked?" | Token lifecycle analysis | `security/oauth-token-management` |
| "Why is this SAML login failing right now?" | Assertion capture and validation | `security/sso-saml-troubleshooting` |

If the answer is genuinely "both" — a mobile app whose users sign in through the corporate IdP and which then calls the API — build them as two configurations and document the boundary. They are related but they are not the same object, and conflating them produces an org that has neither working properly.
