# Well-Architected Notes — Apex Limits Monitoring

## Relevant Pillars

- **Reliability** — Governor limits are the primary reliability constraint in Apex. A transaction that exceeds any limit fails entirely and rolls back all work, and neither a `catch` nor a `finally` block runs to record it (`apexdev L39727–39728`). Guard clauses and re-queue patterns preserve partial progress and make the work resumable rather than lost. Prevention is the only reliability strategy available.
- **Performance Efficiency** — Monitoring actual consumption through the `Limits` methods and logging headroom as a percentage provides the observability needed to tune batch scope, identify hot code paths, and right-size asynchronous work. Without it, performance problems surface only as production failures.
- **Operational Excellence** — The post-transaction and org-wide horizons exist so that a limit problem is visible before a user reports one: `ApexTestResultLimits` catches a consumption regression in CI, and a `Limit_Snapshot__c` time series shows an org limit trending toward exhaustion days ahead of the breach.

## Architectural Tradeoffs

**Guard granularity vs. verbosity.** A guard before every SOQL and DML call is maximally defensive and maximally noisy. Guard any path reachable from a variable-volume context — trigger handler, Batch `execute`, Queueable `execute` — and skip isolated single-invocation utilities with predictable cost. Prefer `hasRoomFor(meter, n)` over a percentage where the per-call cost is known: it is one fact rather than one guess, and it does not need retuning when the ceiling differs by context.

**Degrading vs. failing.** A guard that returns an empty collection converts a loud, rolled-back `LimitException` into a quiet wrong answer that commits. That is the right trade only when the caller can detect truncation and the business accepts a partial result. Where it cannot, throwing an application exception is the safer degrade: the transaction still fails, but it fails with a message naming the meter instead of the platform's generic one. Decide this per call site and write it into the method's contract; do not let the default fall out of whichever branch was easier to code.

**Re-queue vs. batch splitting.** A Queueable nearing its CPU ceiling can re-queue with a cursor or be redesigned as Batch Apex with a smaller scope. Re-queue is operationally simpler, but chain depth is unbounded by default — "no limit is enforced on the depth of chained jobs… For Developer Edition and Trial organizations, the maximum stack depth for chained jobs is 5" (`apexdev L16182–16185`) — so the bound has to be deliberate, via `AsyncOptions.MaximumQueueableStackDepth` and `AsyncInfo.getCurrentQueueableStackDepth()` (`apexdev L16044–16057`). Each execution also consumes one unit of the org's shared 24-hour asynchronous allocation of "250,000, or the number of user licenses in your org multiplied by 200 — whichever is greater" (`apexdev L17689–17691`), so an unbounded chain is an org-wide capacity decision wearing local clothes. Batch Apex gives chunking and preemptive capacity checking instead: "Batch Apex preemptively checks the required asynchronous job capacity when `Database.executeBatch` is called… The batch won't start unless there is sufficient capacity for the entire job available" (`apexdev L17694–17697`).

**Scope size vs. execution count.** A smaller batch scope means more executions, each consuming async capacity and adding overhead; a larger one risks a ceiling inside one execution. The right scope is the largest value where per-execution consumption stays under about 80% of the binding constraint. Limits reset for each `execute` invocation (`apexdev L17712–17713`), which is what makes this a per-chunk calculation. When `start` returns a `QueryLocator` the value caps at 2,000 and "the optimal scope size is a factor of 2000" (`apexdev L17704–17708`).

**Alert sensitivity vs. alert survival.** Thresholds set from a round number rather than from observed peaks produce alerts nobody reads, after which the monitor is worse than absent because it looks like coverage. Two structural defences: put the percentages in `Limit_Threshold__mdt` so tuning them is a reviewed deploy rather than a code change, and emit one aggregated line per poll run rather than one per breached limit. Which limits deserve an alert at all, and who is paged, are `architect/org-limits-monitoring` decisions — this skill supplies the mechanism, not the policy.

**Polling frequency vs. data fidelity.** Polling `OrgLimits` more often than the platform refreshes it buys resolution that does not exist. Both surfaces are lagged by design: "Limit values are updated asynchronously, in near-real-time" (`apexrefguide L226215`) and REST `/limits` is "accurate within five minutes of resource consumption. For consistent values from this resource, avoid concurrent or rapid requests" (`api_rest L7792–7793`). The REST route also costs one API call per poll against the very budget it is measuring; the Apex route does not.

## Anti-Patterns

1. **Catching `System.LimitException`** — the block compiles and never runs. Prevention via guard clauses is the only pattern.
2. **Relying on `finally` for limit-breach logging** — uncatchable exceptions skip `finally` too, so the log line must be written by the guard, before the operation.
3. **Hardcoding limit ceilings** — the correct ceiling depends on context and can change between releases. Derive it from `Limits.getLimitX()` at run time.
4. **Checking limits only at method entry** — consumption compounds inside the method. A guard above a loop validates headroom for the first iteration only.
5. **Charting every meter the `Limits` class exposes** — `getAsyncCalls()` is "Reserved for future use" (`apexrefguide L220473–220490`), and `getRunAs()`, `getSavepoints()` and `getSavepointRollbacks()` all return the same value as `getDMLStatements()` (`apexrefguide L220295–220305`). Four of the lines on that dashboard are one line drawn four times, and one is empty.
6. **Building a second logger for limit readings** — `apex/debug-and-logging` already owns the sink, the correlation id, and the rollback-survival path. This skill decides when to log; it does not decide how.
