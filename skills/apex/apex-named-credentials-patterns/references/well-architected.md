# Well-Architected Notes — Apex Named Credentials Patterns

## Relevant Pillars

- **Security** — Named Credentials are the primary Security pillar control for outbound Apex callouts. Credentials stored against an External Credential principal are encrypted under the platform's org-key framework: "All credentials stored within this entity are encrypted under a framework that is consistent with other encryption frameworks on the platform. Salesforce encrypts your credentials by auto-creating org-specific keys" (`api_meta` L63604–63608, repeated for `NamedCredential` at L89891–89895). Apex never holds the secret — the strongest form the code ever sees is a merge field. The Apex Developer Guide makes the same point in its secrets guidance: outside a managed package, "use named credentials or encrypted custom fields to store secrets" (`apexdev` L13511).
- **Reliability** — The default callout timeout is 10 seconds, the per-callout maximum is 120,000 ms, and a single transaction shares a 120-second cumulative budget across every callout it makes (`apexdev` L35844–35857). Setting an explicit timeout is therefore a Reliability control, not a preference. Auth-layer failures deserve their own branch: a 401 or 403 on a Named Credential callout usually means a principal grant or credential-entry problem, not a bad request, and conflating it with a generic error costs a support cycle every time.
- **Operational Excellence** — Environment portability is a documented platform capability rather than a convention: "If you have multiple orgs, you can create a named credential with the same name but with a different endpoint URL in each org. You can then package and deploy — on all the orgs — one callout definition that references the shared name of those named credentials… the Apex class that defines the callout can be packaged and deployed on all those orgs without programmatically checking the environment" (`apexdev` L34327–34331). Any `if (isSandbox)` branch in callout code is a defect against this design.
- **Adaptability** — Splitting endpoint from authentication means an endpoint move is a one-file change: "if an endpoint URL changes, you update only the named credential. All callouts that reference the named credential simply continue to work" (`apexdev` L34324–34326). Several Named Credentials for related endpoints can share one External Credential, so a credential rotation is one edit rather than N.

## Architectural Tradeoffs

**Legacy vs. `SecuredEndpoint`:** The legacy model is a single record and is simpler to read, but every field that makes it work — `endpoint`, `protocol`, `principalType`, `username`, `password`, `oauthToken`, `oauthScope`, `authProvider`, `certificate` — is deprecated in API version 56.0 (`api_meta` L89950–90240). New work on the legacy shape is building on a deprecated surface. `SecuredEndpoint` costs more files (an External Credential, a Named Credential, a permission set) and one more concept (the principal), and buys credential reuse across endpoints plus a permission-set-based access model that can be reasoned about with the org's other access controls.

**Named principal vs. per-user principal:** `NamedPrincipal` "uses the same set of user credentials for all users who access the external system"; `PerUserPrincipal` "provides access control at the individual user level" (`api_meta` L63806–63808). The named principal is operationally simpler and is the only workable option for Batch, Queueable and Scheduled Apex, where the running user is not the person who triggered the work — but every action in the external system's audit log carries one identity. The per-user principal gives the external system real per-user attribution and lets its own access controls apply, at the cost of an onboarding flow per user, a re-authentication path in the UI, and a class of failure the platform surfaces only as a 401. There is a second, less obvious cost: "Some named credential fields rely on per-user authentication… If an admin edits one of these fields, then the previously authenticated credentials can get invalidated, requiring individual users to reauthenticate" (`object_reference` L186048–186050) — so routine admin edits become user-visible events.

**Who owns the `Authorization` header:** Letting the platform generate it (`generateAuthorizationHeader`, default `true`) keeps Apex free of auth concerns entirely and is the right default. Handing it to Apex via merge fields buys the ability to satisfy endpoints with non-standard header shapes, at the cost of two coupled settings (`generateAuthorizationHeader` false, `allowMergeFieldsInHeader` true) that must travel with the code. One constraint is not negotiable: the platform-generated header "is required if you reference the named credential from an external data source" (`apexdev` L34438–34440), so a credential shared with Salesforce Connect cannot delegate the header to Apex.

## Anti-Patterns

1. **Storing credentials in Custom Labels, Custom Settings, or Custom Metadata** — these are readable in Setup, included in exports, and deployable to sandboxes without rotation. The Apex Developer Guide's own "without a named credential" counter-example exists precisely to show how much auth code this forces into Apex (`apexdev` L34368–34395).

2. **Bypassing Named Credentials for "temporary" one-off callouts** — a hardcoded URL and a concatenated `Authorization` header are the shape that survives into production indefinitely. The checker treats this combination as an ERROR rather than a warning, because the artefact left behind is a secret in version control.

3. **Abandoning a working pattern because of a false constraint** — the two most common are "`callout:` does not work with Continuation" and "`$Credential` merge fields do not work in Apex". Both are contradicted by the guide (`apexdev` L36006–36018 and L34456–34513), and both push a developer toward a hardcoded endpoint or token. Verify a claimed incompatibility against the guide before designing around it.

4. **Deploying a `SecuredEndpoint` credential with no permission set** — the principal exists and grants nothing. Nothing in the deploy fails; the integration simply returns 401 for every user.

5. **Environment branching in callout code** — `if (isSandbox) endpoint = ...` reimplements, badly, the portability the platform already provides through same-named credentials with different URL parameters.
