# Well-Architected Notes — Einstein Activity Capture API

## Relevant Pillars

- **Security** — EAC data includes synced private email content. Any Apex code that reads `ActivityMetric` or `UnifiedActivity` must apply `with sharing` to respect Salesforce sharing rules. Developers must not expose EAC email content or engagement metrics to users who do not own or have access to the related Contact or Lead. Profile-level permission for `View All Data` should not be used as a substitute for proper sharing enforcement.
- **Reliability** — EAC data availability is conditional: it requires active connected accounts, the EAC feature being enabled, and data in the supported query objects. Code that assumes EAC data is always present will fail silently (empty SOQL results) in degraded conditions. Defensive null-checks and zero-default aggregations are required for reliability.
- **Operational Excellence** — EAC storage model differences (legacy external store vs Sync Email as Salesforce Activity) fork every operational assumption. Teams must document which model the code was written for, because the migration is no longer optional: the legacy reporting layer retires in Spring '27 (February 2027), and code that reads Activity Metrics fields degrades to nulls silently rather than failing loudly. Treat "which architecture is this org on?" as a standing item in the runbook, not a one-time discovery.
- **Performance** — `ActivityMetric` can accumulate many rows per contact over time (one row per day per metric type). Queries without an `ActivityDate` filter will scan the full history and consume significant SOQL row limits. Always filter by date range and consider using `@AuraEnabled(cacheable=true)` for UI-bound reads.

## Architectural Tradeoffs

**Aggregate counts vs individual records:** `ActivityMetric` provides aggregate daily counts and was the lowest-friction EAC read surface — it exposes no email subject, body, or individual event detail. That tradeoff is now largely settled by the platform rather than by the team: Activity Metrics retires in Spring '27, and Sync Email as Salesforce Activity delivers individual records as ordinary `Task` / `EmailMessage` at no extra query cost. The live decision is no longer "aggregate or detail" but "migrate now or carry a dated liability."

**Migrating early vs waiting for the deadline:** Waiting is cheaper this quarter and more expensive overall, because the failure mode is nulls rather than exceptions — the regression lands in business decisions (a contact scored zero reads as disengaged) before it lands in an error log, and a seeded `@isTest` suite stays green throughout. Salesforce's published sequence is audit by June 2026, build replacements June–December 2026, validate in a sandbox January 2027. Teams that treat the audit step as the deliverable, rather than the migration, get the value of the deadline without the crunch.

**Periodic batch reads vs trigger-driven reactions:** This tradeoff only exists on **legacy** EAC, which writes nothing to the standard object store and so supports no trigger-driven reaction at all. There, architectures that need to respond to new activity (e.g., updating a "last engaged" date) must use scheduled batch jobs or scheduled flows, accepting latency of typically minutes to an hour depending on sync frequency. On **Sync Email as Salesforce Activity** the tradeoff dissolves: captured email is an ordinary `Task` / `EmailMessage`, so a normal trigger fires and the scheduled job becomes dead weight. Establish the architecture before choosing — and read the trigger security note in `SKILL.md` before writing one, because a trigger over captured correspondence sees the whole org's synced email.

**Custom UI vs native Activity Timeline:** The native Activity Timeline surfaces EAC data without any developer code. Custom Apex + LWC solutions add maintenance cost and must work within the documented SOQL constraints. Prefer the native timeline for display-only needs; use custom Apex only when business logic needs to compute on EAC data or feed it into other processes.

## Anti-Patterns

1. **Choosing a query surface without confirming the EAC storage architecture** — On legacy EAC, querying Task/Event/EmailMessage produces silent zero-row results that look like a broken org. On Sync Email as Salesforce Activity, the mirror-image mistake is reaching for `ActivityMetric` and building on a surface with a Spring '27 end date. The defect is the same in both directions: assuming the architecture instead of establishing it.
2. **Asserting the trigger answer without checking the architecture** — On **legacy** EAC, syncs do not fire Apex triggers on standard objects, and an architecture that assumes a trigger will catch new synced emails or meetings silently does nothing; use scheduled patterns there. On **Sync Email as Salesforce Activity** the reverse is the defect: captured email is a real `Task` / `EmailMessage`, an ordinary trigger fires, and repeating the legacy rule ships a scheduled batch nobody needs. Either statement is wrong when made unconditionally. Whichever side you land on, the trigger's sharing **declaration** is undeclarable (implicit without sharing) and the **outcome** of each database operation follows its access mode — user mode overrides that without-sharing context. Canonical wording is in `SKILL.md` ("Security note for trigger-driven Sync Email designs"), not restated here.
3. **Ignoring EAC data absence in aggregate calculations** — Computing engagement scores or KPIs using `ActivityMetric` without handling the case where a contact has zero rows (no connected account, EAC not enabled) produces misleading zeroes that look like disengagement rather than missing data. Distinguish between "zero engagement measured" and "no EAC data available."
