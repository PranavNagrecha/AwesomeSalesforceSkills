# Gotchas — Webhook Signature Verification

Failure modes specific to verifying third-party HMAC signatures inside Apex.
Grounded in the Apex Reference Guide (Crypto, RestRequest) and the Apex Developer
Guide (Summer '26, API 67.0).

## Gotcha 1: The Base64 Rule on `privateKey` Is Bidirectional

**What happens:** Verification returns `false` for every request, including ones
generated by your own test code, and the digests differ completely rather than by
a few characters.

The cause is almost always an encoding mismatch on the key. The Apex Reference
Guide states it under `generateMac`:

> "You may supply a private key that has been encoded using Base64 encoding.
> However if you do, then you must also supply the Base64-encoded private key when
> verifying the MAC using the `verifyHMac` method."

Provider secrets arrive in wildly different shapes: Stripe's `whsec_...` is an
opaque ASCII string used raw, GitHub's is whatever ASCII string you typed into the
webhook config, and some providers issue a Base64 blob that must be decoded to raw
bytes before use.

**When it occurs:** On first integration, and again whenever someone "cleans up"
the secret retrieval by adding or removing an `EncodingUtil.base64Decode`.

**How to avoid:** Write down, in a comment next to the secret retrieval, which of
the two forms the provider uses:

```apex
// Stripe signing secret is an opaque ASCII string ('whsec_...'). Use its raw
// bytes: Blob.valueOf(secret). Do NOT base64Decode it.
Blob secret = Blob.valueOf(WebhookSecrets.get('Stripe'));

// A provider that issues a base64 secret needs the decoded bytes instead:
// Blob secret = EncodingUtil.base64Decode(WebhookSecrets.get('OtherProvider'));
```

Also note the hard cap: "The value of `privateKey` can't exceed 4 KB." A secret
larger than that is not a secret, it is a certificate, and the provider is using
asymmetric signing — see Gotcha 8.

## Gotcha 2: Apex Map Keys Are Case-Sensitive; HTTP Header Names Are Not

**What happens:** `req.headers.get('X-Hub-Signature-256')` returns `null` in
production even though the header is plainly present in the provider's delivery
log. The endpoint 401s every genuine request.

`RestRequest.headers` is a `Map<String, String>`, and Apex map lookups are exact.
The header name arrives with whatever casing the sender, a proxy, or an
intermediate load balancer produced — `x-hub-signature-256`, `X-Hub-Signature-256`,
`X-HUB-SIGNATURE-256` are all valid HTTP and all different map keys.

**When it occurs:** Intermittently, which is worse than consistently. It often
works in a test written with `req.addHeader('X-Hub-Signature-256', ...)` — the
test author uses the same casing as the handler — and fails against the real
provider.

**How to avoid:** Never index the header map directly. Use a case-insensitive
lookup helper, and use it for every header you read:

```apex
private static String headerIgnoreCase(Map<String, String> headers, String name) {
    if (headers == null) { return null; }
    String target = name.toLowerCase();
    for (String key : headers.keySet()) {
        if (key.toLowerCase() == target) { return headers.get(key); }
    }
    return null;
}
```

Write at least one test that supplies the header in a *different* case from the
one the handler names.

## Gotcha 3: Re-Serialising the Body Guarantees Verification Failure

**What happens:** The handler deserialises the JSON to inspect the event type,
then serialises it back to compute the MAC. Verification fails 100% of the time
and the team concludes the provider's documentation is wrong.

HMAC is computed over exact bytes. `JSON.serialize` reorders map keys, strips
whitespace the sender included, and normalises numeric representation. The
resulting byte sequence is different from what the provider hashed.

**When it occurs:** Whenever the handler wants to branch on payload content before
verifying — a natural instinct, and the wrong order of operations.

**How to avoid:** Verify first, parse second. Hash `req.requestBody` — the
untouched `Blob` — and only after `verifyHMac` returns `true` should the body be
deserialised. When the provider signs a derived string (Stripe signs
`"{timestamp}.{raw body}"`), build that derivation by concatenating the raw body
*string*, never a re-serialised object.

## Gotcha 4: `generateMac` + `equals` Hand-Rolls the Digest Comparison

**What happens:** Nothing visible. The code works. It also compares two digests
with `String.equals`, which short-circuits on the first differing character.

**When it occurs:** In essentially every hand-written and every LLM-generated
Apex webhook verifier, because `generateMac` is the method people know exists.

**How to avoid:** Salesforce ships a dedicated verifier:

```apex
Boolean ok = Crypto.verifyHMac('hmacSHA256', rawBody, secret, providedMac);
```

Valid `algorithmName` values are `hmacMD5`, `hmacSHA1`, `hmacSHA256`, and
`hmacSHA512`. Use `hmacSHA256` or `hmacSHA512`; `hmacMD5` and `hmacSHA1` exist for
interoperability with legacy providers and should never be chosen for a new
integration.

**Be precise about what is claimed here.** The Apex Reference Guide's `verifyHMac`
entry documents the signature, the algorithm names, the 4 KB key cap, the Base64
symmetry rule, and the Boolean return. It does **not** document the comparison as
constant-time, and no other Salesforce source consulted for this skill does
either. Do not tell an auditor that the platform guarantees it.

The recommendation survives that correction intact, because it never depended on
the guarantee. Whether Apex's `String.equals` is genuinely exploitable over the
public internet against a multi-tenant platform with variable latency is arguable.
The point is that you do not have to have the argument: the platform method costs
the same to write, removes a hand-rolled comparison from your codebase, and takes
the question out of the review entirely.

## Gotcha 5: A Valid Signature Is Not a Fresh Request

**What happens:** An attacker captures one genuine webhook delivery (from a proxy
log, a mirrored port, a leaked APM trace) and replays it a thousand times. Every
copy has a valid signature, because the signature covers the body and the body has
not changed. The handler dutifully processes all thousand.

**When it occurs:** Any integration that verifies the signature and stops there.
The signature proves authenticity and integrity; it says nothing about freshness.

**How to avoid:** Two independent controls, and you want both.

1. **A replay window.** If the provider signs a timestamp (Stripe's `t=`), reject
   requests outside a tolerance — five minutes is Stripe's own documented default.
   Check the timestamp *before* the HMAC so a replay flood costs a `Long`
   comparison, not a crypto operation.
2. **Idempotency on the provider's event id.** Upsert against an External Id,
   Unique field. Even without an attacker, providers retry on timeout and can
   deliver the same event twice on success. The `Database.UpsertResult` tells you
   whether this was the first sighting.

If the provider signs no timestamp, use your own received-at time plus strict
idempotency, and document that the replay window is unbounded.

## Gotcha 6: Slow Handlers Cause the Provider to Retry, Not to Wait

**What happens:** The handler verifies, then creates records, fires triggers, runs
a Flow, and makes a callout — taking eight seconds. The provider's client times out
at five, marks the delivery failed, and retries. The retry hits the same slow path.
The org now processes the same event repeatedly and the provider's dashboard shows
the endpoint as unhealthy.

**When it occurs:** As soon as the real payload arrives at real volume, which is
never in the sandbox where the handler was built.

**How to avoid:** The webhook resource has exactly two jobs: verify, and durably
record. Write the raw event to a staging object with an External Id and return
`200` immediately. Do the work in a Queueable or a platform event subscriber.

Also size the payload against the platform limit — the Apex Developer Guide gives
"the maximum request or response size is 6 MB for synchronous Apex or 12 MB for
asynchronous Apex." A provider that posts near that ceiling should be moved to a
notification-plus-pull design.

## Gotcha 7: Apex REST Needs a Session — Webhooks Do Not Have One

**What happens:** The provider's test delivery returns `401 INVALID_SESSION_ID`
before a single line of the handler runs. The signature code is never reached, so
debugging focuses on the wrong layer.

`/services/apexrest/*` requires an authenticated Salesforce session. A third-party
webhook has no user, no token, and no cookie.

**When it occurs:** On the very first delivery attempt of every new webhook
integration.

**How to avoid:** Choose deliberately between the two supported shapes.

- **Provider authenticates.** Register a Connected App or External Client App and
  have the provider obtain a bearer token via the OAuth 2.0 client credentials
  flow bound to a dedicated integration user. Best when the provider supports
  custom auth on outbound webhooks. Keep the signature check anyway: the token
  says who is calling, the signature says the payload was not altered.
- **Public Salesforce Site.** Expose the class to the site's guest user via
  **Setup → Sites → [site] → Public Access Settings → Enabled Apex Class Access**.
  The endpoint is then reachable by anyone on the internet and the HMAC check is
  your *only* authentication — which raises the stakes on every other gotcha here.

Under the Site option, give the guest user the narrowest possible object access
and have the handler write only to the staging object. Guest-user hardening is its
own topic; see `security/guest-user-security`.

## Gotcha 8: Not Every Provider Uses HMAC

**What happens:** The team writes an HMAC verifier for a provider that signs with
RSA or ECDSA. There is no shared secret to configure, so someone invents one and
verification can never succeed.

**When it occurs:** With providers that publish a JWKS endpoint or a public
certificate rather than issuing a signing secret — increasingly common, because
asymmetric signing means the receiver never holds a forging key.

**How to avoid:** Read the provider's signature documentation before writing code
and identify the scheme. For asymmetric signatures, Apex offers:

```apex
// Verify against a raw public key
public static Boolean Crypto.verify(String algorithmName, Blob data,
                                    Blob signature, Blob publicKey)

// Verify against a certificate stored in Setup → Certificate and Key Management
public static Boolean Crypto.verify(String algorithmName, Blob data,
                                    Blob signature, String certDevName)
```

The `certDevName` form is usually what you want, because it keeps the provider's
public certificate in Certificate and Key Management rather than in a custom
metadata field. Rotation then becomes a Setup change rather than a deploy.

## Gotcha 9: Logging the Payload Logs the Secret's Effect, and Sometimes the Data

**What happens:** A debug statement writes the full request body and the
`Authorization` or signature header to a log object or to `System.debug`. The log
object is readable by anyone with the object permission; debug logs are readable
by anyone with View All Data.

**When it occurs:** During the first week of integration, when everything is being
logged to figure out why verification fails — and then never removed.

**How to avoid:** Log the decision, not the material. Event id, event type,
verification outcome, and processing status are enough to operate the integration.
Never log the raw body of a payment or PII webhook, and never log the signature
header (it is not itself a secret, but it plus a captured body is a replayable
request). If a payload must be retained for reprocessing, store it on a staging
object whose access is restricted to the integration's permission set and give it a
retention policy.

## Gotcha 10: Accepting Any Signature Scheme the Provider Offers Is a Downgrade Attack

**What happens:** A verifier splits the `Stripe-Signature` header, collects every
`vN=` value it finds, and accepts the request if *any* of them verifies. Stripe
sends a deliberately fake `v0` signature alongside the real `v1` for test events,
and the header format explicitly allows future schemes.

Stripe's own instruction:

> "Schemes start with `v`, followed by an integer. Currently, the only valid live
> signature scheme is `v1`. To aid with testing, Stripe sends an additional
> signature with a fake `v0` scheme, for test events. ... To prevent downgrade
> attacks, ignore all schemes that aren't `v1`."

**When it occurs:** Whenever the parser is written generically — `for (part : header.split(','))
{ if (part.startsWith('v')) signatures.add(...) }` reads as robust and is the bug.

**How to avoid:** Match the scheme prefix exactly. Collect only `v1`, and treat an
unrecognised scheme as absent rather than as another candidate:

```apex
if (kv[0] == 'v1') { v1Signatures.add(kv[1]); }   // exact match, not startsWith('v')
```

The same principle generalises: pin the algorithm and the scheme in your code
rather than reading either from the request. A verifier that lets the *sender*
choose the algorithm can be steered to a weak one.

## Gotcha 11: Secret Rotation Without Dual Acceptance Is an Outage

**What happens:** The secret is rotated in the provider's console and in Salesforce
at nominally the same moment. In-flight deliveries signed with the old secret fail;
deliveries after the Salesforce change but before the provider change also fail.
The window is small and the failures are silent 401s.

**When it occurs:** At every rotation, and rotation is a control most teams only
exercise after an incident — precisely when they can least afford an outage.

**How to avoid:** Accept both secrets during the cutover. Some providers hand you
this for free: Stripe sends multiple `v1=` values in the `Stripe-Signature` header
during a rotation, and a verifier that loops over all of them rides the change with
no downtime. Where the provider does not, hold `Secret__c` and
`Previous_Secret__c` on the custom metadata record and try both, with a dated
comment recording when the previous value may be removed. Delete the old value
deliberately as a separate change, not as part of the rotation.
