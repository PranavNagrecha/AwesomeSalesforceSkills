# Gotchas — Slack Workflow Builder

Non-obvious behaviors that cause real production problems when Slack workflows call Salesforce. "Connector schema" means the autogenerated Salesforce connector definitions in Slack's `slackapi/deno-slack-hub` repository (`src/connectors/salesforce/functions/run_flow.ts` and siblings). "Slack Help" means the Slack Help Center articles Guide to Slack Workflow Builder, Slack connectors for Workflow Builder, Authenticate third-party accounts to use connector steps, View workflow activity logs, and Manage workflow usage in Slack Connect conversations, all fetched 2026-10-03.

## Gotcha 1: Run a Flow Accepts Auto-Launched Flows Only

**What happens:** The Slack step lists flows, a builder picks a familiar screen or record-triggered flow, and runs fail.

**When it occurs:** The Run a Flow step's flow input is titled "Select a Flow (Only auto-launched flows are currently supported)". The Salesforce Admins blog example adds: "You can only run active autolaunched flows from a Slack workflow." UNVERIFIED (2026-10-03): the "active" requirement is stated in that Salesforce-owned blog post and not in a product guide that was fetched.

**How to avoid:** Keep a dedicated autolaunched entry flow per Slack use case, with a naming convention such as `AL_Slack_`. If the logic lives in a record-triggered flow, move it to a subflow that both can call. The skill checker reports Slack-named flows that are not `AutoLaunchedFlow` or not `Active`.

**Source:** Connector schema, `run_flow.ts`; Salesforce Admins blog, Build No-Code Slack and Salesforce Automations With Flow (admin.salesforce.com, 2025).

## Gotcha 2: The Builder's Salesforce Account Runs Every Step Unless You Change It

**What happens:** A workflow lets any channel member update Opportunities with the builder's (often admin) permissions.

**When it occurs:** Connector steps "require authentication with the third-party service". When adding a step, the builder can "allow them to use your account" or require each person to authenticate: "Under Whose account should be used for this step, select The person using the workflow." In coded workflows the same choice is `credential_source: "END_USER"` or `"DEVELOPER"`, and END_USER workflows "can only be started by a Link Trigger". An earlier version of this skill said the identity model was unknown; the Slack sources document it.

**How to avoid:** Choose "The person using the workflow" when each user's Salesforce permissions should apply. If a shared account is needed, use a least-privilege integration user rather than an admin's personal account.

**Source:** Slack Help, Authenticate third-party accounts to use connector steps; Slack developer docs, Integrating with services requiring external authentication (credential_source).

## Gotcha 3: Disconnecting the Builder's Account Breaks the Workflow

**What happens:** A builder changes roles or tidies their connected accounts, and every workflow that used their Salesforce account stops working.

**When it occurs:** "If you built a workflow with a connector step that uses your account credentials, you'll need to re-connect it before the workflow will run successfully." Coded workflows behave the same way: removing a collaborator's external account deletes the selected auths for workflows that used it.

**How to avoid:** Add workflow managers, document whose account each step uses, and prefer a shared integration identity that is not tied to one person's employment.

**Source:** Slack Help, Authenticate third-party accounts to use connector steps (Disconnect your account); Slack developer docs, Integrating with services requiring external authentication.

## Gotcha 4: Slack Connect Partners and Connector Steps

**What happens:** A partner in a shared channel cannot start the workflow, or worse, can start it and writes to Salesforce under an internal account.

**When it occurs:** Owners and admins control whether external people can use workflows, including workflows with third-party connector steps. "External people can only use workflows with third-party connector steps that don't require them to authenticate their third-party accounts," and they "can't start or continue a workflow" that contains connector steps requiring them to authenticate. The developer docs add that external users cannot use a workflow containing connector functions built by your organization, which can surface as a `home_team_only` warning.

**How to avoid:** Decide the Slack Connect setting with the workspace owner. Do not expose a connector step that uses an internal account to external people; route partner requests through a Salesforce-side intake instead.

**Source:** Slack Help, Manage workflow usage in Slack Connect conversations; Slack developer docs, Creating connector functions.

## Gotcha 5: Deployments That Rename or Deactivate a Flow Break Published Workflows

**What happens:** A release renames the target flow or deactivates it, and the Slack workflow fails at the Run a Flow step.

**When it occurs:** The step stores `flow_name`; a renamed, deleted, or inactive flow no longer matches. UNVERIFIED (2026-10-03): whether Slack re-resolves the flow after a rename when the step is re-saved is not documented in the fetched sources.

**How to avoid:** Treat Slack workflows as dependents of their flows: list them in the flow's deployment checklist, avoid renaming API names, and re-open and republish the Slack workflow after any change.

**Source:** Connector schema, `run_flow.ts` (`flow_name` input); practice guidance for the rest.

## Gotcha 6: Outputs Are Visible to Everyone in the Channel

**What happens:** A flow returns a case description or a sensitive field, and the confirmation message posts it to a public channel.

**When it occurs:** Run a Flow returns `result` (the flow outputs), and later steps post whatever they reference. Slack messages are visible to everyone who can read the channel or DM, regardless of their Salesforce field access.

**How to avoid:** Expose only the outputs the Slack message needs, prefer IDs and record URLs (`record_url` from the record steps), and use private channels or DMs for sensitive confirmations.

**Source:** Connector schema, `run_flow.ts` and `update_record.ts` outputs.

## Gotcha 7: Activity Logs Keep 90 Days and Show Only to Managers

**What happens:** An incident review needs last quarter's failed runs, and the history is gone.

**When it occurs:** "You can only view workflow activity from the last 90 days," and the activity log is available to members who manage the workflow, filtered by complete, in progress, workflow error, canceled, or awaiting user action.

**How to avoid:** Add workflow managers, review the log after each release, and record failures somewhere durable (for example a Salesforce log record written by the flow).

**Source:** Slack Help, View workflow activity logs.

---

## Gotcha 8: Connectors May Need Admin Approval and a Paid Plan

**What happens:** A builder cannot find the Salesforce steps in Workflow Builder.

**When it occurs:** "If your workspace or Enterprise organization requires app approval, connectors will need to be approved for use before they appear in Workflow Builder." Workflow Builder and connector authentication are listed as available on paid plans.

**How to avoid:** Ask the workspace owner to approve the Salesforce connector and confirm the plan before design work. Connect the org first with `integration/slack-salesforce-integration-setup` when Salesforce features are missing entirely.

**Source:** Slack Help, Slack connectors for Workflow Builder; Guide to Slack Workflow Builder.

---

## Gotcha 9: Every Run Is a Salesforce Transaction

**What happens:** A workflow triggered on every message in a busy channel floods Salesforce with flow interviews and DML.

**When it occurs:** Each Run a Flow execution starts an autolaunched flow transaction in Salesforce with the usual limits. UNVERIFIED (2026-10-03): the earlier version of this skill mentioned org-wide caps on asynchronous calls in a rolling window for Salesforce-to-Slack automation; no fetched source gives a number for Slack-initiated runs.

**How to avoid:** Trigger on deliberate actions (links, shortcuts, specific reactions) rather than every message, keep the flow short and idempotent, and move heavy work to asynchronous Salesforce paths.

**Source:** Practice guidance; Slack Help, Guide to Slack Workflow Builder (trigger types).
