# LLM Anti-Patterns — Loyalty Management Setup

Common mistakes AI assistants make on Salesforce Loyalty Management. Facts cite Loyalty Management, Spring '26 (loyalty.pdf), the Loyalty Management Developer Guide object and resource pages, and the Metadata API Developer Guide, Version 67.0.

## Anti-Pattern 1: Using Non-Qualifying Points for Tier Assessment

**What the LLM generates:** A program with a single "Points" currency used for both tier measurement and redemption.

**Why it happens:** A single universal points balance is the intuitive model for loyalty programs.

**Correct pattern:** Create a qualifying currency associated with the tier group for status and a non-qualifying currency for redemption. Qualifying currency "is used for a member's tier evaluation"; non-qualifying currency is what members earn to redeem.

**Detection hint:** A design with one currency serving both tier advancement and redemption.

---

## Anti-Pattern 2: Telling admins to activate and schedule DPE jobs in Setup

**What the LLM generates:** "Go to Setup > Data Processing Engine, activate Reset Qualifying Points, and click Schedule." An earlier version of this skill said the same.

**Why it happens:** Batch jobs are usually scheduled where they are defined.

**Correct pattern:** The Loyalty guide says admins clone the template definitions, customize and activate the clone, and then run it from Flow Builder, where the activated clone appears as an action: "Use the action to run the definition at your required frequency." Build a scheduled flow per clone.

**Detection hint:** Instructions that schedule a loyalty DPE template directly, or that never mention cloning.

---

## Anti-Pattern 3: Reversing the qualifying currency and tier group constraint

**What the LLM generates:** "Each tier group supports exactly one qualifying currency, so create a second tier group for engagement points." An earlier version of this skill stated this rule.

**Why it happens:** The real constraint is easy to read backwards.

**Correct pattern:** "Qualifying points can be associated with only one tier group. A tier group can have more than one qualifying point." The generated tier assessment process uses one currency's minimum balance (the tier group's `TierAssessmentCurrencyId`); status that depends on two or more currencies needs a custom Tier Processing process.

**Detection hint:** A claim that a tier group cannot hold more than one qualifying currency, or a design that reuses one qualifying currency across two tier groups.

---

## Anti-Pattern 4: Inventing two partner DPE definitions

**What the LLM generates:** "Activate both Create Partner Ledgers and Update Partner Balance." An earlier version of this skill said the same.

**Why it happens:** The template name contains two verbs, so the model splits it.

**Correct pattern:** There is one template, Create Partner Ledgers and Update Partner Balances, which updates partner points (prepaid) or balance amount (postpaid) and creates credit and debit ledgers. Clone it, activate the clone, and run it from a flow.

**Detection hint:** Partner setup instructions that list two separate partner DPE definitions.

---

## Anti-Pattern 5: Multiple Loyalty Programs on One Experience Cloud Site

**What the LLM generates:** "Associate the Loyalty Member Portal site with all your loyalty programs."

**Why it happens:** Sites are usually multi-purpose.

**Correct pattern:** "You can't associate the same Experience Cloud site to another loyalty program." Use one site per program, or leave the site unassociated, in which case it shows every program the contact belongs to.

**Detection hint:** Instructions to associate one site with several programs.

---

## Anti-Pattern 6: Expecting tier changes from DPE runs

**What the LLM generates:** "Run the DPE jobs to upgrade members who reached the Gold threshold."

**Why it happens:** The DPE templates handle balances, reset, and expiration, so the model assumes they handle tiers too.

**Correct pattern:** Tier upgrades come from the Change Tier loyalty program process generated by Manage Tier Eligibility > Generate Rules, run in real time as a child of a Transaction Journal process or through a Batch Management job. Regenerate it after changing tier thresholds, names, or adding a tier.

**Detection hint:** A tier upgrade plan with no loyalty program process and no Batch Management job.

---

## Anti-Pattern 7: Posting transaction journals without checking promotion limits

**What the LLM generates:** An integration that posts every POS transaction straight to `/connect/realtime/loyalty/programs/{programName}` with promotions attached.

**Why it happens:** The model assumes the platform enforces every configured limit.

**Correct pattern:** The developer guide says promotion limits on `PromotionLimit` records "aren't automatically enforced" by this resource. Call Eligible Promotions List (POST) first and pass its result as `appliedPromotions`.

**Detection hint:** A call to the Transaction Journals Execution resource with `appliedPromotions` and no preceding eligible-promotions call.
