# Examples — Data Cloud Code Extensions

All examples below are grounded in the official Code Extension developer guide
(`developer.salesforce.com/docs/data/data-cloud-code-ext`). Where the docs describe a
contract without publishing full sample code, the example shows the *shape* and flags it —
the scaffold generated by the Code Extension plugin and its `examples/` folder are the
authoritative source for exact SDK signatures. Do not invent SDK method names.

## Example 1: Toolchain verification before any coding

**Context:** a developer is starting their first code extension and wants to fail fast on
environment problems instead of at deploy time.

**Problem:** the toolchain has hard version floors — a generic Python or an old CLI produces
confusing downstream failures.

**Solution:** verify each documented prerequisite explicitly.

```bash
# Salesforce CLI must be 2.130.9 or later
sf version

# Python must be 3.11 specifically (pyenv on macOS/Linux;
# Python.org / Microsoft Store / pyenv-win on Windows)
python3.11 --version

# Azul Zulu OpenJDK 17.x
java -version

# Docker Desktop running (WSL 2 backend on Windows)
docker info

# Data Custom Code Python SDK installed for the 3.11 interpreter
python3.11 -m pip show salesforce-data-customcode   # macOS/Linux
py -3.11 -m pip show salesforce-data-customcode     # Windows

# Authenticate against the SANDBOX you'll validate in — the runnable command is
# `sf org login web`; the setup guide lists the environment-specific flags
# (production/Developer Edition vs. sandbox vs. custom domain)
sf org login web
sf org display --target-org <sandbox-alias>
```

Also confirm in the org itself: Developer/Enterprise/Performance/Unlimited edition, Code
Extension enabled in **Feature Manager**, **no BYOK**, and the **Data Cloud Architect**
permission set for whoever runs and monitors the code. The Code Extension CLI plugin must be
**0.1.5 or later**.

**Why it works:** every check maps 1:1 to a documented prerequisite, so a green checklist
means the only remaining variables are your code and your org config.

## Example 2: Project package anatomy (what each scaffold file is for)

**Context:** the plugin scaffolds a project and the developer needs to know what to touch
and what to leave alone.

**Problem:** the package is a containerized build — editing the wrong file (the `Dockerfile`)
breaks deployment in ways that look like platform errors.

**Solution:** treat the scaffold roles as a contract:

```
my-transform/
├── Dockerfile              # containerized builds/deployments — DON'T MODIFY
├── requirements.txt        # pip packages the script needs AT DEPLOYMENT
├── requirements-dev.txt    # scaffold-owned local-dev pins — DON'T MODIFY
├── payload/
│   ├── config.json         # Data 360 deployment configuration
│   └── entrypoint.py       # your batch-transform logic lives here
├── examples/               # sample code + data shipped with the scaffold
├── .devcontainer/          # VS Code Dev Container configuration
└── README.md
```

Rules of thumb:

- New runtime dependency (e.g. a parsing library)? Add it to `requirements.txt`.
- Do not edit the scaffold `requirements-dev.txt` (setup guide: don't modify). Extra test
  tools stay in the local venv so they never ship in the deployed container.
- All transform logic goes in `payload/entrypoint.py`; `payload/config.json` carries the
  deployment configuration.
- Start from the scaffold's `examples/` folder for working SDK usage rather than writing
  entrypoint code from memory.

**Why it works:** the split keeps the deployed container minimal and reproducible, and the
unmodified `Dockerfile` keeps your build identical to what the platform expects.

## Example 3: Batch transform script plan with object-type parity

**Context:** an org ingests raw order lines into a DLO and needs a cleansed, deduplicated
output that native transforms can't produce.

**Problem:** the first design read the raw DLO and wrote directly to a standard DMO —
crossing object types, which the platform does not allow.

**Solution:** design the pipeline around the parity rule *before* writing Python:

| Read from | May write to | Notes |
|---|---|---|
| DLO(s) | DLO(s) only | e.g. `Raw_Order_Lines__dll` → `Clean_Order_Lines__dll` |
| DMO(s) | transform-type DMO(s) only | DMO→DMO transforms can only target transform-type DMOs |

Corrected flow:

```
Raw_Order_Lines__dll ──(code extension script: cleanse, dedupe)──▶ Clean_Order_Lines__dll
Clean_Order_Lines__dll ──(standard mapping)──▶ downstream DMO
```

Then wire the deployed script to a **batch data transform** and run it on demand or on a
schedule. After the run, review `DataCustomCodeLogs__dll` for the execution logs, and
manually assign and audit governance tags on the target DLO the script created.

**Why it works:** parity is enforced by the platform (DLOs→DLOs, DMOs→DMOs), so putting the
mapping step *after* the code extension keeps each stage inside its documented contract.

## Example 4: Custom chunking function contract

**Context:** a knowledge base is indexed for RAG, but default chunking splits product specs
away from their product names, degrading retrieval.

**Problem:** the developer wants the function to query a product DMO at runtime to enrich
chunks — which chunking functions cannot do.

**Solution:** design within the documented invocation contract:

```
source content
   │  Data 360 parses it into SearchIndexChunkingV1DocElement objects
   ▼
SearchIndexChunkingV1Request  ──▶  your function  ──▶  SearchIndexChunkingV1Response
   (parsed doc elements in)         (pure chunking)      (chunks out)
   ▼
Data 360 vectorizes and indexes the returned chunks
```

Design constraints to honor in the implementation:

- The function receives only content that was successfully ingested and is readable by the
  search-index pipeline — it does **not** read DLOs/DMOs at runtime. Any enrichment data
  must already be *in* the content, put there upstream.
- Data 360 can invoke the function multiple times depending on batching — process each
  request independently; keep no state between invocations.
- Chunk boundaries are the whole job: e.g. keep a product's name and specs in the same
  chunk so RAG answers stay accurate.
- Log nothing sensitive: output only what's appropriate for anyone with access to the Logs
  DLO; never PII or credentials to stdout.

Wire-up: after deploying, create the search index with **Advanced Setup** and select the
deployed function as the **chunking strategy**.

**Why it works:** the typed request/response payloads are the entire interface — respecting
them (instead of treating the function as a data job) is what makes the function valid.

## Example 5: Sandbox-to-production promotion with a DevOps Data Kit

**Context:** the batch transform from Example 3 passed sandbox validation and must move to
production.

**Problem:** the team reached for a change set. The Code Extension developer guide documents
one promotion mechanism for code extensions — the DevOps Data Kit — so any other plan is
off the documented path.

**Solution:** build a **DevOps Data Kit**:

1. Add the batch data transform to the data kit — the referenced code extension is
   **automatically included**.
2. **Manually add** every DLO/DMO the code extension references (they are *not*
   auto-included).
3. Deploy. The sequence is fixed: **DLOs/DMOs → code extensions → batch data transforms**;
   the code extension must deploy before any batch transform that references it.
4. If a component fails, deployment stops and subsequent components aren't deployed — fix
   and redeploy rather than assuming partial success.
5. Confirm production has the same gates as sandbox: edition, Feature Manager enablement,
   Data Cloud Architect permission set.

**Why it works:** the data kit is the documented promotion mechanism for code extensions and
their transforms, and the fixed order guarantees every reference resolves at deploy time.

## Anti-Pattern: inventing SDK/CLI surface area

**What practitioners do:** write `entrypoint.py` from memory using imagined SDK classes, or
script deployment with made-up `sf` subcommands found in no documentation.

**What goes wrong:** the code fails at container build or deploy with errors that look like
platform bugs; reviews can't verify the code against any doc.

**Correct approach:** scaffold with the Code Extension plugin (0.1.5+) and copy working
patterns from the generated `examples/` folder; keep the verified toolchain commands
(Example 1) as the only hand-typed CLI surface, and consult the Code Extension developer
guide for everything else.
