# Problem and opportunity

## Practitioner problem

Salesforce engineering decisions depend on several kinds of state at once: local metadata and code, deployed org configuration, permissions, automation order, job/test results, release/API behavior, and platform-specific constraints. Generic agents can produce fluent advice while using the wrong project, wrong org, stale guidance, incomplete logs, or too much low-salience context.

## Repository opportunity

SfSkills already contains a large governed knowledge substrate, tiered discovery, active runtime agents, commands, mostly read-only MCP tools, validators, fixtures, and live factuality/probe checks. The opportunity is not to add more prose. It is to convert that substrate into installable products whose claims are grounded, challenged, replayable, and behaviorally tested.

## Market timing

Official Salesforce tooling is exposing broad MCP and skills surfaces, including dynamic/small-surface discovery patterns. Agentic hosts are standardizing plugins, skills, subagents, commands, MCP, hooks, and cloud execution. DevOps/org-intelligence vendors are adding Salesforce-grounded agents. This makes raw tool access and generic generation less differentiated while increasing demand for least-privilege, cross-host assurance and measurable output quality.

## Product opening

SfSkills can own the layer that makes an agent answer responsibly:

- identify the exact target;
- select only relevant Salesforce knowledge;
- gather bounded read-only observations;
- distinguish observed fact from inference;
- preserve contradictions and unknowns;
- independently review consequential output;
- provide a replayable evidence packet;
- compare behavior across hosts/models/releases.
